I work as a software engineer with no formal training in philosophy. I have recently encountered the metaphysical debate between endurantism—the view that a concrete object is wholly present at each moment at which it exists—and perdurantism—the view that an object persists by being composed of successive temporal parts, like a four-dimensional worm. Rather than request an exposition or bibliography, I want you to design a runnable 75-minute workshop for approximately eighteen technical colleagues—engineers and product managers with no philosophical background—that makes them feel the conceptual force of this distinction through action before anyone names it.

To avoid standard philosophical examples, ground the exercise in the following invented scenario. A cloud-native application called Atlas is being migrated from a monolithic architecture to a distributed microservice mesh. During the migration, every line of executable code, database record, and active user session is rewritten or relocated to new physical servers; no material substrate remains in the same process. Nevertheless, the engineering team insists that Atlas has survived uninterrupted, and end users experience no break in service. The activity should stage a structured arbitration simulation in which small groups must render binding verdicts—using only observable operational criteria such as uptime logs, API contract versions, and user identity mappings—on whether Atlas endured as the same object, was replaced by a new one, or exists now only as a sequence of discrete temporal parts.
