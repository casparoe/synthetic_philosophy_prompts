In professional discussions with colleagues who have no formal philosophy training but read popular philosophy of mind, I often encounter the analogy that philosophical intuition pumps function exactly like unit tests in software engineering. The mapping proposed is: the philosophical theory is the code module under test; the carefully constructed hypothetical scenario is the mock input with stubs isolating the relevant feature; the philosopher's intuitive judgment is the deterministic assertion checking for expected behavior; and a conflict between intuition and theory is a failing test that should cause us to reject the theory—just as a red build should halt deployment. This analogy is explicitly used to license the conclusion that intuition pumps are rigorous, reproducible, modular instruments capable of falsifying broad theoretical claims without empirical apparatus, and that treating them with skepticism is analogous to ignoring automated test failures.

I want an explicit audit of this correspondence. Please lay out the mapping table—what corresponds to the test suite, the continuous-integration pipeline that aggregates judgments across philosophers, the shared specification that defines "passing," and the debugging process that fixes either the theory or the intuition when they conflict. Then identify the precise points where the analogy fractures: for example, unit tests require state-independent reproducibility and an agreed-upon oracle of correctness, whereas intuition pumps frequently exhibit framing-dependent variability, depend on unstated background assumptions that function like hidden global state, and lack any intersubjective mechanism to distinguish a false positive in intuition from a genuine theoretical failure. Examine which features of software testing—determinism, falsifiability, isolation—are being quietly imported into the philosophical domain and whether they belong there.

Finally, determine whether the conclusion that intuition pumps should be granted authoritative, theory-refuting status survives once these disanalogies are made explicit. If the analogy was carrying that conclusion, say so; if a different software analogy—perhaps property-based testing with non-deterministic oracles, integration tests in noisy environments, or the accumulation of technical debt through untested assumptions—better captures the actual epistemic role of thought experiments, propose it and explain what it changes about how we should weigh intuitive responses against theory. I am not looking for bibliographies, author citations, or reading lists; I want a conceptual diagnosis of what the unit-test analogy can and cannot carry.
