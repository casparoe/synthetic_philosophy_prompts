I work as a software engineer building incident-response and observability tooling, and I have no formal background in philosophy, but I keep running into conceptual trouble when I try to formalize root-cause reasoning for distributed failures. I sketched the following argument and it now strikes me as proving too much—if it is sound, then no microservice outage could ever have a root cause, which seems absurd. I want to know where the leak is.

(1) On a counterfactual account of causation, roughly in the Lewis style, event C caused event E only if, holding the actual laws and background conditions fixed, in the closest possible world where C does not occur, E does not occur.

(2) In any realistic distributed system, failures are overdetermined: if service C fails at time t, some other service D is already near a critical threshold, so that in the closest world without C's failure, D fails shortly afterward and produces the exact same system-level outage E.

(3) Therefore, for any candidate component C, there exists a nearby counterfactual world without C in which E still happens; counterfactual dependence fails, and C is not a cause of E.

(4) On an interventionist account, roughly in the Pearl style, C causes E only if there is a surgical intervention on C—fixing its value via a do-operator—while holding all other structural equations constant, and this intervention changes the value of E.

(5) But in reactive architectures, D's state-transition rules are defined in terms of C's outputs; holding D's mechanism constant while altering C violates the system's own specification, so there is no coherent modular intervention on C alone.

(6) Hence the interventionist account also denies that C caused E, because no valid do-operation on C exists that isolates it from D.

(7) So both dominant philosophical theories of causation imply that distributed system failures have no root causes.

(8) Yet root-cause analysis is a coherent and successful engineering practice; treating it as conceptually impossible would undermine every post-mortem and automated diagnosis pipeline we build.

(9) Therefore at least one of premises (1) through (7) must be false.

If I have to choose, I would most like to keep (1) and (8) intact. Which step should I reject? Explain why that step looked plausible in an engineering context—perhaps because replay logs and modular service boundaries make it seem natural—and then price the alternatives: what does giving up (1) cost for someone who wants causation to be objective rather than model-relative, and what does giving up (5) or (6) cost for someone who wants causal inference to remain computable from observational traces?
