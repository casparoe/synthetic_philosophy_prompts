I'm a software engineer with no formal philosophy background, but I've been trying to apply the frame-message / outer-message / inner-message distinction I first encountered in Douglas Hofstadter's Gödel, Escher, Bach to the artifacts I work with. By frame message I mean the decoding rules that tell a recipient how to read the artifact—syntax, grammar, protocol conventions, or biological translation tables. By outer message I mean what you get applying those rules straightforwardly. By inner message I mean a second readable layer that appears only if you apply a different decoding frame to part of the outer layer.

Here are my gut verdicts on four cases. I want to know whether there's a coherent principle behind them.

Case 1: A C source file. The frame is the C grammar and compiler conventions. The outer message is the algorithm it implements. Buried in the comments is a poem formed by the first letters of each line—readable only if you ignore the code semantics. Verdict: The file's meaning as a program is entirely the frame plus the outer message; the poem is physically present but not part of the artifact's meaning.

Case 2: A synthetic gene sequence stored in a lab database. The frame is the standard genetic code. The outer message is Protein A, which the database entry describes. But a frameshift reveals Protein B, which is actually expressed in vivo and is toxic to the host cell. Verdict: The gene's biological meaning includes both the outer and the inner message; treating the inner layer as noise would be a serious mistake.

Case 3: An IETF protocol specification document. The frame is English plus the formal grammar used for specs. The outer message is the protocol rules. There is also a pattern in the example IP addresses and in the section numbering that signals "this is documentation, not live traffic" to experienced readers. Verdict: That signaling pattern is not a separate inner message; it is part of the frame itself—part of how the community knows how to read specs.

Case 4: A compiled binary distributed with a hidden "easter egg" that activates only on a specific, undocumented input sequence, intentionally placed by the original developers. The frame is the CPU instruction set architecture. The outer message is the program's standard behavior. The hidden behavior is readable only if you apply an input-frame different from normal use. Verdict: Unlike Case 1, the easter egg is part of the software's full meaning, because it was intentionally engineered and is discoverable through interaction with the artifact.

The tension: Case 1 and Case 4 both embed hidden readable layers in executable artifacts, yet I want to exclude one and include the other. Case 2 treats an inner layer as genuinely meaningful, while Case 3 collapses what looks like an inner layer into the frame.

So: Is there a precise principle—stated in terms of frame, outer, and inner messages, plus some further condition about intention, causation, or decoder community—that captures all four verdicts? If not, which verdict should I drop, and why? Apply your principle precisely, saying which clause handles which case. Then tell me what it predicts for a case I haven't listed: a trained neural-network model file whose weights produce standard outputs on normal inputs, but contain a backdoor that activates only on images carrying a specific, invisible pixel pattern. Is that backdoor part of the model's meaning?
