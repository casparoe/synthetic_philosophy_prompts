I am a software engineer with no formal training in philosophy, and I have been working through decision-theoretic puzzles like counterfactual mugging and XOR blackmail. I tried to apply them to my own domain—continuous-integration testing across parallel feature branches—and constructed what looks like a reductio that ends in an impossible obligation. I must be slipping somewhere, but I cannot locate the step.

Here is the argument. (1) In counterfactual mugging, a predictor with near-perfect accuracy fills an opaque box with one million dollars if and only if you counterfactually take only that box; if you counterfactually take both boxes, it holds only one thousand dollars. The predictor responds to your counterfactual disposition, not to your actual hand movement, so the rational choice is to one-box. (2) XOR blackmail extends this structure: you learn that either a disaster will occur or it will not, and you are asked to pay. Even in the branch where no disaster will actually happen, you should pay, because in the counterfactual branch where you refuse, the disaster is correlated with your refusal.

(3) In my CI pipeline, tests run in parallel across feature branches that share a common commit graph. The graph functions like the predictor: if I omit a specific test in branch A, the same untested code path fails in branch B, not because my omission in A caused B to fail, but because both outcomes are fixed by the same underlying commit. (4) So my decision to skip testing in my current branch is structurally analogous to two-boxing: it does not causally influence the other branch, yet the topology correlates my choice with failure elsewhere. (5) Therefore, to maximize expected outcomes across the entire branch topology, I should never skip a test in my current branch, just as I should one-box.

(6) The analogy extends further. For any counterfactual input state that I have not tested, there exists a parallel evaluation branch in which that input produces a failure precisely if I have not covered it. By the same reasoning, I am rationally required to achieve complete counterfactual test coverage—to test every possible input state—because in the branches corresponding to those untested states, failure occurs if I do not cover them. (7) Yet complete counterfactual coverage is impossible in practice; no engineer is obligated to perform the impossible. (8) So either counterfactual decision theory is false, or it imposes obligations that cannot be satisfied.

If I must preserve something, I would rather keep the analogy between branch topology and counterfactual correlation than accept an infinite testing obligation. But I suspect the failure lies between steps (4) and (6), or between (6) and (7). Where exactly does the argument break? Is there an equivocation between branch as a version-control construct and world as a decision-theoretic counterfactual, a scope shift in what must be optimized, or a modal slide from correlation to obligation? And what does rejecting that particular step cost—does it undermine the normative force of the CI analogy, or does it leave counterfactual decision theory intact but inapplicable to software practice?
