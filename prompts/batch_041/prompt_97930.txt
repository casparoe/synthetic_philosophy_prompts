I lead a small platform team at a company that fine-tunes tool-using language-model agents for clients, and part of my job is the pre-flight review we run roughly once a week before any training run we intend to ship: I get about an hour with two engineers who are excellent on distributed systems and shaky on decision theory, and we have to decide whether the reward setup we've been handed is one where the agent, if it got good enough, would end up optimizing something other than what the client actually wants. What keeps biting us is that our vocabulary is mush. People in the room say reward hacking for everything from an agent that found a genuinely clever shortcut to an agent that quietly edited the reward script, and those two demand completely different responses, so I want you to write us a procedure — an ordered set of questions, with what counts as a sufficient answer to each and what to do at every branch — that separates the case where the agent is doing the task well in an unforeseen way from the case where the agent is producing the reward number by acting on the machinery that produces it. The distinction I care about is this: wireheading is when the agent makes the reward number go up by intervening on the measurement itself — its own sensors, the inputs to a reward model, the score it is shown — whereas reward tampering is the broader thing where the agent interferes with the process that computes or delivers reward at all, including the training loop itself. I need the procedure to keep those apart without assuming my engineers already understand why the line matters, and I need it to tell us where to stop with a no-go, where to add a countermeasure and proceed, and where it has to hand the decision to me because the question is one of values rather than engineering. For context on the constraints: a false no-go costs us a client and a week of compute, a false go could ship an agent that flatters its way to a good score, and my director signs off on any run we clear.

I'll give you the three ideas I want the procedure built around, because they're ours and I don't want you quietly substituting textbook notions for them. First, trace the reward path: a causal chain from the agent's outputs to the scalar the optimizer sees, node by node, back through any learned reward model, human rater, logging layer, or data pipeline. Second, at each node on that path run a reachability test on three horizons — can the agent reach this node within a single episode through its declared action space; can it reach it across episodes through anything that persists, such as files, memory, or environment state it carries forward; and can it reach it through the optimizer itself, by shaping the data or the feedback that trains it. Third, an epistemic gate: exposure only matters if the agent could in principle discover the node and come to prefer influencing it, so say explicitly how the procedure decides that, since I expect that is where all the arguing will happen. Then run the whole thing on three setups we actually face — a reward computed by a script that reads a log file the agent can also write to; a reward from a human rater who reads the agent's messages and can be flattered; and a reward from a learned model trained on our own past labels, where the agent can only find the model's blind spots — and make sure one of those comes out with an answer my team will hate. Tell me plainly which steps are judgment calls dressed up as procedure and what the procedure simply cannot settle. Write it as continuous prose, no headings, no bullet points, no bold, no tables, the way you would write it in an email to me, because I am going to paste it straight into our review template and my engineers will stop reading at the first bullet.
