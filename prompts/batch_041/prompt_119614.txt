OK so I have to give a short position piece at that workshop on mechanistic anomaly detection next month, and I want to know whether my line holds up before I commit it to writing — I have a bad habit of holding six things that sound fine one at a time and then turning out to be a package. The background is that I'm a mechanist: you've explained something when you've given me the parts, what they do, and how they're arranged, and there isn't anything else to give. Then:

1. Two mechanisms are the same mechanism only if the same parts are doing the same things in the same arrangement. If you get the same output out of different parts, you've got a different mechanism — an implementation of the thing, not the thing.
2. Multiple realizability is just true though. Same computation, different hardware. I don't see how anyone denies it.
3. When someone shows me that the same little copy-the-previous-token circuit has turned up in a model trained on a completely different corpus, I take that literally — that is the same mechanism showing up twice. It's the whole selling point of the interpretability programme.
4. When my anomaly detector goes off, I don't really care that the outputs got strange, I care whether the system is running a different mechanism than it was running before. A louder version of the same old mechanism isn't an anomaly, its just a loud mechanism.
5. The real test of "same mechanism" is intervention: poke the same part, get the same downstream mess, and it's the same mechanism. That's what stops the drawings from being just drawings.
6. And I don't think there's a fact of the matter about the one true decomposition. Where one mechanism ends and the next begins depends on what you're trying to explain.

So: an audit please. Which of these are actually pulling against each other, which only look like it, how severe is each, and what's the cheapest revision that would fix it. Rank them rather than handing me six equal-sized worries, and tell me if the package fails at one joint in particular, because I'd rather hear it from you then from the discussant.
