A two-party escrow protocol I am designing works as follows: each side submits a program to a mutually trusted runtime, each program may read the other side's source code before choosing whether to cooperate or to defect, and the runtime guarantees that the code which executes is exactly the code that was submitted and that neither side can alter its program after the other has read it. This is precisely the setting to which the solution concept of program equilibrium applies, a profile of submitted programs being in equilibrium when neither party could have obtained a higher payoff by submitting a different program, in the knowledge that it would be read by the other. I want an account of the most important implications of that solution concept for how a protocol of this kind should be designed and appraised. Which cooperative outcomes can it sustain, and which can it not? How far does the sustained cooperation depend on the parties' mutual knowledge of one another's payoffs, and on the code-inspection guarantee being literally true rather than merely stipulated? What becomes of the analysis as that guarantee is weakened — when the other side's program is visible only through a lossy summary, when the runtime is not fully trusted, or when one party can submit a program that simulates the other without itself being simulated in return? And does the concept suggest that parties would welcome such a protocol, or that they would prefer that it not be available to them at all?
