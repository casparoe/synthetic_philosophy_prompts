I am a software engineer with no formal training in philosophy. In technical discussions I keep encountering an analogy invoked to defend a kind of conservatism: a Lakatosian scientific research programme is like a mature, long-lived codebase, so we should not abandon a long-running theory (or, by extension, a large system) just because one test fails; we should patch peripheral code and judge the whole thing by its long-run trajectory. As I have heard it, the hard core maps to core modules and architectural invariants that are deliberately shielded from change; the protective belt maps to adapters, compatibility shims, and peripheral modules that absorb requirement churn; the negative heuristic maps to a rule against editing core code in favor of patching around it; the positive heuristic maps to the architecture's roadmap; a progressive problemshift maps to a codebase whose refactors enable genuinely new capabilities; and a degenerating problemshift maps to a legacy system in which each new requirement forces another ad hoc patch that passes only the current test.

How far does this analogy actually hold? I would like a correspondence table identifying where each element has a genuine counterpart and where one side has no counterpart at all; an analysis of which breaks matter for the conclusion about when to abandon a theory or system, as opposed to incidental disanalogies; an account of what the software metaphor quietly imports into philosophy of science that is absent in Lakatos's actual picture—for instance assumptions about a designer, a maintainer, and a requirement specification; and a verdict on whether the conservatism being argued for survives once those disanalogies are on the table. If a different engineering analogy captures Lakatos's picture more faithfully, I would also like to know what it is.
