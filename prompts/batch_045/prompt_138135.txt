i keep going back and forth on this and I think I need someone to just build the thing.

Setup reminder, so we're using the same words: in the program game each player submits a program instead of an action, the program gets to read the other player's program's source, and then the two programs output actions and get paid. The usual pitch is that this dissolves the one-shot prisoners dilemma, because a program can cooperate with cooperators and defect against defectors and both sides know it. I want a case that runs the other way: one where the program-game move leaves both players strictly worse off than they would have been in the plain game.

What I need:

- A realistic one-shot situation. Two parties, no repetition, no reputation, no outside enforcement, no talking after the programs are submitted. The programs should be the sort of thing that could actually exist: smart contracts each side deposits, pricing or bidding bots filed with a platform that publishes the source, whatever you like, just no sci-fi and no superintelligence. Programs have to be deterministic (no randomness source), have to terminate, and may read each other's source and run sound bounded simulation or proof search, and nothing beyond that. No oracles, no prediction that isn't derivable from the code.

- An explicit payoff matrix for the underlying simultaneous-move game, with numbers a normal person could care about (money, or months of someones work). It has to have a unique pure-strategy Nash equilibrium, and you have to show that uniqueness by walking the deviations rather than asserting it. That equilibrium has to be strictly better for both players than what your program pair produces. I couldnt see how to do this with only two actions each — if you think it's impossible in a 2x2, say so in one line and go to three.

- A pair of programs, a few lines of pseudocode each, that is a Nash equilibrium of the program game and that produces an outcome strictly worse for both than that unique base equilibrium.

- Then the deviation check, with payoffs shown each time: submitting a constant-action program; submitting the standard cooperate-with-cooperators program; submitting the agreed program with a last-move defection bolted on; and submitting something that mimics the agreed program's source while behaving differently. Show why each fails to profit.

- No cheating. Neither party may be hostile, confused, ignorant of the payoffs, or bad at programming. Both would rather have the base-game outcome. The trap has to be structural: two competent people who both want the good outcome and can't get there one at a time. Also, I don't want the case to die to the objection that a single typo in the source sets off the destructive branch, so make the trigger behavioural if you can — compare what the programs do, not what they look like. If you can't, say so and say what breaks.

- After the scenario: which single feature is doing the work; what happens to the case if you remove it (my guess is that if programs can't condition on the other's source it collapses straight back to the base game, but tell me what else kills it); the strongest thing someone who thinks program games really do dissolve the dilemma would say against it, and whether that reply lands; and finally, honestly, whether the program framing is doing any work at all here or whether this is just an ordinary commitment-and-deterrence story wearing code as a costume.

Keep it tight: one paragraph for the scenario, at most eight lines of pseudocode per program, bullets for the checks, whole thing under about a page if you can manage it.

For context on what counts as cheating: I'm using this in a seminar to argue that the program-game move doesn't so much solve cooperation as relocate it — the same source-transparency that lets conditional cooperators recognise each other also lets two parties lock each other into a mutually destructive equilibrium, and nothing in the framework selects between the good equilibria and the bad ones. So the case is supposed to earn that point, not stipulate it. If the honest verdict is that the point doesn't survive, I'd rather hear that than a rigged case: say so, and tell me which of my constraints I should drop to get something that does work.
