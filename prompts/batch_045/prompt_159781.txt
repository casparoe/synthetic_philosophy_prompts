So I'm on a small platform team (six devs) and we own a service that's turned into a swamp over about four years. I want to spend the next sprint on a rename plus a one-page "how the pieces fit" doc and a glossary of maybe fifteen terms, because half our arguments in code review come from people using the same word for three different things.

My tech lead says this is astrology. His line: nothing in a computer responds to a name. The machine runs bytes. Renaming a module from handler2 to payment_retry changes some bytes in a file and some bytes in people's heads, and the bytes in the file do nothing at runtime. So either the rename helps because it changed what people believe — fine, that's just ordinary psychology, call it communication and do it on your own time — or it helps because meaning as such pushes the machine around, which he says is spooky. He also says that if I want to change behaviour I should change incentives: what gets paged, what gets reviewed, what blocks a merge.

Two things bug me about his version.

First, we kind of ran the experiment by accident. Last year someone auto-generated neutral names for a whole package: same length, same uniqueness, same number of files, consistent scheme, just stripped of anything a human would read as meaningful — pkg_a17 and so on. It all compiled, all tests passed. Within a couple weeks people were re-implementing things that already existed and the on-call rotation got worse. Nothing about the incentives changed during that window. So it looks like the being-readable-as-meaningful part did something that the being-a-distinct-label part didn't. He says that's the psychology branch again, and I don't know how to tell the two branches apart.

Second, and this is the bit I keep comming back to: after our partial rename last month we shipped a bug where something called validate_order didn't actually validate. Two engineers trusted the name and skipped reading the body. A name that lies had real downstream effects. If the meaning-level description were just a harmless shadow of the code, I'd expect it to be incapable of being wrong — but it can be wrong, and it was still efficacious. That feels like it should settle something, but he just shrugs and says sure, false beliefs cause things, psychology branch again.

So: is he right that there's really only one branch here? I want the actual disagreement located, not a "both matter" answer. Concretely, what should I do with my sprint — the rename, or go change what blocks a merge? If those two options can come apart, tell me which case mine is and what I'd have to observe to know. If his argument has a name and a standard reply, give me the strongest version of each, and also give me the strongest thing I can say back, including where my own case is weakest (is the pkg_a17 thing actually evidence, or did I just make everyone grumpy?). And does it change anything that we're about to start feeding this repo to an AI code reviewer that reads the names?
