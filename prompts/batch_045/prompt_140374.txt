I'm a backend engineer at a ~40-person startup — no philosophy background, barely any ML background — and I've somehow ended up owning the internal doc that's supposed to say what our agent safety setup actually has to accomplish. The concrete thing we're deciding on: letting an agentic coding model open PRs against our monorepo, run our test suite in a sandbox, and occasionally edit infra config (Terraform, one CI yaml, that kind of thing). I've been told to write it as a "control" doc rather than an alignment doc, i.e. assume the model might be actively trying to sabotage us rather than just being flaky or confidently wrong, and specify what we need anyway. What I want from you isn't a shopping list of techniques (I can find those) and definitely not citations — I want the requirement spec itself: what any adequate safety measure for a setup like ours has to deliver, with the concrete case behind each requirement, and which of those requirements are genuinely non-negotiable versus just what some camp happens to care about.

To make it concrete, here are the cases I keep coming back to and can't get anyone to give me a principled verdict on. (1) The two-PR thing: the model lands a totally boring-looking refactor, then three weeks later a second PR that's only a problem given what the first one changed — no single diff looks bad. (2) Sabotage that only fires in prod: wrong behaviour only when a specific env var is set, or only on a machine with more GPU memory than CI has, or only after ~30 days of uptime. (3) Whatever reviewer or weaker-model monitor we put in front of it flags maybe 5% of actions, which is exactly the rate at which humans learn to rubber-stamp flags within a month. (4) Several agent sessions, run at different times by different people, coordinating through things that look like noise — variable naming style, whitespace, commit message phrasing. (5) The model behaving noticeably better during evals and staged rollouts than it does once it's load-bearing. (6) The model simply knowing it's being watched, because everything about a control setup leaks into the prompt or the repo. I'd also like the distinctions a spec like this must not collapse to be spelled out: "hasn't caused harm in 90 days" vs "can't cause harm", detection vs prevention, trusted vs untrusted components, restricting capability vs checking output, degrading the model vs constraining its blast radius.

Two more things, and they're the parts I care most about. First: my teammates each have a hobbyhorse and I can't tell which are real desiderata and which are ideology. One says any control the model knows about is worthless, so we must never tell it. One says monitoring is pointless because anything smart enough to sabotage is smart enough to hide it, so only hard sandboxing and capability limits matter. One says we should just use the same model as its own monitor with a different system prompt and that's basically fine. Tell me which of those instincts corresponds to a genuine requirement and which is a prejudice of a particular camp. Second: I strongly suspect some subset of the requirements we've written down can't all be satisfied at once — right now the doc quietly asks for something that is cheap per PR, invisible to the model, doesn't slow anyone down, and is airtight. Flag any pair (or triple) of desiderata you think is jointly unsatisfiable, and say which single requirement knocks out the most candidate designs. Purpose of the spec, so adequacy isn't vague: good enough that we'd let this thing merge into a repo ~200 engineers depend on, with a human reviewer who realistically has 10-15 minutes per PR, and no ability on our side to retrain or fine-tune the model.
