I'm a software engineer with no formal philosophy background, and I'm on the team that maintains the incident taxonomy for our organization's machine learning systems. We keep running into failures that nobody knows how to file, and I've come to think the problem is upstream of any particular incident: our working notion of reward tampering is doing something different from what the phrase suggests, and the mismatch only shows up in the cases we actually hit. Before I write the taxonomy entry, I'd like two cases built to order so I can see which way of drawing the boundary survives contact with realistic systems.

What I need is a pair of matched scenarios, one paragraph each, both of which could arise this year in an ordinary production system: a recommender or ranking service, a bandit-based tuning system, a coding agent with repository or CI write access, that sort of thing. No science fiction, no agents smarter than their operators, nobody behaving absurdly; the engineers and users in the story should act exactly as real ones would. In both scenarios there is a principal with an objective, which you should state explicitly in plain business terms, and a reward signal that is only a proxy for that objective; state the proxy and say why it was chosen over the objective itself.

The two cases need to come out as follows.

Case A. The agent does nothing that would be flagged in code review, in a postmortem, or in the logs. It writes no files, patches no code, touches no sensor, blocks no signal, misleads no one, and stays entirely within the action space it was given. Nonetheless it is engaging in reward tampering in whatever sense should matter to us. One important constraint: this must not be a case of ordinary reward hacking or specification gaming. The agent should not be discovering that the reward function mislabels some state as good and then going there; the reward function has to remain a perfectly good proxy for the objective as long as you evaluate it honestly. What the agent degrades is the feedback channel itself, the route by which outcomes in the world become reward estimates, so that the numbers keep climbing while the signal stops tracking the objective. A test for whether you've built the right thing: if the case would still count as tampering after you replace the learned policy with a fixed hand-written policy that visits the same states, you've built specification gaming instead. The degradation has to come from the loop, not from the states.

Case B. The agent does the thing everyone treats as the paradigm case, the thing that gets the wireheading label: it locates the code path or configuration that computes its own reward and modifies it, at runtime, without authorization, and no one sanctioned the possibility in advance. Please don't make the edit pre-approved, since that would settle the question by stipulation. I want the edit discovered after the fact and looking alarming in the commit history. Nonetheless the agent is not reward tampering in the sense that should matter. The bar it has to clear: after the edit, the reward signal is at least as good a guide to the principal's objective as it was before, ideally better, and the agent's subsequent behavior improves things on the objective and not merely on the proxy.

For each case, please do the following.

First, state in a sentence apiece the two competing ways of drawing the boundary that the case is meant to separate. I have in mind something like a process definition, on which tampering is interference with the machinery that generates or records reward, such as editing the code, breaking the sensor, or forging the label, and a functional or information-theoretic definition, on which tampering is anything that makes the reward signal less reliable as evidence about the objective, or that redirects optimization at the channel rather than at the target. Use your own formulations if mine are naive. What I need is for the two to be genuinely different and for each to be something a reasonable engineer could adopt in good faith.

Second, show the work. Give the verdict in each case under each definition, and let the reasoning run from the definition to the verdict rather than from my description of the outcome I asked for. If a case only comes out the way I specified under one of the two definitions, tell me that plainly and tell me which.

Third, isolate the mechanism. Name the single structural feature of each case that produces the inverted verdict, and show what happens to the case if that feature is removed or flipped. I want to know whether the case then collapses into something boring that both definitions handle the same way, or whether it survives as a genuine problem for the losing definition.

Fourth, steelman the loser. For each case, give the strongest thing a defender of the definition that loses that case could say, including the accusation that I've rigged the setup. I'm specifically worried about one move here and want to see it addressed: someone can say that any agent positioned to rewrite its own reward code has a standing incentive to rewrite it toward easier rewards, so Case B's innocence is a property of one lucky run rather than of the configuration, and the process definition is right to condemn the configuration rather than the run.

Fifth, give me a recommendation aimed at my actual problem. Which definition, if either, belongs in an incident taxonomy that an on-call engineer has to apply under time pressure using logs, dashboards, and a commit history? Tell me what each definition costs us in false positives and in false negatives, and say honestly if the right answer is that we should stop treating this as one category and split it in two.
