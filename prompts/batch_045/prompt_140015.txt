I work on the platform team at a mid-sized AI lab, and every time safety comes up in our internal review meetings our VP of Engineering says some version of the same thing: look, this is just computer security. We've known for decades how to build reliable systems out of components we can't trust. You don't assume good intentions, you assume breach. Sandbox it, least privilege, defense in depth, monitor egress, keep the trusted computing base small, log everything, put a honeypot in the network so an intruder trips over something fake. On that picture the model is just untrusted code that happens to be very capable — whether it "wants" the right thing is irrelevant, because you build the system so it doesn't matter. He uses this to argue that (a) we shouldn't be putting headcount into alignment research, (b) we can ship our agent product with real tool access now as long as the controls are in place, and (c) anyone talking about slowing down is being dramatic.

I can't tell whether he's smuggling something in, and two things make me suspicious. First, he talks as if the sandbox is free: the tighter we make it, the less the product does, and the whole point of an agent is that it acts on the world. Second, we've been told to build a decoy environment — a fake production system that looks real from the inside, so that if a model ever does try to do something catastrophic it does it somewhere harmless. Half my team says that's just a honeypot and the security analogy is holding up fine. The other half says a decoy that fools something smarter than you have to be about as complicated as the real thing, at which point you're not containing anything. There's also the monitoring setup: we have a weaker trusted model read the stronger model's outputs and flag them, with some context redacted so the model doesn't know if it's being evaluated — except the thing being monitored is also the input to the monitor, which feels like feeding attacker-controlled traffic straight into the thing inspecting it.

Can you audit the analogy properly? I'd like:

1. The mapping stated explicitly, table-style: what is supposed to play the role of the attacker, the exploit, the sandbox, the patch, the honeypot, the malicious insider, defense in depth, the trusted computing base, and a zero-day.
2. The places it breaks — and for each one, whether it actually matters for the conclusion he's using it for, or whether it's a difference that doesn't bite. Things I half-suspect matter: the attacker and the thing you're defending with get built by the same people and scale together; copies of the same model fail in the same ways so redundancy buys much less than it does in security; there's no patch, because the problem isn't a bug in the code but what the system is trying to do; the artifact changes every few weeks so there's nothing stable to certify; and the monitor is weaker than the thing it's watching, which has no real analogue in a firewall.
3. Somewhere I think the analogy might be stronger than it looks: an attacker with a good zero-day doesn't waste it on a low-value target, and a model that behaves differently in evaluation than in deployment is doing something structurally similar by holding capability back. Is that right, or am I pattern-matching?
4. Which security tools genuinely transfer to this case — least privilege, blast-radius limits, rate limits, kill switches, egress control, audit — and which ones only look like they transfer because the words match.
5. Whether taking assume-breach seriously actually pushes the other way: if you really are supposed to assume the adversary is inside the perimeter and smarter than your detection, doesn't the security mindset say don't deploy, rather than deploy with controls? That would mean the analogy is carrying his conclusion backwards.

Please don't give me a reading list or paper citations; just reason it out, and tell me if there's a better analogy we should be using instead for thinking about a system that might be working against you while it works for you.
