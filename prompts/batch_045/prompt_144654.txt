hey — I'm a 4th year philosophy PhD student, working on agency attributions to AI systems, and I'm trying to write the one-page "where I actually stand" section that goes at the front of my framing chapter. My supervisor says I need to commit to something before I write the rest, which is fair. Before I hand it in I want to know whether the bits fit together, because I have a feeling two of them are quietly doing the same job in incompatible ways and I cant see which. Here's the list roughly as I've got it written:

(1) The distinction that's doing real work for AI safety is tool vs agent. The thing to avoid is building agents; capability on its own isn't the risk. So the target is a very capable system that answers questions, makes predictions, writes code on request — an oracle-ish thing — and we should treat building an agent as the failure mode, not building something smart.

(2) But I don't think tool vs agent is a difference in the innards. It's stance-relative, interest-relative: the same trained system, same weights, can be a tool in one deployment and an agent in another, and there isn't some intrinsic scalar "amount of agency" sitting there to be measured. What makes it an agent is partly what we're doing with it and how we're talking about it.

(3) Which is why I've been using what I call the orphan test: a system is an agent just to the extent that it would keep working toward the same end after the person who gave it that end stops watching, stops giving feedback, and can't be reached any more. I like this because it's behavioural and it doesn't care what's inside.

(4) I also want to regulate on properties of the system rather than on how people happen to deploy it or describe it. A rule like: anything that forms ends of its own that survive a context switch, or survive losing its principal, belongs in a seperate regulatory bucket regardless of whether anyone is currently calling it a tool.

(5) And I think the reason agency is dangerous is the instrumental reasons point: give a system pretty much any final goal and it has reason to secure resources, keep itself running, and resist being corrected or switched off. So the danger tracks how much grip the system has on the world, not what it happens to want.

(6) Meanwhile I want to say that a system can do open-ended multi-step work — hours long, calling other tools, writing and running its own code — without being an agent at all, because the objective is handed to it fresh each time it's invoked and it has no stake in which objective it gets.

(7) Last one, and this one matters to me: I think the tool/agent line is moral, not just prudential. If something is a tool, what it does is attributable to whoever is using it, and there's no seperate question about whether the system itself did something wrong. Also I'm happy to keep saying things like "it decided to retry" or "it wants the file to parse" about systems I've classified as tools, when that's the most useful way to talk.

So: which of these are actually in tension, which only look like it, and what's the cheapest thing to give up? Please rank the tensions rather than flagging everything as equally bad, and for each real one say which commitment has to move and what it costs me — and if a pair is genuinely fine, tell me why it's fine, I'd rather know that than get seven tensions back. Say if you think one single revision would clean up most of it. And push back plainly if the problem isn't a conflict between claims at all but that I'm using "agent" in two different senses; where you're reading me charitably versus just guessing what I meant, say which.
