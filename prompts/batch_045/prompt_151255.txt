The team you work on logs every deploy. Over the last two years:

- All deploys by the team: 400 deploys, 24 caused an incident
- Deploys touching the payments service: 60 deploys, 9 caused an incident
- Deploys made on a Friday: 80 deploys, 8 caused an incident
- Deploys touching payments AND made on a Friday: 25 deploys, 6 caused an incident
- ... AND made after 6pm: 8 deploys, 4 caused an incident
- ... AND where the person deploying was Priya: 3 deploys, 2 caused an incident

Tomorrow Priya is deploying a change to payments at 7pm on a Friday. You want a figure for how likely it is to cause an incident. To get one you have to put tomorrow's deploy in some class of similar events and use the rate in that class, and tomorrow's deploy belongs to all of the classes above at once, which give very different rates.

In the lecture your lecturer offered the following rule, which she called the stability rule: take the widest class whose rate does not shift by more than 5 percentage points when you narrow it by any one further recorded property, counting only those refinements that still contain at least 20 data points; if a class has no eligible refinements left, count it as stable. Use the rate in the class you end up with.

(a) State the reference class problem and explain why it makes the figure above hard to come by. (6 marks)
(b) Apply the stability rule to the table and report the figure it gives for tomorrow's deploy, showing your working. (7 marks)
(c) Explain whether the stability rule escapes the arbitrariness it was meant to answer, and how it compares with the older rule of thumb, use the narrowest class for which you still have enough data, taking enough here to mean at least 20 data points. (7 marks)

The student's answer is below.

Part (a)
The reference class problem is the problem of which class of events to count a single case as part of, when you want to say how probable it is. Any one event belongs to a great many different classes at the same time, and those classes have different rates, so you get a different answer depending on which class you pick. Tomorrow's deploy is at once a deploy by this team (6% caused an incident), a payments deploy (15%), a Friday payments deploy (24%), a late Friday payments deploy (50%), and a late Friday payments deploy by Priya (2 out of 3). Nothing in the frequency data itself tells you which of those is the right class to use, and because the class you choose determines the figure you get, you can produce more or less any number you like by choosing the class to suit yourself. That is the problem: the choice of class looks arbitrary and is not settled by the data.

Part (b)
The stability rule is meant to take the choice out of it. Instead of going as narrow as possible, you go as wide as you can get away with: the widest class whose rate doesn't move by more than 5 points when you narrow it by one more property, ignoring refinements that leave you with fewer than 20 data points. Running it: the widest class, all 400 deploys, gives 24/400 = 6%. Narrowing it to payments gives 9/60 = 15%, a 9 point jump, so all deploys is not stable. The payments class itself is 15%; narrowing it by Friday gives 6 out of 25, which is 20%, so that is a 5 point move, exactly on the tolerance, and I'll count payments as stable. So the rule gives 15% for tomorrow's deploy.

Part (c)
Does it escape the arbitrariness? I think it does, or at any rate the practical version of it. The two thresholds (5 points, 20 data points) are to some extent arbitrary and you could argue about them, and the rule can only test refinements that somebody thought to record in the first place — if the team had never logged the day of the week, Friday could not have come into it at all, so the output depends on what data you happen to have. But whether a class is stable is a plain statistical fact about the numbers, not a judgement call, so unlike simply picking a class by hand the rule does not beg the question; it finds the rate that is really there rather than the one you were hoping for. So the probability that tomorrow's deploy causes an incident is 15%, and that is the deploy's actual chance of going wrong, not merely what we should expect given what we know. It also shows that the stability rule is a genuinely different rule from the old narrowest-class rule, since that one would tell you to use the narrowest class with enough data, which here is Friday payments at 24%, while the stability rule says 15%.
