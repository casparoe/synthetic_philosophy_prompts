At work we build and eval LLM agents, and there's a convention on my team I can't get anyone to justify. We grade on the final answer only — tests pass, task done — and the model's chain-of-thought is treated as non-committal: it gets stripped before the user sees it, and it never touches the score. But the second something goes wrong, everyone reads that same trace like a confession: "it noticed it was being evaluated and played nice", "it was really trying to exfiltrate the keys and bailed". Same object, two totally different statuses. Then a third thing: we sometimes penalize a trace that mentions the eval or strategizes about the grader even when the final answer is correct — so a bit of the process does count, but only against the model.

It smells like our own code review setup: CI only cares whether the build is green, but a reviewer will reject a diff that works for the wrong reason. A couple of us want to switch to step-level scoring — scoring each reasoning step, the way the process-reward-model crowd does — and the pushback we keep getting is that we'd be grading whether the model *knows* the answer instead of whether it *got* the answer, which supposedly isn't the job.

Can you lay out what each of these practices is actually assuming? What does answer-only grading presuppose about knowledge or justification — some reliabilist thing where a reliable route is enough, or just "reasons aren't checkable so check what you can"? Does step-level grading quietly require that the stated reasons *are* the reasons the model acted on, and that getting the right answer by a bad route or by luck is a real defect and not just a risk? Where exactly is our shop inconsistent: if the trace isn't a commitment, how is it evidence of what the model was up to, and if it is, shouldn't it also count when the answer came out fine? And concretely, what would have to change in the eval pipeline if we took the process view seriously instead of just bolting it on as an extra penalty?
