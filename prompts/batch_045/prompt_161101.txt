I have a question about a configuration I keep running into, and I would rather get the carving right than be handed a label, so I will ask it at some length.

About me: I am a software engineer, fifteen years, mostly build systems and developer tooling. CS degree, one undergraduate logic course, no philosophy beyond that. I want to know whether what I am about to describe has an established name and an established literature, and — more importantly — whether whatever name exists actually covers my case or only a neighbour of it.

Three cases from work.

1. A self-hosting compiler. The compiler for language L is written in L, so building it requires an already-built compiler for L; the repository therefore contains a checked-in binary that everyone treats as the bottom of the story. When a new hire asked how we know that binary is a faithful translation of the source, the honest answer was not a derivation but a provenance chain ending in trust. We tried to close the gap: rebuild the compiler with itself until the output stops changing, build it with an independent implementation and compare. This did not remove the thing we were standing on; it relocated it onto the comparison procedure, the second implementation, and the hardware. And there is a sharper version of the worry that I cannot get rid of: the tool you would use to audit the rebuilt toolchain is itself an output of the rebuild, so no test run inside the loop can distinguish a faithful toolchain from one that lies consistently about itself.

2. A schema language used to describe our API schemas, itself described by a schema that validates itself. A defect in the meta-schema is invisible to validation, because the instrument and the object under the instrument are the same file. The same shape shows up with a linter whose own configuration is linted by the linter, and with a code-review bot whose rules live, as ordinary files, in the repository the bot reviews.

3. Reflection: a language where a program can construct and run a representation of a program, so that the thing doing the describing and the thing described are the same data structure; and type systems in which the collection of all types is itself a type, which is known to make the system collapse rather than tower.

What interests me is not the loop. The loop is well known and has an obvious name in my field; books get written about it. What interests me is the following, which I have no word for.

(a) The outside of the loop is not a tier of it. Whenever people diagram one of these cases they either add a box on top — call it the meta-level, or the spec, or the model — which simply restarts the problem one level up, or they declare the whole arrangement viciously circular and stop talking. Neither matches what I see. The thing that stops the regress is not a further box. It is the background: the silicon, the person who wrote version 0.1, the fact that the meta-schema is interpreted by code that no schema checks, the fact that the diagram of the loop is drawn in a notation the loop does not contain. It is off the canvas rather than above the canvas.

(b) That background is convertible but not eliminable. You can always pull it into the picture — write the meta-meta-schema, produce the independent second implementation, formalise the provenance chain — and the moment you do, a fresh background appears behind it. So the un-tangled thing behaves less like a fixed rung than like a horizon that recedes at the rate you approach it.

A colleague showed me the Escher print of two hands drawing each other and said this is the same phenomenon. I take the point about the two hands, but my question concerns the pair of hands that is not in the picture, and whether, if you drew that pair, you would need another one.

What I would like:

1. Does this have a name and a literature? Terms I already have — self-reference, bootstrapping, meta-level, reflection — name the loop or the machinery, not the off-canvas background, and none of them say anything about its receding behaviour. I have also seen it claimed that in any such arrangement there is necessarily some level that cannot itself be tangled; I have no source for that and no idea whether it is a theorem, a stipulation, or folklore, and I would like to know which.

2. If the nearest established notions are things like a loop that crosses levels, a hierarchy whose levels come back to where they started, and a structure with no permanently top or bottom element, I want the carving rather than the name: what each of those covers, exactly where my case comes apart from each, and which fits best. In particular, settle this for me if you can: is the outside-of-the-loop supposed to be structurally outside — forced by how the system is put together — or only pragmatically outside, a matter of what we happen not to be able to question this quarter? And is the receding behaviour I described a consequence of anything, or merely an observation about how careless engineers work?

3. If nothing established fits, coin a term and give it a definition a working programmer could apply to a new case, plus the boundary cases: the minimum a system has to do to count, and the cases that resemble it but should be excluded. Two I would like ruled on specifically: ordinary mutual recursion that provably terminates, which looks like a loop but seems to me well founded and therefore different; and the phasing discipline in macro systems, where macro expansion happens in numbered stages and each stage can only use macros from strictly earlier ones, which looks to me like either a genuine tower or a very good disguise.

Please argue the distinctions directly rather than pointing me at a literature — I cannot chase down references, and a list of things to read would be useless to me. Six hundred to nine hundred words is fine.
