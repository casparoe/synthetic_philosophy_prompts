I'm in a small reading group that has been working through the setup where two players in a one-shot prisoner's dilemma each submit a program, each program is run with the other's source code as input (and can refer to its own), and each outputs cooperate or defect. I'm trying to decide what program I would actually be willing to submit, and I've found that my gut verdicts on cases don't line up with any principle I can state. Assume payoffs T=5, R=3, P=1, S=0, so that mutual cooperation beats taking turns, and note that T+P equals 2R exactly, which turns out to matter below. I'd like you to extract the principle behind my verdicts, tell me which of them it forces me to drop, and apply it to two cases I haven't considered.

My verdicts. (a) Both players submit the program that cooperates just in case the opponent's source is byte-for-byte identical to its own; both cooperate, and I gather this is a genuine program equilibrium. Verdict: that is the real thing, and I would submit it. (b) Same, except one copy has a variable renamed and some extra whitespace: both defect. Verdict: a fiasco, and it makes me retroactively suspicious of (a) — whatever was achieved there looks like an artifact of syntactic coincidence rather than cooperation — though I can't say what the program should have done instead. (c) Both submit a program that cooperates just in case there is a proof, in some fixed sound system such as Peano arithmetic, that the opponent cooperates with it; against its own twin this cooperates, by Löb's theorem. Verdict: better, this looks like cooperation and not coincidence. (d) The same kind of proof-based program, paired with a program implementing the same policy but searching for proofs in a different formal system. I have a vague memory that the handshake can break down here and the pair can mutually defect; I may be misremembering. Verdict: if that is right, I want to call it a failure like (b), but I suspect it is a limit rather than a bug, so my verdict is genuinely unsettled. (e) A variant I find distasteful: each program, with some small probability, cooperates outright instead of trying to simulate or prove anything about the other, which short-circuits the infinite regress that a naive simulator falls into. It secures mutual cooperation and, for small enough probability, no profitable deviation. Verdict: a hack rather than a solution — but I can't articulate what is wrong with it. (f) Unconditional cooperator against unconditional defector: obviously never submit the first. (g) A prudent program, which cooperates only when it can prove the opponent would cooperate with it and deliberately withholds cooperation from programs that would be suckered by an unconditional defector, played against an unconditional cooperator: it defects and collects 5. Verdict: fine, arguably admirable; suckers aren't owed anything and leaving the temptation payoff on the table is sentimentality. (h) The same prudent program against a program that cooperates only with programs that do not exploit unconditional cooperators: both defect, 1 apiece. Verdict: here I feel bullied and I want to blame the other program, but it is just another conditional cooperator, and I don't know what makes its condition illegitimate while the reciprocity in (c) is legitimate. Note that across (g) and (h) the prudent program gets 5+1=6, while the plain proof-based program of (c), which cooperates with anyone it can prove reciprocates, gets 3+3=6 — a dead heat, which is part of why I'm stuck. (i) A proof-based program whose proof system is unsound, so that it proves that an unconditional defector cooperates with it and cooperates, scoring 0. Verdict: worthless; cooperation bought with a false proof doesn't count as cooperation. (j) Two programs that try to split the surplus by comparing hashes of their sources, the smaller hash cooperating and the larger defecting. Verdict: a gimmick, not cooperation, and I'm told it isn't even an equilibrium — that no program equilibrium can push anyone below their minimax payoff of 1.

My tentative principle is: cooperate with an opponent if and only if you can prove, in a sound system, that it cooperates with you. It handles (c), (f) and (i) neatly, it tells me to cooperate with the sucker in (g) which contradicts my verdict there, and it seems to have nothing to say about (b), (d), (e) or (j).

Please do three things. First, state the best principle you can — or two or three candidates, if they genuinely diverge — precisely enough that each clause can be traced to the case that motivates it. Second, say which of my verdicts it cannot accommodate and what it would have me say instead. Third, give its verdicts on two cases I haven't listed: (α) an opponent that is provably behaviourally identical to my own program except that it also cooperates with unconditional defectors — a slightly more trusting twin, which will cooperate with me either way — where exploiting it nets me 5; and (β) a friend's claim, which I can't evaluate, that the folk theorem for these games means there are equilibria in which the two players get unequal payoffs, say 2 for me and something like 3.5 for the other, both above minimax, enforced by mutual threats. If such an arrangement exists and the alternative is mutual defection at 1 apiece, should a well-designed program accept the unequal deal, and if so how does that differ in principle from the hash-splitting gimmick in (j)?
