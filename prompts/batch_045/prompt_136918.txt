Our team does mechanistic anomaly detection on models we didn't train, and we've fallen into a shorthand that I think is doing more work than it should: a mechanism is to a model as software is to hardware. The mechanism is the thing being computed, the model is just the substrate it happens to run on, so the same mechanism can turn up in two models trained independently by different people on different data — and if it does, the anomalies we catalogued on one should count as anomalies on the other. We've been leaning on this to carry a safety case across: same mechanism, same failure modes, thresholds transfer.

Concretely. We audited Vellum-7B thoroughly. Then there's Vellum-7B-Instruct, an in-house instruct tune off that same base, and Marlowe-3B, which a partner lab trained from scratch on a broadly similar mix. Our detector — internally we call it a "path-signature match": run a bank of about forty fixed interventions (ablate this attention head, patch that residual direction, rescale this MLP block, that sort of thing), record the causal effect on the behaviour we care about, compare profiles — says Instruct is running the same mechanism as Vellum and Marlowe is an anomaly. We also require what we call port-stability: the candidate mechanism has to survive being patched into the other model and still do its job.

Two wrinkles I don't think the software picture handles. First, Instruct's signature only matches in the top quintile of prompt lengths; below that it does something else entirely, and our intervention bank never sees it because all forty probes were calibrated on long prompts. Second, Marlowe produces the same outputs with a scrambled intervention profile, and we genuinely can't tell whether that's a different mechanism doing the same job or the same mechanism that our forty probes simply don't reach. Wether either case counts as "the same mechanism" is exactly the call our safety case rides on.

I'd like an audit of the analogy rather than a view on our models. What maps onto what, in a table if that's easiest — is the base model the hardware, the fine-tune a patch, the training run the compiler, the intervention bank the test suite? Where does the mapping break? I've got my own list I want checked and extended, but the one I keep coming back to is that hardware is designed before and independently of what runs on it, whereas the "hardware" here was shaped by the "software" during training, so you can't hold one fixed while you swap the other. Also: which features of software does the analogy quietly import that a trained net definately doesn't have — a spec written down somewhere, stable interfaces, compilation that preserves semantics by construction, a clean line between a bug and the machine it runs on, someone you can ask what the programme was supposed to do? And which of those imports actually matter for the conclusion we want, as opposed to being harmless decoration?

Then the part I care most about: does "same mechanism, so the safety case transfers" survive once the disanalogies are on the table, or was the analogy carrying the whole thing? If it doesn't survive, is there anything in the neighbourhood that would carry it — we need the mechanism to be the same in a sense that licences transferring thresholds, and I want to know what that sense would have to be, even if it turns out not to be one we can currently measure? And is there a better analogy? Someone here suggested a metabolic pathway (no spec, kept running by the surrounding cell, recruitable for new jobs, sometimes vestigial) and someone else suggested a dialect (no author, no version number, mutual intelligibility a matter of degree and different in different directions). Which of those, if either, fits better, and what would each of them make us say about the Instruct and the Marlowe cases?
