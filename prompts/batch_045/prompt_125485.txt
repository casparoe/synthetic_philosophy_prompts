I write and debug production software for a living and have no formal philosophy training. I got pulled into an argument on a mailing list that I can't close out, and I'd like a diagnosis of it rather than a reading list.

Here is the argument, as I now have it written down. It concerns program states running on real hardware, but I'm told it is a well-known argument in another field, wearing a different costume.

(1) Completeness of the base level. Take any event in a machine — a packet leaving a network card, a row committed to disk, a robot arm moving. Given the complete microphysical state of the machine at t and the laws of physics, the physical state at every later time is fixed. Nothing beyond the physical state at t gets a vote.

(2) Realization without identity. The states I actually reason about — the buffer is full, the retry counter has reached three, the process is deadlocked — are realized by microphysical states but are not the same thing as them. The same source-level state can be realized by wildly different hardware: a service compiled for one instruction set and for another, or running under an emulator inside a virtual machine inside someone else's data center. And no microphysical description of the machine, on its own, tells you which program state is present.

(3) No systematic overdetermination. When an event has a sufficient physical cause, it does not also have a second, independent, sufficient cause — except in freak coincidences, the kind where two causes are genuinely unconnected and the event would have happened anyway. Effects are not, as a general rule, doubly caused. If they were, the independence would show up somewhere as slack in the correlation, and it doesn't.

(4) Therefore, for any event E that a program state S appears to bring about, where S is realized by microphysical state P: P suffices for E by (1), S is distinct from P by (2), and E is not doubly caused by (3). So S is not a cause of E. Program states are causally inert. The code doesn't do anything; the electrons do.

(5) That conclusion is unacceptable to anyone who debugs for a living. Change one line and the output changes; leave it and it doesn't. The postmortem cites the buggy comparison, not the voltages. The on-call engineer fixes the world by shipping a config change. The same source compiled to a different architecture reproduces the behavior. Whatever "cause" means in ordinary engineering practice, code is the paradigm case of it.

(6) And the argument doesn't stop at software. Run it one level up and the emulator's states are epiphenomenal relative to the host machine's; run it sideways and every cause the special sciences cite — a gene, a price, an algorithm, a protocol, a contract — is drained of causal power while every explanation that mentions it keeps working exactly as before. A machine that retires every cause except the fundamental physical one isn't telling me something about software. It is a device for manufacturing epiphenomenalism about everything above the floor.

So: which step do I reject, and what does rejecting it cost? If I have to choose, I would rather keep (1) — that the hardware story is physically complete — than keep my professional self-conception; but I would also like to keep the claim that the postmortem identifies a real cause, and I want to know what I am paying for each of those.

Two things I want you to take up beyond the diagnosis.

First, the fix I keep circling back to, which I'll call the specification condition: a realized state is a genuine cause only if something outside the physics — a source file, an interface contract, a standard — settles which physical states count as realizing it and what it is supposed to do, so that counterfactuals of the form "had this state been different in the way the specification says, the outcome would have differed" are well defined and checkable against the hardware. That seems to rescue software. It also seems to fail for beliefs and desires, because nobody wrote those down. Is that the right shape for a fix, or is it a category mistake dressed as a criterion?

Second, the case that any fix has to give a determinate answer about: a compiler deletes a variable as dead code. The emitted machine instructions never mention it, and the observable behavior of the program is unchanged. Was the source-level variable ever a cause of the output, or did it never do anything? And alongside it: two implementations using different algorithms that agree on every input at the interface — same cause, or different causes? I don't need you to agree with whatever answer I'd give; I need a diagnosis that says something specific about these.

My colleague's real point, and the reason I care: this is said to be the same argument that is used to threaten mental causation, and he says whatever saves software saves beliefs and desires too — or, if it doesn't, that difference is the interesting result. So once you've settled the software case, tell me whether the fix transfers. Is there something about code — that it has an author, a specification, a compiled artifact, a public semantics, a correct behavior it can fail to match — that makes it a specially easy case, so that vindicating it tells us nothing about whether my decision to deploy on Friday afternoon caused the outage? Or is the analogy exact, and the software case just a better-lit picture of the same answer?

Tell me which premise you reject and why that premise looked innocent when it was stated. Price the alternatives you didn't pick — including the ones that force you to give up something I said I wanted to keep. I'd rather you commit to a verdict than tell me the answer depends on what "cause" means, though you should say which reading of "cause" your verdict is relative to.

Lead with your bottom line in the first sentence — which step fails — and then give the reasoning, with no preamble and no restating my argument back to me. Close by naming the single consideration that would most likely make you change your verdict, and where you think your own diagnosis is weakest.
