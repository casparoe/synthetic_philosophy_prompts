I'm an infrastructure engineer, and for the past year I've sat on the design-review rotation for the agent systems we deploy internally. I have no philosophy background; the vocabulary I have comes from our own internal wiki, which distinguishes "approval-directed" designs — the agent tries to do whatever the human overseer would approve of — from "goal-directed" ones, where the agent optimizes a stated objective. The checklist we work from doesn't actually say how to choose between them, so in practice the calls have been made by one senior reviewer (I'll call her D.), and her track record is the only thing I have to extrapolate from.

Six calls so far:

1. Approved. Step-level approval: at every step the agent samples five candidate actions, a human picks one, and the agent executes it. There is no internal objective beyond that, and nothing runs without a click.
2. Rejected. Outcome-reward RL: a reward model trained on human thumbs-up/thumbs-down over complete runs, then RL over eight-hour episodes with no human contact during an episode.
3. Approved with conditions. An approval predictor trained on the same kind of human approval data as in (1); the agent acts on predicted approval for up to fifteen minutes between human check-ins; every action is logged and the logs are audited weekly. Conditions were a hard kill switch, the fifteen-minute cap, and immutable logs.
4. Rejected. An explicitly goal-directed agent with a narrow, machine-checkable objective — hold the p99 latency of one internal service below a threshold with no error-rate regression, with each change verified by a checker before rollout — running for weeks with no human in the loop. D. rejected it even though by our usual standards the objective looked small and the checker was sound.
5. Approved. A multi-week project agent whose objective is to maximize the probability that a designated reviewer approves at each of three coarse milestones; at each milestone the reviewer inspects the actual artifact the agent produced, not a report about it.
6. Rejected. The same setup as (5) except that the reviewer only ever reads a changelog that a separate summarizer model writes from the agent's own action logs, and approval is collected on the changelog. The reviewer is permitted to go read the underlying diff, but in practice doesn't.

I genuinely cannot tell what is doing the work across these. Three candidate stories fit them all as far as I can see: the approval-versus-goal distinction; the length of the stretch the agent spends optimizing with no real check; or something about who controls what the reviewer ends up seeing. Those give different answers for the case now in front of me.

The new case: a multi-week agent that performs a large refactor plus a data migration across one of our older services. Its objective is a frozen approval predictor — trained only on single-step approvals, the same data behind (1) and (3), and never updated during the run. At the end of the run it produces a diff, and a separate translator model renders its action log into a human-readable changelog. The reviewer reads the changelog, runs a short fixed smoke test that the agent did not author, and may inspect the full diff and logs if they choose. The agent itself decides which unit tests to add and which log lines to emit; it cannot modify the review tooling, and it has no contact with the reviewer during the run.

What I'd like from you: which rules are consistent with all six prior verdicts, stated precisely enough that I could apply them myself; what each predicts about this case; which precedent is the closest analog; your best guess at D.'s call with the reasons for preferring it; an honest statement of what principle we would be committing ourselves to under each of the viable decisions if the precedents really do underdetermine it; and, if I get one clean probe for next month's review, the minimal variant of this case that would best separate the surviving rules from each other.
