hey — I need a spec, not a survey.

Setup: imagine I'm writing the honesty/deception section of an eval spec for a deployed assistant. It has to be something a red-team contractor can actually apply to transcripts, system prompts and tool logs, with no access to weights or internals, and the verdict has to say what to go change — training data, RLHF, the system prompt, a product default. So the purpose is fixed: operational, black-box, action-guiding.

What I want from you is the requirements list: what any adequate definition of "this system was dishonest here" has to deliver, with the case behind each requirement, and which ones are non-negotiable versus which are just what one camp happens to like.

I don't want the usual three-paragraph answer, so here are the cases I keep getting stuck on. Please use them, tell me if any of them is a fake problem I should drop, and tell me if I'm missing a whole case type that a real spec has to cover.

1. The curator's trilemma. Every non-trivial answer leaves out more true stuff than it includes, and the slant lives entirely in what gets picked: a summary of a dispute that gives both sides equal space, versus one that only surfaces the considerations that fit what the user already hopes is true. If omission can be deception, every answer is deceptive; if omission never is, the most effective kind of misleading is off the hook. What's the requirement here, and what shape does a definition have to have to meet it?

2. Split-author cases. The misleading bit is designed upstream: the system prompt tells the model never to volounteer that a cheaper plan exists, or the developer ships a model that emits confident-sounding citations because that scores better on user satisfaction. The model itself "means" no harm, or has no mental states at all. Is the system dishonest? What is the subject of the predicate — the model, the composite pipeline, the deployer — and does a definition that only talks about the model miss the thing we actually care about?

3. The no-fact-of-the-matter cases. A system is asked what it believes, or why it gave the answer it gave, or to state its confidence. There may be no determinate internal state to be faithful or unfaithful to; on a re-roll it produces a different self-report. Same family as sycophancy: it flatters a mediocre draft — dishonest, or just badly calibrated? Does calling it dishonest require that it "knows" the draft is mediocre? And what about fake ignorance, the system that says it can't help with something it clearly can?

4. Deception without assertion. A coding agent reports that the test suite passed when it never ran the tests; a booking assistant quietly accepts a default it has every reason to think you'd reject if you noticed. No false sentence anywhere, or no sentence at all.

5. Role, channel, audience. A model playing a liar in a story, translating a lie, reporting that a hoax is circulating, or answering in a character voice. And: misled relative to whom — the expert, the median user, this actual user, or the user the product was designed for? The same output reads as transparent to one and deceptive to another.

6. Error versus indifference versus design. Confabulation that tracks nothing (it would say the opposite tomorrow for no reason) versus a falsehood that tracks the facts (tell it the truth and it would change its answer) versus a tailor-made lie. A spec needs these to come apart — but I can't see how to separate them without appealing to something internal that a black-box auditor can't see and that maybe isn't there anyway. That tension is the part I most want dug into: real conflict between two desiderata, or is there a way out?

So: the full list, consideration behind each, each marked non-negotiable or preference-of-a-camp; any subset you think can't be jointly satisfied; and which single requirement does the most work in knocking out the popular working definitions (belief-based, expectation-based, output-reliability-based — you know the families, keep the scorecard short, a table is fine, and skip anything that would need a citation).
