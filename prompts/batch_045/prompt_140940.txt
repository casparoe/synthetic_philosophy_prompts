I work on the serving and evaluation infrastructure behind a deployed LLM-based product, and the same disagreement keeps resurfacing in our design reviews, always in roughly these terms.

Half the room treats the system as an agent: it represents the state of a user's repository, takes actions that change that state, forms multi-step plans, and can be graded on whether it achieved what it set out to do. The other half calls this a category mistake. What we actually serve, on their view, is a simulator: a conditional distribution over continuations given a context, which can be induced to impersonate an agent much as a novel can contain a character who wants something. On that view the system no more wants the user's tests to pass than a novel wants its protagonist to succeed, and everything that looks like planning is something the character does inside the simulation, not something the system does.

Both framings have saved me from bad design decisions and both have led me into some. I suspect they break down in the same place, but I cannot locate that place, and that is what I would like help with.

Please construct one concrete, worked example that isolates the breakdown. I would like a single episode involving a tool-using assistant, described in enough detail that I could turn it into an eval case, built on top of these stipulations, which are the parts I think matter:

- Part of the character the system impersonates lives outside the weights: a persistent memory store is retrieved into the context each turn, so the role is jointly implemented by the model and by state the model does not contain.
- The role is not fixed at the start of the episode. It can drift partway through in response to what the tool results turn out to contain, and the drift can be towards either more or less agency.
- The mechanism that selects a role and the mechanism that enacts one are the same weights, shaped by the same post-training, so there may be no fact internal to the model about where selection ends and enactment begins.

The example needs to do three things. First, an agent-level description of the episode should predict one observable behavior and a simulator-level description should predict a different one. Second, the actual behavior should be a third thing that neither description anticipates, and that third thing should be what a third description of the system would have predicted — if you think the right third description is not the one sketched above, use yours. Third, the difference has to matter for a decision I would actually have to make: whether to treat the failure as misalignment or as role confusion, whether to fix it in the system prompt, the fine-tune, the retrieval policy, or the tool sandbox.

Two further things, please. Include the diagnostic: the smallest change to the episode that flips which of the three descriptions is the natural one, so that I can tell them apart rather than argue about them. And tell me at what grain the third description locates the agency, whether in the weights, the context window, the scaffold, or the deployment as a whole, since I suspect a lot of our arguments are really arguments about grain.

Finally, if my three stipulations describe nothing more than the simulator framing with extra machinery bolted on, say so directly and explain why. I would much rather find that out here than in a design review. Assume a generic instruction-tuned model; please do not build the example on any specific model's documented quirks, and do not assign the views to named authors or papers. I want the reasoning, not a reading list.
