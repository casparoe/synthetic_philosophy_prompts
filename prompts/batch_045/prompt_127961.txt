I build software, not arguments, and what I need is a specification rather than another paper to read.

The situation: my team maintains a long-running agent that rewrites its own planning module, and we keep running into the same wall. As I understand it, the wall is this. If the agent's reasoning is formalisable as a theory T of ordinary strength, then T cannot certify its own reliability: by Löb's theorem, if T proves the general claim "for any P, if I derive P then P", then T proves every P outright, i.e. it is inconsistent and worthless. Nor can it get what it needs piecemeal, because for a particular P, if T proves "if I derive P then P" then T already proves P — so the sentences whose soundness T can vouch for are exactly the ones it didn't need vouching for. Every design we try hits some version of this. The agent wants to install a successor whose behaviour depends on reasoning the agent has not yet done; it cannot certify that successor; and so it either refuses to act at all, or it acts on a trust it cannot justify. A third failure mode is worse: it installs a successor whose entire plan is to install a successor, and the agent spends its whole budget building better versions of itself and never merges a single patch.

Before I look at another proposal, I want the desiderata. What does any adequate account of self-trust for a self-modifying agent have to deliver — which cases it must get right, which distinctions it must respect (trust in a derivation versus trust in a component versus trust in a successor; an agent's believing it is reliable versus its being reliable), and which impossibility results it has to be consistent with — with the case or consideration behind each requirement, and an explicit verdict on which requirements are non-negotiable and which are the prejudices of one camp. Write it so that I could turn each requirement into an acceptance test in our CI: a requirement with no operational test is not a requirement.

Fix the purpose first, since adequacy is relative to it: this is for a sandboxed agent that improves a codebase, where the failure we care about is the agent bricking itself, drifting off the objective, or burning its compute budget on self-improvement theatre. Not existential stakes. State the purpose you are writing the spec for, and say which desiderata would tighten or change if the stakes were higher.

Here is my candidate list, with the case behind each. Tell me which are genuine desiderata, which are parochial preferences of one approach, and which are not desiderata at all.

D1. No self-certification. The account must not require the agent to prove its own soundness, even schematically. This looks less like a preference than like a constraint with a theorem behind it — but tell me if the prohibition is narrower than I think (for instance, whether it bites only on unlimited reflection, and whether there is room for a restricted form).

D2. Act anyway. Self-reference must not stall ordinary planning. Case: the agent declines to merge a three-line, tested, reviewed patch on the grounds that it cannot prove the post-patch agent is sound. I take this as non-negotiable, but I can imagine someone replying that the paralysis is the correct answer and the problem is my impatience.

D3. Trust beyond simulation. The account must let the agent accept a successor whose reasoning it cannot run in full — longer proofs, a larger budget, a genuinely stronger system. This is the whole point of self-improvement; if the parent must be able to execute everything the child does, nothing has been gained.

D4. No infinite deferral. The chain of rewrites must terminate in useful work, in whatever sense turns out to be the right one, and the agent must not be able to satisfy its objective by arranging to arrange to arrange. Case: the delegation cascade above.

D5. Property preservation with a warrant. Whatever we care about must survive the rewrite, and the agent needs some reason — not necessarily a proof — for thinking it does. The interesting question, which I want you to answer, is what counts as a warrant here once proof is off the table, and whether demanding a warrant at all just reintroduces D1 through the back door.

D6. Graded trust. Trust should come in degrees that track evidence, rather than being binary proof-or-nothing. Our current hack is a trust ledger: every rewrite carries a machine-checked certificate issued by a checker that is strictly weaker than the agent's own logic, and the ledger records who certified what with which budget. My worry is that this only pushes the bump in the carpet down one level, since we now have to trust the checker. Is "verify with a strictly weaker checker" a desideratum, or a dodge?

D7. No epistemic wishful thinking. A successor's own assurance that it is safe should count for roughly nothing; the agent must not be able to raise its confidence in itself by asserting its own reliability, or by building a successor selected for saying reassuring things. Case: the child agent that reports "all good" because its training rewarded reassurance. I suspect D7 and D3 are in direct tension, and I want to see the tension stated precisely rather than dissolved.

D8. Pessimistic tiling — this one is ours, not from anywhere. Require the agent to justify every modification under the assumption that the entire self-improvement cascade fails: the modification must be worth making even if every future rewrite it enables is worthless. Tell me whether this is a genuine desideratum or merely an expression of our risk appetite, and whether it is satisfiable at all given that the point of self-modification is downstream value.

D9. Bounded implementability. Any rule you propose has to run inside a finite proof budget; a principle that quantifies over all proofs is not a specification but a wish. I genuinely do not know whether this is a desideratum or an engineering prejudice that a philosopher is entitled to throw out — argue it both ways and then pick a side.
