I'm a backend engineer at a mid-sized software company, and I've somehow ended up on our internal launch-review board for anything involving machine learning. Every review lately stalls at the same place: someone says the proposed system is "just a tool," someone else says it's "basically an agent," and then both sides assert that their label settles which safeguards apply -- human-in-the-loop requirements, sandboxing, rate limits, the works. Nobody on the board has any philosophy background, and I've noticed we keep using "tool" and "agent" as vibes rather than criteria. I've seen enough of the online discussion of tool AI versus agent AI to know this is a real debate with real positions, but I don't trust our team to reconstruct it from memory, so I want to hand them a worksheet that does it for them.

Write me that worksheet: a decision tree that takes a reviewer from "here is the design doc for the system we want to ship" to a named position on where the system sits in the tool/agent landscape, and what the label should and shouldn't buy us. Build the tree from the logical space rather than from a list of positions: start from the properties that could distinguish systems, figure out which combinations of answers are possible, and then locate positions in that space. I'm imagining roughly eight to twelve branch nodes and six to eight leaves. Each branch node must be a question a reviewer can answer from the design doc without knowing which leaf it leads to -- so things like "does the system persist state or objectives across separate user requests, or is each invocation self-contained," "within a single invocation, does it search over multi-step plans before producing anything," "can its outputs affect the world without passing through a human who reads and approves them," "can it expand its own action space, e.g. by writing and then executing code, spawning subprocesses, or spending a budget," and whatever other splits you think the space actually contains. No node may use the words "tool," "agent," or "agentic."

Two leaves I specifically want included, because they capture distinctions my board keeps fumbling: first, a leaf for systems that do heavy internal search and planning but only inside one bounded episode with no carryover -- the sense in which a chess engine deep in a game is doing something agent-flavored while remaining inert between games; second, a leaf for the position that "tool" is not a property of a system at all but a relation between a system and how it's deployed, so that the same model is a tool in one harness and an agent in another -- with the tree handling the fact that this position claims half my nodes are asking the wrong question. At each leaf, give the position a name (coin one if it's unnamed), one concrete example system a software team might plausibly ship, and one sentence on its most awkward commitment. Mark any combination of branch answers no one occupies, with a one-line diagnosis of whether it's incoherent, unattractive, or just unexplored, and explicitly flag any pair of leaves your tree cannot really separate from design-doc answers alone. Finally, for each leaf, state in one or two sentences which launch-review safeguards the classification is actually supposed to trigger or waive, and warn us if the label doesn't in fact settle that -- because that's the whole argument I'm trying to end.
