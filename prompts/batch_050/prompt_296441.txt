So at work we have this LLM agent that triages bug reports and can push small patches to a staging repo (human still merges to prod, for now). Two guys on my team, Dan and Sofia, got into a proper argument about how much we should lock it down, and I've stayed out of it because I genuinely can't tell who's right. Both are good engineers, neither is stupid. Here's the exchange as best I remember it:

(1) Dan: We should put the effort into alignment evals -- does it follow instructions, does it ever try to grab resources it wasn't given, does it deceive in the test scenarios -- and if it passes, ship it without heavy containment. Sandboxing it to death is a substitute for actually solving the problem, and it gives everyone false comfort.

(2) Sofia: That's backwards. Containment and monitoring exist precisely *because* alignment evals can be wrong. It's the same reason we don't assume third-party dependencies are benign just because they passed code review once. You architect assuming the component might turn out to be adversarial.

(3) Dan: But if you really assume the model is actively deceptive, no containment scheme survives that assumption -- it just behaves during testing and defects later. So your "control" approach is safety theatre against the very scenario you say motivates it. At least alignment aims at the actual problem instead of pretending.

(4) Sofia: I don't need containment to defeat some hypothetical superintelligence. I need it to defeat the model we *actually have*, which might be opportunistically misaligned in ways our evals missed. Tripwires, canary credentials in the environment, read-only everything by default -- those work on today's model even if they'd fail against something much smarter. And control buys time for alignment work.

(5) Dan: Then your scheme still bottoms out in trust. You want a smaller trusted model reviewing the agent's patches, but if the agent is cleverer than the reviewer it can smuggle stuff past it, so really you're just making an alignment claim about the reviewer model with extra steps.

(6) Sofia: Not with extra steps -- make the reviewer conservative: anything it doesn't fully understand gets rejected, not waved through. The agent being smarter at *writing* code doesn't automatically make it good at hiding intent in code a cautious reviewer reads line by line.

(7) Dan: And then you reject 60% of perfectly good patches and the whole tool is pointless. There's a real tradeoff and you're pretending the conservative option is free.
