I’m a software engineer with no philosophy training, so apologies if this is just a well-known mistake with a name. I was reading about conceptual engineering and tried to translate it into refactoring terms. Unfortunately it now seems to prove that conceptual analysis is impossible, which can’t be right.

The analogy is that concepts are a bit like public APIs. There is some shared specification, different users rely on it, and eventually you discover edge cases where the spec is ambiguous or internally inconsistent. So you publish a cleaner version.

A mate turned that into this argument:

1. A concept is determined by its application conditions: the conditions under which something counts as falling under it.

2. Competent speakers do not agree on those conditions for concepts like person, knowledge, fairness, free will or consciousness. They disagree about foetuses, Gettier-style cases, manipulation cases and so on, even after the nonconceptual facts are fixed.

3. If two people are using the same concept, they cannot rationally disagree about its constitutive application conditions. Persistent disagreement therefore means that they are using different concepts.

4. To make the concept useful, we have to replace the messy pattern of use with one definite and coherent set of conditions.

5. Any definite set of conditions will diverge from at least some competent speakers’ actual judgements.

6. Relative to those speakers, adopting the new conditions is not analysing the old concept; it is proposing a successor concept and changing the subject.

7. So philosophy cannot discover whether a foetus is a person, whether a Gettier subject knows, or whether a manipulated agent acts freely. It can only advocate person2, knowledge2, freedom2 and so forth.

8. The same goes across history. If ordinary use is too divided to fix one concept, then ancient and modern writers on life, cause or justice were generally not investigating the same concepts either. They were just attaching the same words to different successor-concepts.

9. Therefore almost every apparently substantive conceptual dispute is really people talking past one another, followed by a political or practical negotiation about which replacement concept to adopt.

That last step seems mad. It would make a huge amount of science, law and ordinary disagreement not merely difficult but illusory. On the other hand, each premise looks annoyingly plausible if I think about how software interfaces get versioned. At some point enough breaking changes mean it is no longer the same API, even if the package name stays the same.

Which premise or inference should I reject? Please explain why it looked compelling, and what it costs to reject it. I’m especially interested in whether there is a principled difference between analysing a concept, repairing it, and merely legislating a new technical meaning. If there isn’t, does that commit me to the conclusion in (9)? If there is, how do we tell which one a particular philosopher is doing without simply trusting their description of the project?
