I'm a software engineer on a platform team, and we keep getting proposals for new LLM-powered features. Management has decided "agents" are the future, so every proposal is now an autonomous agent that plans, acts, calls APIs, loops until done. My gut says a lot of these should just be tools -- single-shot, human-in-the-loop, does one thing when asked -- but I can't articulate why beyond vibes, and "it feels safer" doesn't win arguements in design review.

I've read a bit about the tool AI vs agent AI distinction (the idea that these are genuinely different design philosophies, not just capability levels, and that agents introduce qualitatively new risks because they pursue goals in the world instead of just producing outputs on request). Can you turn that into a decision procedure I can actually run on a design doc? Like: the questions to ask, in order, what a good answer to each looks like, which answers hard-stop the agent design and push it back to a tool, and which ones are judgment calls where I should escalate to a human because it's a values/business-risk question and not a technical one. Please mark clearly where the procedure needs judgment instead of pretending it's mechanical.

Then run the procedure on two of our actual proposals: (1) a code review bot that reads PRs and either comments (current version) or autonomously checks out the repo, fixes the code, and pushes commits (proposed "agent" version), and (2) a customer support assistant that drafts refund responses for a human to send vs. one that issues refunds itself up to $50. Ideally one of these should come out agent-OK and one shouldn't, so I can see the procedure doing real work. Also tell me where the procedure will misfire -- the kind of proposal where following it gives a wrong or useless answer.
