I work as a software engineer with no formal philosophy background, and I keep bumping into a problem in the philosophy of mathematics through a programming analogy. In code, a well-designed module gets used only through its interface; any behavior that depends on the particular implementation is an accident, and relying on it is a bug. I gather philosophers say something similar about numbers: whether you build the naturals as von Neumann ordinals (0 = ∅, successor of n is n ∪ {n}) or Zermelo's way (successor of n is {n}), arithmetic comes out the same, so the numbers themselves must just be whatever plays that structural role. On the first construction, 2 literally is a member of 4; on the second, it isn't.

A colleague then walked me into this argument, and I can't find the exit:

(1) A claim about "the natural numbers" is a genuine mathematical truth only if it comes out the same on every legitimate implementation; anything implementation-relative is an artifact of the construction, not mathematics.
(2) "2 ∈ 4" is true on the von Neumann implementation and false on Zermelo's.
(3) So "2 ∈ 4" has no truth value as a claim about numbers; it's a fact about a construction, not about the numbers.
(4) The same test disqualifies every claim about what the numbers are — whether they're sets, how many members they have, what contains them.
(5) So there are no objects that are the numbers; there is only the structure, and talk of individual numbers is a convenient fiction.
(6) But then "there is exactly one even prime," which appears to quantify over objects and which every mathematician treats as straightforwardly, determinately true, loses its subject matter too.
(7) So either essentially all practicing mathematicians are confused about what they're talking about, or this argument proves too much.

The first disjunct of (7) seems absurd to me, so I assume the argument goes wrong somewhere — but each of (1) through (5) looks like exactly the interface discipline I'd enforce in a code review, and I can't name a step to reject without feeling like I'm licensing reliance on implementation details. Which step do you reject, why did it look fine, and what does rejecting it cost? In particular: does the fix let some implementation-relative claims back in as legitimate mathematics, and if so, what keeps them from swamping the conclusion in (3)?
