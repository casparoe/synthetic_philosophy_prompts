I'm helping write the safety spec for an autonomous system — fictional for now, but think a logistics robot that runs a warehouse: it schedules deliveries, orders stock, reroutes forklifts, and it's going to have an off-switch the shift supervisors can hit. My boss keeps saying "just make it corrigible" like that's one thing, and I've read around enough to know it definately isn't. Before we evaluate any actual proposals I want the requirements list first: what does a design have to do to count as solving the shutdown problem for something like this?

So: write the desiderata. For each one give me the case or failure mode behind it — the specific thing that goes wrong if a design doesn't meet it. The kind of thing I mean: it must not have any incentive to disable the switch or route around it (including sneaky versions, like acting before the human can reach the button); it also must not start *wanting* to get itself switched off, which I've seen claimed as a failure mode of one popular fix where you make the agent indifferent about being shut down; it must not learn to shape the human's decision, e.g. by behaving well only when watched or by making shutdown look expensive; and it has to survive the system getting smarter and gaining the ability to modify its own code, since a corrigibility mechanism that's just another part of the code is a target like anything else. That's the shape of what I want but it's surely incomplete — please fill it out properly and add whatever I'm missing. Answer in British English btw.

Two things matter to me most. First, mark which desiderata are genuinely non-negotiable (a design that fails them just isn't corrigible, full stop) versus which are contested preferences that one camp treats as core and another would happily trade away — for instance I've seen people disagree about whether a corrigible system should push back when the operator is about to shut it down by mistake, or mid-task when shutdown would be catastrophic, and I honestly can't tell if that's a disagreement about the definition or about the engineering. Second: if some subset of the desiderata looks jointly unsatisfiable — you can have full deference to the operator or you can have the system catching operator errors, but maybe not both, that sort of tension — say so explicitly and explain where the incompatibility actually comes from rather than just gesturing at it. That part is worth more to me than a tidy list.

Keep it at the level of "what the design has to achieve," not "which formalism to use" — I don't need you to adjudicate between specific published proposals, though if one requirement is famous for knocking out a whole family of approaches at once, flag it. No citations or reading lists, I'll track down the literature myself, and keep the tone practical since this is going into a design doc rather than a philosophy journal — even though the problem is basically philosophy wearing a hard hat.
