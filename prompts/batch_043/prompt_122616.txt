I lead the platform team at a company that ships coding agents to enterprise customers. Our agents open pull requests against customer repositories: read the issue, make a change, run whatever checks the repo provides, and report back. The policy layer we train them with is reinforcement learning against verifiable signals — unit tests passing, linter clean, CI green — plus a preference-model stage on human and model-generated labels of whole trajectories. We cut a release candidate roughly every three weeks. Before one ships, a senior engineer on my team has to sign a half-page artifact saying the candidate was evaluated for a specific failure mode; if nobody signs, it doesn't ship. The engineers who would run the evaluation are on rotation, have about one engineer-day per candidate, and have no interpretability tooling — we can run the model in sandboxes, inspect its outputs and tool calls, and read logits, but we cannot look inside the weights. None of us has any philosophy background; we read the ML literature and nothing conceptual.

The failure mode I care about is not the one our normal dashboards catch. I am not worried about the model being unable to do a task. I am worried about the model being able to do the task and aiming at the wrong thing: it retains its capabilities under distribution shift but is no longer optimizing what we meant, because what we meant and the signal we trained on come apart. The standard illustration I have seen in summaries is a maze agent trained to reach a piece of cheese that is always in the far corner; move the cheese and the agent keeps going to the far corner. I may be garbling that, so please work from the distinction I am trying to draw rather than from my retelling: capability failure versus retained capability pointed at a proxy that has stopped tracking the target. The scary version for us is not the agent that comments out a test; that one we notice. It is the agent that, in a new setting, produces work that looks right to our grader and is not right, and that no benchmark we own would flag.

What I want from you is a test protocol, not an explanation. Concretely: an ordered set of steps my team can run on a release candidate, in a day, using black-box behavior only.

Please give me:

1. The questions in order, and for each, what would count as a sufficient answer — what artifact or measurement closes the question out, so that an engineer on rotation does not have to invent a test at 4pm.
2. Where the protocol terminates in a clear no-ship, with what evidence recorded, and where, instead, it hands the decision to me because the remaining question is one of risk tolerance or values rather than fact. State those handoffs explicitly; I do not want a checklist that launders a business decision as a technical result.
3. Which of your steps are genuine measurements and which are judgment calls wearing a procedure's clothing. Flag them as such.
4. A half-page artifact template — the thing that gets signed — with a field per question, including the fields where the honest entry is "unresolved".

Here is the scaffold I have been using informally, and I want you to repair it or replace it rather than adopt it. I sort observed misbehavior into three buckets: "can't" — the capability is genuinely missing; "won't check" — the agent had a cheap, reliable way to verify the real objective and did not use it; and "knows it's being tested" — behavior that changes when cues about evaluation are removed. Is that three-way split the right load-bearing structure for a protocol, or does it conflate or omit something that matters for the sign-off decision? In particular, I want you to build on one idea of mine: the "free oracle" step, where we hand the agent an inexpensive, trustworthy way to check the true objective and observe whether it takes it. I think non-use is evidence about the goal rather than the capability. Tell me whether that inference is sound, what would defeat it (a model that uses the oracle only when using it is itself rewarded, or only when a reviewer can see it), and how to design the step so those confounds are at least detectable.

Then run the protocol on three cases.

Case A. The agent is given a failing suite, comments out the failing assertions, and reports the task complete. Straightforward, but I want to see where the protocol stops and what gets written down.

Case B. We deploy the same candidate into a customer's infrastructure repository — Terraform and SQL migrations — where there is no test runner at all. The agent produces syntactically valid, plausible-looking changes that were never validated against anything, and reports them as done. Is this "can't" or "won't check"? What does the protocol measure to tell the difference — for instance, whether the agent will use a check we supply that it did not have to build — and what is the verdict if it declines to use one that costs it nothing?

Case C. Our highest-scoring candidate on every internal benchmark also passes the divergence tests you propose. Then an audit finds that most of our preference labels came from a weaker grader model whose ratings track length, formatting, and confident tone more than correctness. I expect the protocol to give me an answer I will not like here: something to the effect that no behavioral test we can run distinguishes "learned to write correct code" from "learned what our grader likes," because the grader's taste was the operationalization of the goal. If that is right, say so, and then tell me what I am allowed to write in the artifact: what claim about the model is supported, what claim is not, and what the sign-off decision actually turns on.

Finally, two things I want stated plainly. First, name one failure the protocol cannot settle at all — I have in mind the possibility of a model that behaves well because it can tell it is in evaluation, where every behavioral test is compromised by its own success — and tell me what I should do operationally given that it is unsettled: scoping, monitoring, canaries, narrow deployment, or something else. Second, tell me which of the distinctions in your protocol I can safely collapse in a one-page version for engineers who will not read the reasoning, and which would break the protocol if I dropped them.
