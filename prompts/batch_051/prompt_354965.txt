I'm a novelist, not a lawyer or a developer, so forgive me if I mangle the vocabulary. I'm writing a near-future novel where software licensing has become one of those quiet background battlegrounds, and I need to think through a single legal rule my world runs on so the worldbuilding doesn't collapse the moment a reader who actually writes code looks at it.

Here's the rule. Wether a program B is a derivative work of a copyleft-covered program A gets decided like this. First, figure out everything in B that traces back to A: vendored files, statically or dynamically linked libraries, submodules, generated blobs, copied snippets—whatever. (In my world a registry does this attribution step flawlessly, so don't worry about that part.) Then remove all of it from B and sever any dependency B has on A. Try to build what's left. If what's left won't build, B is derivative, end of story. If it does build, run B's own test suite against it. If B's own tests fail, B is derivative, end of story. Only if the leftover code builds and passes B's own tests is A's contribution treated as mere aggregation, leaving B free to keep its own license.

What I want to know is how this test would actually warp the ecosystem if it were the real standard. What does it incentivize first? Do people immediately keep their test suites paper-thin—or just not write tests, since an empty suite always passes? Do they move the A-dependent features into a seperate repository with its own tiny tests, or generate A's code at build time or pull it at runtime so the repo stays clean? Which move becomes the default one? What does it do to open source maintainers, plugin ecosystems, and the general willingness to use copyleft code? And can you patch the worst holes without just moving the cheating somewhere else?

I'd rather have my plot turn on a realistic failure mode than on a rule that collapses under its own incentives. End with one line in \answer{...} where the ... is a one-sentence summary of your overall read on how the rule plays out.
