I'm a high school senior and I captain my school's programming club, which meets weekly and sends teams to regional competitions a few times a year. I review each team's submissions in the days before a contest and have the final say on what gets used. Over the past season, I've noticed that a large share of our mid-contest debugging is spent on bugs produced by mutable state: two variables aliasing the same list, a helper function quietly modifying its input, an object whose fields change in an order the code doesn't make obvious. I've read the standard advice — prefer immutable data, avoid global state, return new values rather than mutating inputs — but my teammates resist, because in contest problems the immutable version is often slower or longer and the time limit doesn't care about elegance. What I don't have is a clear account of why mutation is hard to think about, and therefore no principled way to say when the cost of avoiding it is worth paying.

Please write a decision procedure I could actually run on each submission, grounded in a real account of why mutable state is hard to reason about: the difference between an object's identity and the state it currently has (the same object persisting while its properties change), aliasing (two names denoting one object), the loss of substitutivity (two expressions can currently have equal values but behave differently later because one denotes a location that will be updated), and the fact that a mutated variable's meaning depends on when in the execution you look at it. The procedure has to be usable by me in about ten minutes per submission, and the questions should be plain enough that I can explain them to teammates who have never studied programming language semantics. For each question, say what counts as a good enough answer, where the procedure stops, and where it hands the decision to a person because the trade-off is one of priorities rather than fact.

Then run the procedure on two or three short cases, including one where the procedure tells me to take the slower or longer immutable version even though my instinct is to keep the mutation. Cases: (1) a teammate's function sorts a list in place, but another part of the program still needs the original order; (2) a dynamic-programming solution fills a global cache in place across recursive calls instead of passing state explicitly; (3) a graph traversal marks cells by overwriting the input grid, while the clean alternative copies the grid or keeps a separate visited structure at a real cost in memory and time. Be honest about the kinds of code this procedure cannot settle and the situations where it would give bad advice.
