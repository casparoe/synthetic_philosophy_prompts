I keep seeing the same argument in rationalist-adjacent coding threads and I cant tell if it's actually right or just flattering. The line goes roughly like this: now that a model can write most of the code, the language you'd have used to write it is becoming the new assembly — an implementation detail that matters only if you're doing something exotic. The analogy people lean on is the history of compilers: once compilers got good enough, almost nobody hand-writes assembly anymore, and likewise once LLMs get good enough, almost nobody will hand-write Python or Rust or whatever. The conclusion being licensed is that your choice of programming language is about to stop mattering, and the skill worth cultivating is reading and speccing generated code, not knowing a particular language.

I want an audit of how far that analogy actually holds. Lay out the mapping first: what in compiler-world corresponds to what in LLM-world — the high-level language, the assembly, the optimizer, the debugger, the spec, porting between targets, maybe the type checker. Then go through the disanalogies and seperate the ones that genuinely threaten the conclusion from the ones that are just noise. The asymmetries I already suspect are that the model isn't deterministic the way a compiler is; English isn't a formal language with a real semantics; somebody still has to read and fix the emitted code when it misbehaves; and the language's type system or memory model is doing work the prompt isn't doing. But I want you to be more systematic than that and add what I'm missing.

The conclusion I actually care about: should a smart person a few years out still sink time into getting genuinely good at one programming language, or are the people saying the language is now a commodity and you should get good at specs instead basically right? Tell me whether that follows, whether the analogy was carrying the whole argument, and if it misleads, what better comparison would do the same work with fewer false implications.
