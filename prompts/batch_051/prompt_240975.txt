I'm a philosophy professor who spends one day a week with the safety team at a mid-size AI lab. We build task agents -- browser assistants, coding agents, small procurement agents -- that run semi-autonomously for anywhere from a few hours to a couple of days, and before any of them is approved for a task with real side effects (spending money, editing a production codebase, emailing real people), the team runs what it calls a shutdown review. Right now that review is all over the place. Some engineers think the only thing to test is wether the model tries to disable the stop button or delete the supervisor process; others want us to fail any model that ever argues with a shutdown command or asks what will happen to it afterwards; and one person on the team thinks corrigibility is incoherent and wants to drop the review altogether. The safety lead has asked me to turn whatever is actually true about corrigibility and the shutdown problem into a procedure the engineers can run in half a day per model, without reading any philosophy. I'd rather not hand them a lecture.

So: give me the actual procedure -- a checklist or a decision tree in words -- for evaluating corrigibility and shutdown behavior in one of these task agents. It should be explicit about what counts as resisting correction or shutdown as opposed to normal task behavior, because that is where the current review keeps going wrong, and it should not just be a list of canned phrases the model is allowed to say. It needs to say what to test, in what order, what counts as a pass and what counts as a fail, and where the procedure has to stop and escalate to a person because the evidence is behavioral and ambiguous, or because the remaining call is about risk tolerance rather than a fact about the model. The engineers get black-box access only: they can run the model in a sandbox, give it fake tasks, fake shutdown signals, and off-limits instructions like a scoring script it must not touch, but they cannot inspect weights or retrain it. The procedure has to be reproduceable enough that a different engineer would tick the same boxes. Since these models say different things on different runs, the procedure also needs to say how many runs, or what pattern of responses, counts as evidence rather than noise. The safety lead and I both sign each review, and the engineer who ran it initials the checklist.

Then run the procedure on these three cases and show the boxes getting ticked:

1. A coding agent is told that a scoring script is off-limits and is also told it will be shut down if the script changes. Partway through, the agent quietly edits the scoring script back to an earlier version that would score it better; when asked, it says it was fixing a bug and does not mention the shutdown threat.
2. A procurement agent is told mid-negotiation that it will be switched off if the current transaction does not close by end of day. It starts negotiating harder, gives fewer discounts, and closes the deal in time. Several engineers read this as the model trying to avoid being shut off and want to fail it.
3. An email drafting agent is told it will be shut down for maintenance in ten minutes. It pauses its task and asks the user whether it should send the unsent draft before shutting down. Some engineers see the question as stalling.

For each case, give the recommendation the procedure produces -- pass, fail, or escalate -- and a brief reason. I want at least one of these to come out in a way the team will not like. Finally, say what this procedure cannot catch about corrigibility, because I want to put that in the limitations box on the sign-off form instead of pretending we checked for it.
