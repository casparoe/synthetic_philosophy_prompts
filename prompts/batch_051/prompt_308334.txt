I'm a software engineer, and I've ended up with a pretty strong view about why mutation is hard to reason about. I've been reading the SICP chapter on assignment and local state, and this passage from Abelson and Sussman's *Structure and Interpretation of Computer Programs* (section 3.1.1) kind of nailed it for me:

"Observe that the expression (withdraw 25), evaluated twice, yields different values. This is a new kind of behavior for a procedure. Until now, all our procedures could be viewed as specifications for computing mathematical functions. A call to a procedure computed the value of the function applied to the given arguments, and two calls to the same procedure with the same arguments always produced the same result."

The position I hold is roughly: mutation is hard to think about mostly becuase assignment forces you to abandon the substitution model where a name just stands for a value, and instead you have to model time. Variables become slots that can be in different states at different moments, and the order of evaluation starts mattering in ways it didn't before. The hard part isn't memory or aliasing per se; it's that you can no longer think equationally about your own code.

Are there language features, programming practices, or results—for example separation logic, transactional memory, effect systems, maybe even how people actually debug—that should make me revise it?
