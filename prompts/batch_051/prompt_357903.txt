I work as a staff engineer at a mid-size payments company, and over the last eighteen months about two-thirds of our new code has been machine-written—Copilot completions, whole-module generation, and an internal agent that opens pull requests on its own. Our review process hasn't caught up. The old checklist assumes a human author you can interrupt and ask why they did something, and it spends most of its time on readability and maintainability. Meanwhile the generated code compiles, passes our tests, and still goes wrong in ways that feel like a language-level problem with no author to pin it on: a function that only hits a nullable value on an unexercised path, two modules aliasing the same mutable state, an overflow check written for a different numeric type than the one deployed, a transaction relying on a weaker isolation level than our on-call runbook assumes.

I've been asked to turn what programming language semantics, type systems, and module boundaries actually give us into a reusable review procedure for our engineers—say five to eight checks they run in order on any generated pull request. Give me worked examples for two or three cases: one where the code is clean, idiomatic, passing CI, and the procedure rejects it because that's the one my colleagues will hate; and one where the checks genuinely don't settle it and a person has to decide. Also say which checks we can automate and which cannot, and where the whole procedure misfires if someone treats it as a substitute for judgment. Our reviewers get about fifteen minutes per pull request, most are not programming-language people, the code moves real money, and I'll have to get the platform lead to sign off on it.
