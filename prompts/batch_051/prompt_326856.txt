I'm a backend engineer working on predictive maintenance for a fleet of commercial chillers, and our anomaly detection currently flags when a machine drifts outside its normal operating envelope. My team keeps calling the next step "mechanistic anomaly detection": cluster the flagged machines by root cause—by the actual mechanism of the anomaly, not by how similar the telemetry looks. The motivation is real: a failing bearing and cavitation can produce near-identical vibration spectra, so purely statistical features group them together even though the fix is completely different.

Where I'm stuck is pinning down "same mechanism" in a way that's true of the machine itself, not just an artifact of however I describe it. If one bearing fails from fatigue and another from corrosion, are those the same mechanism or two different ones? If two, I need the rule that tells me why "bearing failure" stops being one mechanism the moment I add causal detail. It feels like there should be some objective grain at which a mechanism is what it is—like a causal graph that's equal up to some equivalence class—and everything finer or coarser is just bookkeeping or pragmatics.

Is there a principled way to pick that grain? I want to implement it as a distance metric where two anomalies get distance zero iff the share the same mechanism, and I'd rather not have the answer depend on which engineer drew the system boundary or which failure mode we happened to care about that week.
