I am a software engineer with no formal training in philosophy. The short essay below is an attempt to think through something that comes up constantly in my work: how we reason about the code that was never written. I would like your comments on the essay, and I would especially like you to address the three numbered questions at the end. Please do not simply praise or summarize it; press on the parts that are confused, unsupported, or technically wrong, and tell me what a more careful version of the argument would have to say.

**Causation and the missing null check**

I spend a large part of my working life in postmortems. When a service goes down, we reconstruct the sequence that led to the failure. Sometimes the culprit is an instruction that executed: a function dereferenced a variable that happened to be null. But often the moment we actually point to is an instruction that never executed because it was never written. The crash was caused by a missing null check. Nothing in the running system corresponded to that missing check, yet the sentence feels true, and nobody in the room finds it strange.

This suggests a puzzle. A running program is a complete sequence of machine operations. The missing check is not among them. If causes have to be happenings — events, states, objects doing things — then a missing check cannot be a cause, because it is not a happening at all. It is an absence. But engineering practice treats absences as first-class causal factors. It is not a metaphor or a polite simplification when an incident report lists no validation of the user ID at the gateway as the root cause of a breach.

I understand that philosophers call this family of issues causation by omission. The obvious first move is to say that causal claims track counterfactual dependence: the failure occurred because the code did not contain the check, and if the check had been present, the failure would not have occurred. This has the advantage of cleaning up the ontology. Causation lies in a certain kind of dependency between possibilities, not in physical contact. A missing check can be a cause because the world is one way and would have been another way if the check existed.

However, as an explanation, counterfactual dependence is far too permissive. For any given crash, there is an enormous set of absent lines that would also have prevented it. The service would not have crashed if the variable had a default value; if the caller had been rewritten to return a non-null sentinel; if the language made null impossible; if a linter blocked the commit; if the function had wrapped the call in a try-catch. In the postmortem, though, we single out the missing validation. We do not treat the absence of an exception handler as the same kind of contributor, even if it is counterfactually true that an exception handler would have masked the failure. So counterfactual structure alone cannot explain why one absence gets selected as the cause.

The selection seems to track something normative. We identify an absence as the cause roughly where the code diverged from what a competent engineer working under the project's invariants and conventions would have written. The missing null check is the cause because the value could plausibly be null and the interface carried an implicit contract, not merely because writing the check would have averted the crash. That is why we do not say the absence of a second, redundant check was the cause. If the norms were different — if the language choice were different, or the review standards were different — the causal story might also be different. Absence causation in engineering looks norm-relative in a way that causation by collisions or dereferences does not.

That leads to my main uncertainty. One could say one of two things. The deflationary view: omissions are not literal causes. The missing check caused the outage is shorthand for a pair of facts — the outage counterfactually depended on an absence, and the code failed to meet a relevant standard. Literal causation is reserved for the executed instructions that actually moved bits. The realist view: absences can be literal causes in good standing, and engineering talk about missing checks is not shorthand but an accurate report of how the failure came about. My job does not force me to choose between them; both are compatible with our postmortem practices. But the deflationary view implies that many root cause analyses are, strictly speaking, false or elliptical, while the realist view implies that the causal order includes things that never happen. I do not know which is stranger.

The dilemma generalizes beyond code. The same pattern appears in any claim of the form that something caused harm by not doing something: not maintaining a system, not reviewing a change, not checking a sensor reading. If absence claims are norm-relative and merely counterfactual, then a causal statement smuggles in a judgment about what should have happened and should not be mistaken for a purely descriptive engineering fact. But if absence claims are not merely shorthand, we need an account of how something that did not occur can have causal efficacy. I suspect the answer turns on whether causal efficacy is the right thing to demand, but I lack the vocabulary to develop the point.

Questions for you:

1. Where does the analogy between missing code and standard cases of causation by omission hold, and where does it break? In particular, are software norms precise enough to play the selection role I describe, or do I overstate how determinate the relevant standard is in engineering?
2. Is my deflationary/realist distinction drawn correctly? Are there positions in between that I am missing, and have I mischaracterized what the deflationist is committed to?
3. What would it take for an absence to count as causally efficacious, and should I instead stop using the language of efficacy altogether? If so, what should replace it?
