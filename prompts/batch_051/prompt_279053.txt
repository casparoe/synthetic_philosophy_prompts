I'm a backend engineer at a company that builds evaluation infrastructure for proposed alignment techniques, and I keep watching design reviews stall because participants use "alignment is solvable in principle" to mean very different things; the disagreement then resurfaces downstream as incompatible assumptions about what the harness should even test. I don't have formal philosophy training, so I lack the vocabulary to make these differences explicit, but I can tell that "solvable" is sliding between at least three senses: that some correct program exists in the mathematical sense, that there is a procedure we could actually run and verify, and that the problem is well-posed enough that we could even write down what success would consist in.

I would like you to write a decision tree for our internal docs that takes a reader from their starting commitments about what kind of problem alignment is to a named position. Build it from the logical space rather than from a list of labels: first decide which questions carve up the space, then locate the actual positions as leaves, and note the unoccupied answer-combinations with a one-sentence diagnosis of whether each is incoherent, independently unattractive, or merely unexplored. Each branch node should be a question an engineer can answer without already knowing which leaf it leads to, and at least two nodes should be concrete cases rather than abstract criteria — for instance, a specification that is correct but is being optimized by a system that can search a much larger space than its designers, and a system that matches intended behavior on every input the harness can generate but diverges under adversarially chosen inputs.

The distinctions that matter for our purpose are: whether the target values can be given a finite specification at all; whether a valid specification would still be gamed by a sufficiently strong optimizer; whether a solution must remain stable under the system improving itself; whether solvability means mere algorithmic existence or includes actual resource bounds; whether verification can work even when specification does not; and whether the guarantee covers only the training distribution or also out-of-distribution adversarial behavior. The leaves should include at least an algorithmic-existence position, a specification-skeptical position, a Goodhart-style adversarial-unsolvability position (a valid-looking objective gets gamed), a convergence position (a correct outer specification but the trained system develops a divergent internal goal), a verification-without-specification position, an empirical "we will find out by trying" position, and a dissolutionist position holding that the phrase is ill-posed until one fixes the capability regime and the evaluation criteria. Flag any two leaves the tree cannot really separate using only the questions. Assume an audience of engineers and product people with no philosophy background, aim for roughly eight branching questions, and keep it to no more than nine leaves.
