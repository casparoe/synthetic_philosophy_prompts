I'm a backend engineer and I've never taken a philosophy class, so excuse me if I'm reinventing something obvius. At work I've been building an internal LLM agent that does small, boring refactors across our codebases: renaming functions, moving modules, changing config keys, that kind of thing. The point was to let it run without a human reviewing every diff, so I wanted a conservative default. The first version was too blunt: I told it "rename this function and change nothing else," and it would either break every call site or do the rename and then "helpfully" reformat three unrelated files. So I settled on the instruction: make all and only the changes needed to carry out the request. That felt like it solved the problem for about a week.

Then the edge cases started. If I ask it to rename `normalize_input` to `sanitize_input`, should it update the docstring examples? The README? A test that asserts the old name shows up in a schema? A copy-pasted legacy script in another team's folder that happens to call our function but is basically dead? A dashboard query that tracks how often the function is called? Every time I drew the line somewhere, I realized I was smuggling in a little more of my own picture of what matters: code compiling, tests passing, docs being honest, not breaking someone else's half-dead script, keeping observability intact. My teammates draw the line in different places, and the agent has no way to draw it at all unless I hand it a valuation. So now I'm stuck on the concept itself: it seems like you can't even say what counts as a "side effect" without already saying what you care about, in which case "minimize side effects" isn't the cheap substitute for a full specification of value that I wanted it to be. Is that right? Is there a principled way to define "don't have side effects" or "minimize impact" that doesn't secretly require a full spec of what matters? And if there isn't, what's the second-best move — is the whole attempt to get neutrality out of that constraint confused, and I should just bite the bullet and write down what matters?

Could you think this through carefully, as someone who works on AI alignment and the philosophy behind it? Maybe start by brainstorming the different ways a term like "side effect" or "impact" could be made precise, then walk me through which of those definitions, if any, escape the need for a full value specification, and what the ones that don't escape are still good for. I'm less interested in practical engineering fixes than in whether the concept is coherent at all.
