I'm helping teach an introductory programming course, and the textbook introduces variables through the familiar picture of a labeled box: a variable is a box with a name on it, and assignment is placing a value inside the box. The authors use the picture to license a specific conclusion — that reassignment is merely a matter of swapping out the contents, and that once students have the picture, a statement like x = x + 1 should cause no trouble.

A colleague who writes mostly functional code tells me this is exactly backwards: the box picture, he says, is what makes mutation, aliasing, and object identity so hard to think about later, because it invites students to imagine that objects live inside variables rather than being reached through them. His evidence is the familiar failure mode in which students can do reassignment exercises correctly but then cannot predict what happens when two variables are assigned the same mutable list and one is mutated through the other. I'd like the analogy audited rather than just adjudicated. What maps onto what in the box picture — the variable name, the binding, the value, the storage location, the object — and at which points does each correspondence begin to mislead? Which features of literal boxes get quietly imported into the programming case (single contents, one label, contents replaced by wholesale substitution) and which of those imports actually matter for the conclusion the textbook draws? Does the conclusion that the box picture makes reassignment unproblematic survive the disanalogies, and if not, is there a better minimal analogy that does the work the box was meant to do without smuggling in the wrong picture of identity and mutation?
