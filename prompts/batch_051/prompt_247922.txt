I work on the open-source license compliance team at a software company. Our review process answers a recurring question: when a product uses copyleft-licensed code, where does our program end and the copyleft work begin? Our checklist gives seemingly clean answers, but no one can state the rule behind them. A GPL library statically linked into our executable: the whole executable is treated as one work, and our code must be offered under GPL. The same library dynamically linked and loaded into our process at runtime: treated as a single work too, but our legal team marks the case uncertain and tells engineers to prefer a separate process. The same library running as a daemon that our code calls over a local socket: treated as a separate work, so our client ships under a proprietary license. The same library invoked through its command-line interface from a shell script: treated as mere aggregation, with no copyleft obligation on the script. Functionally these arrangements perform the same operations; only the mechanism of connection changes, and with it the answer about what counts as "the program."

I want to understand what this practice presupposes. What theory of program identity, or of derivative work, does a checklist like this implicitly rely on? It looks as though it presupposes that program boundaries are fixed by runtime architecture — address space, process boundary, IPC, command invocation. Is that a coherent criterion, and does the checklist apply it consistently? Reconstruct the implicit view as charitably as you can, distinguish what the checklist strictly presupposes from what it merely assumes out of caution, and say what would change in our review process if we replaced that view with an alternative, for instance that two pieces of code form one work when one incorporates the other's expression or when they are designed as an integrated functional unit. Also say where the process is genuinely underdetermined, such that several different views would license the same checklist.
