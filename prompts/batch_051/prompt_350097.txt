I chair the API-design committee for a numerical computing library, and we're deciding how the next release's polynomial root-finder should hand results back. The current spec returns roots as an ordered list, sorted by real part and then imaginary part, and a lot of downstream user code now just writes root[0], root[1] and depends on that order for tests and docs. One faction wants to keep that canonical ordering: deterministic output is a virtue, users need stable labels, and root[0] has to mean something. The other faction wants an unordered collection instead. Their line is that the ordering is a polite fiction: for a polynomial with a conjugate pair, choosing which root is first is exactly as arbitrary as choosing one of the square roots of -1 and calling it i—it works locally but pretends a distinction the math doesn't give you, and a tiny change in coefficients can make the sorted labels jump, so what root[0] refers to can change discontinuously. They say code that needs to tell roots apart should pass an explicit ordering criterion, so the arbitrariness is visible rather than hidden. Draft the short decision memo I'll circulate before next month's vote: recommend a concrete spec, give the strongest version of the losing side's argument, and say what to do about backward compatibility for existing user code.
