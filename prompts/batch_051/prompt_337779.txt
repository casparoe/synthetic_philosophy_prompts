I've been going back and forth with a coworker who's very "functional programming is the answer" about why stateful code feels so much harder to reason about than pure functions. His line is that mutation is the root of the problem: make everything immutable and the bugs mostly vanish. I'm not convinced. When I actually write immutable code, I feel like I haven't removed the hard part, I've just given it a different name. I'm still tracking how an entity stays the same thing while its properties change, still asking "which version of this value is in scope right now and how did it get here." It just shows up as threading a value through twelve functions, or wrapping it in a monad, or writing lenses, or rebuilding nested records by hand. And the nastiest bugs I've hit in supposedly immutable code came from something aliasing-adjacent: two parts of the program holding different snapshots of the same logical object without realizing they've diverged.

So here's the assignment. Make the strongest argument you can that immutability does not dissolve the conceptual problem of state and identity — it relocates it, and can even make it harder to see. Defend the more specific claim that the genuinely hard thing is modeling objects that persist and change (identity through time), and that assignment statements are almost incidental to that. In making the argument, say what a language or type system would need to actually address the underlying issue — linear or uniqueness types, explicit versions or time, something else — instead of just outlawing one symptom.
