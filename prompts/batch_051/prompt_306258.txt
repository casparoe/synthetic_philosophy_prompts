I had an argument at work that I keep coming back to, and I'd like a careful take on it. The old position, the one Brooks pushed decades ago and Dijkstra gestured at from a slightly different angle, was that the hard part of software is the conceptual construct—what you're actually trying to make the machine do—and not the notation you represent it in; no tooling was a silver bullet for that. A corrolary that has fueled endless language wars is that a language shapes the thinking habits of its users, so features like static types, immutability, and strictness are not neutral. But now my team is in a world where most of the code is drafted by models; we prompt, review, patch, and sometimes just accept. The accidental complexity—remembering APIs, wrangling boilderplate, translating thought into strict syntax—has largely collapsed for us.

So the dispute is this: does the language-shapes-thought argument survive when the machine writes the code? If nobody on my team is really thinking in the implementation language anymore, is the choice of language now just a weak nudge on what the model happens to emit, or does it still shape the design even when the model does the designing? Or has the locus moved upstream, so that a language matters mainly because it shaped the code the model was trained on, not because it shapes us? I want to know whether the old argument is dead, needs repair, or goes through unchanged, and which premise is actually under pressure—the claim that language shapes thought, or the claim that the programmer is the relevant thinker. If there's a repaired version that still says something important, state it plainly.
