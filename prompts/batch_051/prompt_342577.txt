I keep chewing on a parallel between the independence axiom in expected utility theory and an assumption we basically live by in software design, which is that if you benchmark two libraries against the same interface, the ranking is supposed to survive when you drop either one into a bigger system. The way I understand it, independence says that if you prefer lottery A to lottery B, then for any common lottery C and mixing probability p you have to prefer pA + (1-p)C over pB + (1-p)C. The common branch is supposed to cancel out, like a shared term you factor out before comparing. The Allais paradox is the famous case where it doesn't: people prefer a certain $1 million over an 89% chance of $1 million / 10% chance of $5 million / 1% chance of nothing, but when the common branch changes from an 89% chance of getting $1 million to an 89% chance of getting nothing, they flip to the risky side, even though the remaining 11% is the same bet in both problems. Software feels full of the same pattern. A library can win on microbenchmarks and then lose once its running in the real system, not because the other code is different, but because of the shared machinery both candidates now sit behind: the logger, the GC, the retry loop, contention on some lock. The shared context is identical for both candidates, yet it changes the ranking. So my question is: are these the same kind of failure — a failure of compositionality — or am I just pattern-matching on the word independent? If they are structurally the same, does the software side suggest anything about how to fix the Allais side, like factoring out the shared context before you compare? And if they aren't the same, where exactly does the mapping break?
