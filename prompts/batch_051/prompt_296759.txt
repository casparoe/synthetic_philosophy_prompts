I'm a staff engineer at a mid-sized software company, and I run the working group that writes our code-review standards. We keep getting stuck on the same question several times a week, and it has already cost us one production incident: when a function receives an object, when is it acceptable for that function to alter the object in place, when should it return a changed copy instead, and when is it acceptable to mutate but take ownership of the object so that the caller may no longer use it? Underneath the disagreement there seems to be a conceptual ambiguity about what makes something "the same thing" — whether we mean sameness of identity (the same underlying object continuing through a change) or sameness of value (the same contents or observable state). Our codebase has all the usual accelerants for this confusion: caches that hand out shared references, objects used as dictionary keys or compared by identity, UI components that keep references to records, deep-copy utilities that sever object references that were load-bearing, and an event-sourced module whose correctness depends on the order in which mutations are replayed. I would like you to turn the underlying distinction — identity versus value, same thing versus same state — into a reusable code-review procedure that an ordinary engineer can run in about ten minutes before approving a merge, with no background in philosophy and without naming the philosophical machinery.

The procedure should be a sequence of questions or concrete tests, ordered so that the cheap checks come first and the harder ones are reached only when they matter. For each step, say what counts as a sufficient answer, and explicitly flag the steps where a reviewer is making a judgment call dressed up as a mechanical test. It should also state when the procedure has to stop and hand the decision to a human because the question is not settleable by the rules alone. Then apply the procedure to three cases: a function that normalizes a customer record in place when that same record is also held by the cache layer (a case where I expect the author will resist the verdict); a pure formatting function called on freshly deserialized data that no other component has seen yet (a case where I expect the procedure may allow or even recommend in-place work); and one case of your choosing that forces the procedure to admit its own limits. The point is not to build a machine for saying "use immutability everywhere"; it is to make mutation easier to reason about by making the identity/value question explicit. Please write the answer in American English.
