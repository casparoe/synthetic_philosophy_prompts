A mid-sized software company that runs a payments and billing platform is considering a new governance rule for its production code. We are not asking whether the rule is a good idea in the abstract; we want to understand how it would actually behave if adopted. The proposed rule, called "versioned state," has three parts.

First, every mutation of a value must go through a wrapper that assigns the new value a monotonically increasing version number, records the content hash of the previous value it supersedes, and appends the transition to a public lineage log attached to that variable.

Second, the author of each mutation must tag the transition either "same entity" or "new entity." A "same entity" tag asserts that the new value is a later stage of one continuing object — a balance after a debit, a user record after a rename. A "new entity" tag asserts that the old object was discarded and a fresh object created in its place. If a post-hoc review finds that a tag was wrong, the author loses merge privileges for a week and the change must be remediated.

Third, a function may not retain a reference to a value across any point where control can leave the function — no closure that outlives the call, no cache, no memo field — unless the reference is marked "stable," in which case the runtime checks the lineage log at each use and aborts the operation if the value has been superseded.

The architects claim this will force programmers to make explicit decisions about object identity, aliasing, and time, and that it will eliminate the class of bugs in which one part of the program mutates shared state while another part still believes it holds the old object.

Analyze this as a mechanism rather than as a moral or aesthetic position. What does it incentivize among junior developers, senior reviewers, and the team leads who decide what counts as a wrong tag? How would it be gamed — in tagging practices, in the use and avoidance of "stable" references, in how the codebase gets carved into modules, and in what gets rewritten from scratch instead of evolved? What second-order effects should we expect for libraries and patterns that assume ordinary mutation: caches, locks and mutexes, reactive streams, object-relational mappers, undo/redo, event sourcing? Where does the scheme fail first, and which failure modes could be fixed without giving up the core idea that identity transitions should be explicit? In the end, would it select for code that is genuinely easier to reason about, or for something else?
