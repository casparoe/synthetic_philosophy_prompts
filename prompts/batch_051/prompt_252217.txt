I'm a software engineer with no formal background in philosophy, and I've been trying to get clear about what makes it true that a piece of code — or a person — implements or follows a particular rule. I have a set of verdicts that feel right to me individually, but I can't find the principle that unifies them. I'd like you to extract it, or tell me which verdicts have to go.

1. A function `increment(x)` has only ever been run on inputs from 0 through 999, and it returns x+1 in every observed case. I have no hesitation saying the function implements the rule "increment by one." I do not think it implements the rule "increment by one up to 999, and return 14 for anything larger," even though every observation we have is equally consistent with both descriptions.

2. Now consider a different function whose source code literally contains a branch: return x+1 when x < 1000, and return 14 otherwise. Suppose it has the same observed history as the first function, because no input of 1000 or more has ever occurred. Here I say it implements the gappy rule, not the increment rule, despite the identical observed behavior. The source code matters, not just the input-output record.

3. A junior engineer writes a function believing it computes the mean of a list, but the code actually computes the sum. In code review I say the code implements summing, not averaging; the author's stated intent doesn't override what the operations and branches actually do. But when the code itself is genuinely ambiguous, I do appeal to the author's documented intent and to surrounding project conventions to settle which rule it expresses.

4. A model is trained on many examples of addition with operands under 100, and it then generalizes correctly to new pairs like (25, 30) → 55. I'm unwilling to say the model has learned the rule of addition. I'll say it has learned a function that generalizes well over the tested range, and that calling it "addition" is a practical summary rather than a fact about something in the model.

5. A new hire has only ever solved addition problems with operands under 57. I'm comfortable saying they have learned addition, not "bounded addition" — where bounded addition agrees with addition below 57 and returns 5 above 57. But when I go looking for the fact that makes it addition rather than bounded addition, I can't find one: their past behavior, their test scores, and even everything they've consciously thought about arithmetic are all consistent with both. I still believe there is such a fact, but I can't say what it consists in.

My tentative principle is this: a system implements a rule when its explicit internal structure — source code, or a person's understanding — selects one rule from the many that are consistent with its observed behavior; behavior alone never settles it, and the selected rule then supplies a standard for which untested outputs would count as correct. But the principle strains around cases 4 and 5. It gives a clean verdict in case 4 (no explicit structure, so no rule), which I can maybe accept. But in case 5 the person's "understanding" was exactly the thing I couldn't locate when I tried.

Is there a principle that captures all of these verdicts, or close to all of them? State it precisely, show how it handles each case, and say what it predicts for a case I haven't listed — for example, two developers who write behaviorally identical functions, one of whom documents "addition" and the other of whom documents nothing and has left the company. Be honest about which of my verdicts the principle cannot accommodate. If the best account says that in at least some of these cases there is no fact of the matter about which rule is being implemented or followed, say that, and walk me through how that account treats each case.
