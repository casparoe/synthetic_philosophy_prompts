I'm a software engineer who spends most of my time maintaining large legacy systems, and I've begun to suspect that a 'function' in biology and a function in a codebase are close cousins. In philosophy of biology there are two leading accounts of biological function. The selected-effects (or etiological) account says a trait's function is the effect for which it was selected over the course of its evolutionary history: the heart's function is to pump blood because pumping blood explains why hearts were retained and spread. The causal-role account says a trait's function is whatever it does in the organism's present organization that contributes to some system-level capacity, regardless of how it got there: the heart's function is to pump blood because pumping blood is what keeps oxygen circulating now. Restate this debate, in detail, in the vocabulary I actually use to reason about code: intended behavior, design docs, commit messages, issue tickets, git history, test suites, runtime behavior, backwards-compatibility shims, dead code, code written for one purpose but now load-bearing for another, refactors, regressions, and defects. Be systematic: build both accounts in my vocabulary, then give me the residue report. Which claims translate cleanly, which have to be bent, and which have no counterpart at all in how we talk about software? In particular, work through what each account says about a working but obsolete module, a bug that everyone has come to depend on, and a clearly specified component whose tests still pass even though it no longer affects actual output. Then tell me whether the philosophers' dispute survives the translation or mostly collapses into the difference between what the code was built to do and what the code does, a distinction I live with every day. Finally, say what the software vocabulary cannot carry: does the analogy smuggle in an intending designer in a way that misrepresents Darwinian selection, and does either side of the biological debate have resources for talking about malfunction and normativity that the code vocabulary treats as obvious only because engineers have specs, tests, and clients? I want to know whether my hunch that the two accounts are just two senses of the same word is right, or whether one of them is tracking something the other cannot see.
