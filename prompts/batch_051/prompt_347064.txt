I have been trying to make my views about mutable state and identity in programming consistent by writing down my verdicts on concrete cases, and I would like to know what principle, if any, captures them. When two variables in Python are bound to the same list, an append through one variable shows up through the other; I regard this as beyond dispute: they are two names for one list, not two lists that happen to share contents. When I instead write b = list(a), where a and b are flat lists, I regard them as distinct lists from that moment on, even though their elements are exactly the same at the moment the copy is made. If an instance of a class has each of its fields reassigned one at a time, I still want to say it is the same instance afterward, since the binding was never replaced; but if a row is deleted from a database and a new row with the same primary key and the same values is later inserted, I hesitate to call it the same record, even though later queries would see no observable difference. When a mutable object is passed to a function and the function mutates it, I say caller and callee are dealing with the same object; when the function rebinds its parameter to a fresh object, I say the rebinding is local but the object the parameter formerly denoted has not changed identity. For immutable values, such as small integers or interned strings, I find object identity almost beside the point: two occurrences of 5 are the same value whether or not the implementation happens to use one representation or several.

The cases that still trouble me involve replacement and copy-on-write. On a server I maintained, I gradually replaced every module, every configuration file, and eventually the machine underneath it, while keeping the same name, port, and API; the pull of saying that this is still the same server is strong, but I cannot tell whether I am tracking a real sameness or just continuity of an identifier and an interface. In a copy-on-write filesystem, immediately after a snapshot, the source file and its snapshot may literally share the same disk blocks, and a write to either one then causes them to diverge; I would say the two are distinct files all along, despite sharing all their storage at first. I want a precise account of identity under mutation that preserves as many of these verdicts as possible, explains which of them it must overturn, and tells me what it predicts for a case I have not settled: a proxy object that forwards every operation to a backing object which is swapped out underneath it. Is the thing clients are talking to the same object before and after the swap, and does the answer change if the swap is observable? Please state the principle precisely, with the case that motivates each clause.
