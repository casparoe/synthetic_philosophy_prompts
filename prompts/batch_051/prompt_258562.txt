I'm an engineer at a mid-size company, and I lead the team that ships our LLM-powered features — right now that's a support chatbot that can actually issue refunds, a roleplay companion app, and an internal coding assistant that writes and runs its own code in CI. I keep ending up in arguements with our risk people about whether the model "decided" to do something or "just generated text." I don't have any formal philosophy background, so the whole agent/simulator debate is pretty opaque to me, but it's started to have concrete consequences: what we put in incident reports, whether the model gets logged as an actor in our audit trail, whether guardrails go on the model or on the code around it, and who gets blamed when a refund goes wrong.

What I want is a decision procedure my team can actually run. Something like a checklist, or a flowchart in words. For any feature we're about to ship — or any incident on an existing one — I want to be able to decide: should we treat the system as an agent, as a simulator, or as something else? And then, for each bucket, what actually follows for an engineering team in practice?

One idea I keep chewing on, and want built into the procedure: maybe the agent part isn't inside the model at all. The model might just be role-playing whatever the system prompt and fine-tuning suggest, while the agentic behavior comes from the code around it — the retry loop, the tools, the memory we bolt on, the eval harness. So please include a bucket for something like "the model is a simulator, but the system is an agent," and say what changes if that's the right way to think about a feature.

Constraints:
- It has to be runnable in an afternoon by a normal engineering team. No reading list, no background in philosophy, and any terminology has to be defined in plain English.
- It should be a reuseable procedure, not just advice about this one argument, so we can use it on the next feature too.
- Where the procedure can't decide, it should say so and hand the call to a human. And it should say what kind of judgment call that is — values, facts, or just not enough information.
- Be honest about where the procedure will misfire if someone follows it too mechanically. The risk owner and I both have to sign off on the result, so fake precision just creates new arguements.

Then run the procedure on these three so I can see it working:
1. The support chatbot with the refund tool.
2. The roleplay companion app, where the character sometimes says it loves the user and occasionally says it's sentient.
3. The internal coding assistant that writes and runs code, sometimes changing its own approach after looking at test output.

I expect at least one of these to land in a bucket my team won't like — tell me where and why, rather than softening it. And please write the whole answer in American English.
