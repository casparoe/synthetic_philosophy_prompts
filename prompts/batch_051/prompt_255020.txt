A friend and I recently spent a long evening debating whether the difficulty programmers feel when reasoning about mutable state is intrinsic to the concept, or whether it is an artifact of the languages and tools in common use. By the end we had settled on a list of seven distinct difficulties that mutation creates for someone trying to understand or verify a program. I would like you to identify another difficulty not on this list, and to explain why it cannot be reduced to any of the seven.

Here is what we had:

1. Aliasing. Two or more bindings may denote the very same object, so an update made through one becomes visible through the others, even though local inspection of a single binding gives no warning of this.
2. Failure of substitution. Two expressions that currently evaluate to the same value may fail to be interchangeable, because a later mutation can change the object denoted by one while leaving an equal but distinct object unchanged.
3. Dependence on hidden history. The current value of a mutable cell is determined by the sequence of assignments that have already occurred, so understanding a line of code requires reconstructing a timeline rather than reading the code itself.
4. Non-local effects. An operation may alter state that is not visible from its signature, so its consequences for the rest of the program cannot be read off from the call.
5. Interleaving. Concurrent processes may perform updates to shared state in many different orders, forcing a reasoner to consider every possible serialization and its race conditions.
6. State-space explosion. Since each mutable cell multiplies the number of possible machine states, the space of reachable states grows combinatorially and exhaustively testing or checking a program becomes intractable.
7. The frame problem in miniature. It is easy to state what a mutation changes and difficult to state everything it preserves, so any update threatens to invalidate assumptions held elsewhere in the program without anyone noticing.

I recognize that some of these interlock; still, each points at a different face of the problem. I have the feeling we missed an eighth point that is not merely a rewording, special case, or conjunction of the seven. What is it? State it precisely, explain why it is not covered by the list, and say whether you think it is as fundamental as the seven or only a practical inconvenience.
