I keep running into different stories about what it means for something to be complex, and before I read any more of them I want a spec for what a complexity measure is even supposed to do. I'm a software engineer, not a philosopher, so plain language is fine. Here's what's bugging me: a random string can't be compressed, so by one definition it's maximally complex, but intuitively it's just noise; a living cell or a sandcastle feels complex in a way that a pile of sand or a shuffled deck doesnt; and a huge legacy codebase feels complex in a way that five million lines of repeated boilerplate doesn't. So write me the desiderata that any adequate measure of complexity has to meet, with the example or case behind each requirement. Make sure you cover distinctions like random vs. structured (and where 'ordered but simple' fits), one object vs. a thousand copies of it, and complexity as a property of the thing itself vs. the process that made it. Flag any pair of requirements that you think can't be satisfied together, and say which requirements are negotiable and which aren't. Then briefly score Shannon entropy, Kolmogorov complexity, and assembly theory's assembly index (the idea that complexity is the minimum number of build steps from a set of basic parts) against the list — but the list is the main thing I want, not a survey. My actual use case is deciding whether something like a codebase or a physical object is genuinely complex rather than just messy, so anchor the requirements to that where you can.
