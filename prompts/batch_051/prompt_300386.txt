I run open-source compliance for a mid-size software company. Several times a quarter, a product team brings me an architecture for an upcoming release that mixes GPL-licensed code with proprietary code, and asks the question that decides everything: are our proprietary pieces derivative works of the GPL pieces, or are they separate works merely distributed alongside one another? If they are derivative, we must release our own source under the GPL; if they are not, we can ship as we like. Our company has adopted the Free Software Foundation's interpretation as its working standard, even though legal counsel stresses that parts of it are unsettled law. So the decision does not need to be a legal opinion; it needs to operationalize the FSF's line between one program and two. The people who would run this procedure are engineers and product managers, not lawyers. They typically have a few hours during release planning, and the decision reaches me for approval. I want a reusable procedure they can run before I see the case.

Write a decision procedure in the form of ordered questions. It should guide a non-lawyer from a description of how two pieces of software interoperate to a preliminary answer: likely a single program and therefore likely derivative, likely separate works and therefore mere aggregation, or genuinely uncertain. Cover at least the following configurations, and for each explain which way the FSF's framework points and what facts decide it: static linking; dynamic linking at load time; a plugin interface where the plugin calls host functions using data structures from a GPL header; two separate executables in one installer that communicate only by command line; separate processes passing simple text over a socket or pipe; and use of GPL header files or copied data structures without other linking. Keep separate the question of whether the proprietary code is derivative from the narrower obligations that still attach when we distribute someone else's GPL software unchanged; the procedure is about the first, but it should not let a non-derivative answer obscure the second.

For each question in the procedure, state what counts as a sufficient answer, when the procedure stops and answers, and when it must escalate to a lawyer because the matter is legal rather than technical. Mark the steps that are judgment calls no procedure can eliminate, and say what information an engineer should assemble at each point.

Then run the procedure on three proposed architectures: (a) a proprietary tool statically linked to a GPL command-line parsing library; (b) a proprietary plugin written to load into a GPL host through the host's plugin API, where the plugin includes structures defined by a GPL header and calls host functions through that interface; and (c) a paid proprietary dashboard that invokes a GPL command-line analyzer by spawning it as a child process, reads its text output, and is functionally useless without that analyzer, with both executables shipped in the same package but no linking or shared memory between them.

Apply the procedure honestly, including at least one case where a product team is likely to dislike the answer; say where you would expect pushback and how the procedure should respond. Finally, say what the procedure cannot decide: which parts of this boundary are genuinely legal questions, where the FSF's own view gives out or is contested, and what signs should trigger escalation regardless of the procedure's answer.
