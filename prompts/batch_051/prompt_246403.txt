A blog I was reading tries to explain why mutable state is hard to think about, and I can't tell how much of it to trust. The post says: "The real problem with mutation is that when you change an object, you're not updating it — you're retiring the old object and swapping in a new one while keeping the same name. That's what makes aliasing dangerous: if two variables refer to the same object and you mutate it through one of them, the change shows up under the other name, so you can't treat each name as having its own private object. Pure functional languages dodge all this by making values immutable, so a name always refers to the same value for the entire program, no matter what else happens." The part about aliasing makes sense to me, but the "retiring the old object" line feels like it might be smuggling in a functional-programming picture instead of describing what ordinary mutation does. Is the post's summary fair?
