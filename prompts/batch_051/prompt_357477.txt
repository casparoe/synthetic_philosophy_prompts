I’ve recently become personally absorbed in state and identity in programs after inheriting a large agent-based simulation in which nearly every stubborn bug turned out to involve mutable state crossing the boundaries its original author had intended: two components silently sharing an object, a method that looked like a pure accessor quietly modifying a timestamp, and behavior changing when evaluation order changed. The topic stopped being a textbook abstraction for me, and it has made me a more careful reader of student work on it.

I’m now helping grade a take-home midterm for an upper-level undergraduate course called Philosophical Issues in Computation. Below is the exam question and one student’s script. I’d like you to act as my co-examiner. Please bring real expertise in programming language semantics and the philosophy of computation, and please grade carefully rather than giving an impressionistic mark: before you settle on a grade, work through the exam question yourself and fix in your mind what a strong answer would have to establish, then read the script twice, once charitably and once skeptically. The mark scheme rewards correct handling of the more visible claims and penalizes quiet conceptual slips that change the force of the argument.

The exam question reads as follows. “Harold Abelson and Gerald Jay Sussman, with Julie Sussman, open Section 3.1 of Structure and Interpretation of Computer Programs (second edition, MIT Press, 1996) with the following passage: ‘We ordinarily view the world as populated by independent objects, each of which has a state that changes over time. An object is said to “have state” if its behavior is influenced by its history. A bank account, for example, has state in that the answer to the question “Can I withdraw $100?” depends upon the history of deposit and withdrawal transactions. We can characterize an object’s state by one or more state variables, which among them maintain enough information about history to determine the object’s current behavior. In a simple banking system, we could characterize the state of an account by a current balance rather than by remembering the entire history of account transactions. […] This view of a system can be a powerful framework for organizing computational models of the system. For such a model to be modular, it should be decomposed into computational objects that model the actual objects in the system. Each computational object must have its own local state variables describing the actual object’s state. Since the states of objects in the system being modeled change over time, the state variables of the corresponding computational objects must also change. If we choose to model the flow of time in the system by the elapsed time in the computer, then we must have a way to construct computational objects whose behaviors change as our programs run. In particular, if we wish to model state variables by ordinary symbolic names in the programming language, then the language must provide an assignment operator to enable us to change the value associated with a name.’ Explain what they mean by saying that an object has state if its behavior is influenced by its history. Then assess their claim that, if we wish to model state variables by ordinary symbolic names, our language must provide an assignment operator. Is assignment truly required for modeling such systems, or is it only one technique among others? Finally, identify the main conceptual difficulties that introducing assignment creates and say how serious you take them to be.”

The student’s answer reads as follows. “I think Abelson and Sussman’s core definition is correct, but they overstate the implementation requirement. They are saying that an object has state when its behavior depends on its history rather than only on its present inputs; a bank account qualifies because whether you can withdraw a hundred dollars depends on prior deposits and withdrawals. To handle that without storing an infinite history, they say, we introduce state variables that summarize the relevant history, such as a balance, and those variables must change over time. They then claim that if we model time by the computer’s elapsed time and use ordinary names for our state variables, the language has to provide assignment, because a name has to be able to change its value. I think this is a false dilemma. We can model the same account without assignment by threading the balance through each call, so that withdraw takes both the balance and the amount and returns a new balance; nothing ever has to be reassigned. So assignment is not required, and the passage’s claim, stated without qualification, is too strong. The deeper point, though, is still right: once assignment is admitted, a name no longer simply stands for a value but for a location that can hold different values over time, and that is what forces us to separate an object from the value it currently holds and to think about identity. As SICP later explains, the central problem this creates is equality: with mutation, two distinct objects can have the same contents, whereas in a functional language equality reduces to structural equality. The real difficulty is that mutation breaks referential transparency, because the same expression, such as (withdraw 25), may return different values depending on hidden history. But I agree with the authors that assignment is unavoidable for simulating local state in modular systems, and that the costs, while real, are worth paying.”
