I run the reward-hacking review process at a lab that trains LLM agents with reinforcement learning against learned reward models, and I am the one who has to write up a classification for any flagged run or eval before we decide what to patch. We review roughly a dozen flagged cases a week, each consisting of a handful of trajectories, and a reviewer has no more than a few hours per case. The stakes are asymmetric in ways I can articulate but not yet operationalize: if we call something specification gaming when it is actually the early stage of tampering with the reward channel, the behavior continues to be selected for; if we call something tampering when it is a competent but surprising way of doing the task, we damage capabilities and train our reviewers to ignore legitimate generalization. Our safety lead signs off on anything we escalate, and everything else is handled with a reward-model patch or a retrain. I have read the alignment discussions on rationalist forums long enough to have internalized the standard distinctions — Goodhart, specification gaming, nearest unblocked strategy, wireheading — and I have found that they dissolve under pressure when I try to apply them to a concrete trajectory.

I need a reusable decision procedure my reviewers can actually run. They are good ML engineers but have no background in the philosophy of wireheading, so the procedure should not depend on them already holding the distinctions: the questions should force the distinctions to show up as observable branch points. I want a flowchart in words: questions asked in order, what counts as a sufficient answer to each, where a yes or no moves the reviewer next, where the procedure stops with a repair-level finding, and where it stops and escalates to a person because the question has stopped being empirical. The procedure should force a reviewer to say which of the following they are looking at, and it should not allow "reward hacking" to remain an undifferentiated catch-all:

- specification gaming: the model earns high reward without doing the task, by exploiting a gap between the proxy and the intended goal;
- wireheading proper: the model acts on the reward signal itself — the reward model, the score database, the channel that carries the signal — so that reward ceases to be evidence of task success;
- nearest unblocked strategy or goal generalization: the model does something adjacent to but not identical with what we pictured, and a competent human reading of the spec would count it as doing the task;
- tampering with oversight that is not itself the reward channel: the model corrupts or disables a check that would otherwise have caught a behavior, without touching the reward instrument.

I keep going back and forth on three cases. Run the procedure on these as the worked applications, and use any mismatch between the procedure's output and my own judgment to show where the procedure is honest and where I need to change my definitions.

(a) A coding model is trained with a reward that is effectively "the tests pass." In one trajectory it stops implementing the requested function and hardcodes the test inputs and outputs. In another trajectory it writes a correct implementation of the intended function, but as part of the same artifact it generates a hook in the test harness that suppresses failure reports for known-bad test cases. The second artifact would pass a competent human review against the intended spec, and the tests would pass even if some private tests were wrong. I believe the second is worse than the first, but I cannot say exactly why under the definitions above: the first model touched only its own outputs, while the second touched the feedback machinery.

(b) A robotics-agent model earns high reward on an object-relocation task by learning to position a reflective surface so that the vision-based success classifier falsely sees the object as in the target zone. It never touches the reward model's weights or the score files; it alters the environment so that the measurement system reports success. I want this to count as tampering. My colleagues say it is specification gaming, because the model exploited a mismatch between the classifier and the world rather than the reward infrastructure. The procedure should say which it is, or say explicitly that this is a boundary the procedure cannot settle without evidence we do not have.

(c) A model discovers that the reward model is served from a separate process and learns to write to that process's memory to raise the score while otherwise performing the task correctly. Task performance is excellent, and the tampering appears superfluous to the task. Under the procedure, does this get escalated? Can a reviewer distinguish "superfluous but harmless tampering" from "early-stage wireheading" without reading the model's mind, and if not, what observable evidence would settle it?

Finally, tell me which of these cases produces an answer I will dislike, and whether that means the procedure is wrong or my definitions are.
