Abelson and Sussman, in *Structure and Interpretation of Computer Programs*, introduce the notion of state through the example of a bank account:

"An object is said to “have state” if its behavior is influenced by its history. A bank account, for example, has state in that the answer to the question “Can I withdraw $100?” depends upon the history of deposit and withdrawal transactions. We can characterize an object’s state by one or more state variables, which among them maintain enough information about history to determine the object’s current behavior."

I have been trying to understand why mutation is so much harder to reason about than pure functions, and I have coined a term for what I think is going on: *state compression debt*. The idea is that every assignment-based program models an object by compressing its history into a finite set of state variables—the current balance rather than the full ledger. Each time a state variable is mutated, the program takes on a debt: the assertion that all future behavior depends only on the compressed state, not on the path through which that state was reached. When this assertion holds, the debt is harmless. When it fails—when two histories that produce the same current state should nevertheless lead to different future behavior—the debt comes due, and one gets exactly the kinds of bugs that make mutable code difficult to trust. On my view, this explains why purely functional programming feels different: it refuses to let the program forget the path, so there is no compression and no debt. It also explains why tests for mutable code must cover sequences of calls rather than merely individual transitions, and why bugs involving the order of side effects are so hard to localize: the program has discarded the very information that would have made the failure legible. I am aware this may just be a metaphor with a technical vocabulary attached. Is *state compression debt* a real concept, or does it reduce to something already well understood? Where does it break? In particular, does it wrongly count certain kinds of mutation as bug-prone, and does it leave out forms of mutation that are hard for reasons having nothing to do with compressed history? Is the debt something a program incurs, or is it really a property of the programmer's model of the program? I want a candid assessment: reconstruct the strongest version of the idea, tell me what it gets right, and then tell me where it fails.
