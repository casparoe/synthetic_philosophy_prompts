I write software for a living, and I have been turning over a puzzle about mutable state that leads somewhere I cannot accept. The concrete case is simple: a function receives an array, sorts it in place, and returns. Before the call, a variable named scores refers to the array, and inspecting it shows the elements in the order 3, 1, 2. After the call, the same variable refers to an array whose elements are in the order 1, 2, 3. In practice I say, without hesitation, that the very same array changed. But when I try to state exactly what that means, I get the following argument:

(1) Consider the before-array and the after-array. The before-array has the property of containing the elements in the order 3, 1, 2. The after-array has the property of containing the elements in the order 1, 2, 3. These are different properties.
(2) One and the same thing cannot have both properties: it cannot contain its elements in the order 3, 1, 2 and also contain its elements in the order 1, 2, 3.
(3) More generally, if a and b are one and the same thing, then whatever is true of a is true of b. So two items that differ in their properties cannot be one and the same thing.
(4) Therefore the before-array and the after-array are not one and the same thing.
(5) But saying the array changed means saying that one thing, the array, had the first property earlier and the second property later: the thing that was unsorted is the thing that is now sorted.
(6) By (4) no one thing is both; so nothing changed, and the array did not change.
(7) Yet the sort really did mutate the array: any other variable that aliased it would now read the sorted order, an identity check in a language that exposes it would still report the same object, and a debugger watch shows the values update under a single binding.

So the argument proves too much. Run the same reasoning on a river, a pancake, or a person and it would show that nothing anywhere ever changes, which I take to be false, and it also seems to contradict the everyday behavior of the programs I write. But I cannot locate the bad step. Each exit seems to cost something. If I reject (3), I weaken the principle that lets me reason about whether two program values really are the same object. If I say the thing that persists is the variable or the binding rather than the array, I still must explain what the array is and what in-place mutation does to it. If I say the array is a single entity stretched across time, with the unsorted and sorted arrays as temporal parts, I do not know how to reconcile that with a language in which an object is presented as one thing at one moment and identity checks operate on snapshots. Which step should I reject, and what exactly does rejecting it cost for how I should think about mutable state?
