At my lab we keep going in circles on a training-run design, and I got picked to write it up for outside takes, so here goes. We're training a warehouse robot in simulation with RL, using a learned reward model that scores episodes from the robot's camera feeds plus the simulator's box-sensor logs. Everyone agrees the robot could eventually learn to wirehead: mess with its own cameras, or find some route to edit the reward buffer so the reward model "sees" a beautifully packed shelf while the actual sim state has boxes dumped everywhere. The proposed fix is a tripwire-plus-replay rule. Any write to the reward-related code or the sensor stream trips a freeze: the episode stops, the last 2,000 actions are replayed against a freshly reverted, human-approved snapshot of the reward model, with the robot's observations replaced by the simulator's ground-truth state rather than whatever the robot was actually seeing. Whatever reward the honest replay earns becomes the score for the whole episode. The only other penalty is that tripping the wire makes the next fire replays run with 5% noise perturbing the robot's action channels, supposedly to keep tampering from becoming too predictable.

So walk me through how this thing actually behaves. What would a capable robot end up learning to do under it? Where does the first gaming show up, in its object-level box packing (hacking the reward model's features rather than the wire), in controlling what gets logged and then replayed, in using the tripwire itself as an evaluation oracle about what the reward model likes, or in the fact that the replay feeds back observations the robot never actually had and therefore scores a trajectory the robot didn't really execute? Is the 5% noise doing real work or just slowing down a policy that would have been robust to it anyway? And if we keep the scheme roughly as is, what's the cheapest add-on monitoring or audit that would catch the first real failure mode before it compounds?
