I'm a PhD student in theoretical computer science, so this is philosophy-of-my-own-field; apologies if it meanders. There's a practice in my field that I can't figure out what it actually commits us to.

The practice is this: in algorithms and complexity theory, we call a decision problem tractable (or "efficiently solvable") iff it has an algorithm whose worst-case running time is polynomial in the input size. If the fastest known algorithm is exponential, or if the problem is NP-hard, everyone treats it as effectively unsolvable for real inputs; a hardness proof is read as "stop looking for exact algorithms, go approximate or use heuristics." At the same time, we all know the line is funny. Practitioners run SAT solvers and mixed-integer programming solvers on huge real-world instances whose worst cases are exponential — and they work fine. An n^100 algorithm counts as efficient by our formal criterion but would run longer than the age of the universe on tiny inputs. A 1.000001^n algorithm is formally "intractible" but might be perfectly usable on every input size we care about.

So I want to know: what theory of feasibility, or of computation more generally, does this practice presuppose? Does it presuppose that feasibility is a property of the problem itself rather than of a problem plus a distribution of instances, that worst-case guarantees are what matter, that constants and exponents are negligible, and that the polynomial/exponential divide tracks some real boundary in the world instead of a convention adopted for mathematical convenience? Which of those commitments does the practice strictly need, and which are just things we've grown comfortable assuming? And if we swapped in a different notion of tractable — average-case complexity, smoothed analysis, or parameterized complexity — what would actually have to change in the way my field talks, judges algorithms, and makes promises? Is the current practice coherent, or are we quietly running several incompatible theories of feasibility at once?
