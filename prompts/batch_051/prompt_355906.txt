I have recently become responsible for maintaining a legacy codebase whose public API is widely disliked but too heavily depended on to abandon, and around the same time my reading group began discussing the contrast between analyzing concepts as they are actually used and engineering them to better serve our needs. The parallel that keeps recurring to me is this: ordinary conceptual analysis seems to treat current usage as authoritative, the way a commitment to backward compatibility treats an existing API as a constraint; ameliorative analysis, by contrast, treats current usage as defective and revisable, the way a rewrite treats the API as a specification to be replaced. I want to know whether this is a genuine structural correspondence or only a loose metaphor. If it is genuine, what would have to be true of both concepts and code for the transfer to be justified? And do software engineering notions such as deprecation, semantic versioning, and breaking changes have real analogues in conceptual engineering, or does the parallel predict things about concepts that are false?
