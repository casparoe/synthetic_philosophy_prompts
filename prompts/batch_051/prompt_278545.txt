I'm the eval lead at a mid-size lab, and roughly every other week someone walks into my office with a new 'low-impact' regularizer for our coding agent—penalize filesystem changes outside a sandbox, measure how much the agent changes the optimal value of a bank of random reward functions, make the agent plan as if it'll be shut down in five minutes, that kind of thing. My job is to decide, before we burn a sprint building one, whether its actually measuring side effects or just smuggling in a value function through the back door—or will get Goodharted the moment the models get better. I need a decision procedure my eval team can run on any proposed impact measure, written so someone who hasn't read the whole literature can still run it. It should be an ordered checklist, it should flag the steps that are values calls rather than technical calls, and it should say clearly where the honest answer is 'you can't define this without specifying what you care about.' Then run the procedure on three proposals: (1) penalize the agent for modifying any file outside a designated sandbox directory; (2) penalize it in proportion to how much it changes the optimal value of a bank of randomly generated reward functions; (3) constrain it to act as if it will be shut down in five minutes so long-horizon side effects get cut off. I want at least one of these to come out looking worse than its proponents think. Vague red flags like 'that penalizes the wrong thing' aren't enough—give me the specific test that catches each failure, and tell me where the procedure itself stops being able to help.
