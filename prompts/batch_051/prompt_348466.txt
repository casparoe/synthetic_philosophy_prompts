A friend in systems programming walked me through this argument last week and I still can't find where it goes wrong. The conclusion is obviously too strong, but the steps all sounded fine in the moment. It's about copyleft and where one program ends and the next one begins.

(1) The GPL's copyleft attaches only when your code is a derivative of the covered code—not when your code merely runs it or calls it as a separate process. Nobody thinks a shell script that calls grep becomes GPL'd just because grep is.

(2) The standard free-software position is that dynamically linking your proprietary code against a GPL library makes your code a derivative work of that library. That's why the LGPL—the Lesser GPL, a deliberately weaker copyleft for libraries—was created.

(3) Now imagine a GPL'd library that does lossless compression. You could use it two ways. First, your program links against it in-process and calls its compression functions directly, passing pointers to the library's own compression structs. Second, keep the same library behind a tiny proxy process that links to it—the proxy itself would of course be GPL'd, and that's fine—and have your program talk to the proxy over a local Unix socket, sending the same fields as length-prefixed bytes and reading compressed bytes back.

(4) In both cases the same GPL code executes, performing the same operations in the same order on the same data. The only difference is plumbing: in-process function calls across a shared address space versus serialized bytes moving between two processes.

(5) If a work's status as derivative can flip based on that plumbing choice, then the derivative-work relation is tracking an implementation detail about process boundaries, not anything about authorship or creative expression.

(6) So one of two things must be true. Either dynamic linking never made your code a derivative, in which case the standard position is wrong and the LGPL was created for a non-problem; or talking to a GPL program over a socket is enough to make your code a derivative, in which case every shell script and web app that touches a GPL tool is derivative too, and the category swallows the world.

(7) The second horn is absurd. But the first horn makes the GPL trivial to evade: wrap any GPL library in a separate process and a pipe, and your proprietary code can lean on it without being derivative. That can't be what the license means.

So which step should I reject, and what does rejecting it cost? My hunch is something slides between (4) and (5)—maybe "same program" isn't the same thing as "same work"—but I can't reconstruct a stable line from there. If the honest answer is that the line is conventional, tell me that, but only after showing me exactly where the argument breaks.
