I cover AI and software for a magazine, and at a conference afterparty last week I watched two people I respect get into it about whether programming languages still matter when models are writing more and more of the code. I was taking mental notes because its obviously my beat, but honestly they both landed some good shots and I couldn't referee it. Can you go through thier exchange turn by turn and say who's right about what?

Chris opened by saying that a language is only a serialization format between the model and the compiler or interpreter. Now that a model can write idiomatic code in any language you name and freely translate between them, the scarce skill isn't knowing a language; it's specifying the problem precisely and verifying that what came back is right. So languages, he said, are becoming a matter of taste, like a font.

Nadia pushed back that even if the model writes the first draft, people still read, review, debug, and maintain the code for years, and that's where most of the cost sits. She said a language is the interface through which a human has to understand and modify what the machine emitted. If you let the model write everything in, say, Haskell, and the team mostly reads Python, you've moved the bottleneck to review rather than removed it. Languages matter the most as interfaces for human repair.

Chris said the model can just translate it on the fly, and can summarize or comment in whatever language the reviewer likes, so the language becomes a view layer over the same underlying program. Nadia answered that it isn't the same underlying program: translation between languages routinely changes the failure modes — nil versus exceptions, static versus dynamic checking, mutability conventions, how concurrency behaves. A program that's idiomatic in one language can have real production bugs in another. So if the model is choosing the language, it's quietly choosing what can go wrong, and the humans inherit that.

Chris said those choices can be given to the model as explicit constraints — write it without exceptions for control flow, use only immutable structures — so the constraints, not the language, are doing the work. Nadia said that just pushes the question up a level, because a list of constraints is itself a notation, and some languages make certain constraints natural to enforce while others make them a fight. Plus, people don't only choose languages for syntax; they choose an ecosystem — libraries, build tools, deployment story, static analysis, security patches. Models are trained on and generate within those ecosystems, so they don't dissolve them.

Chris admitted the ecosystem point but said that's not an argument about languages per se; it's an argument about infrastructure, and the infrastructure still matters even if the language itself doesn't. Nadia said the infrastructure and the language are inseparable in practice — you can't get the ecosystem without deciding what language your code, configs, and glue are written in.

At that point someone changed the subject and I never got a resolution. I'd like you to referee it: take each move in their exchange and say whether it's basically right, mostly wrong, or a mix; point out where they talk past each other; say what, if anything, both of them are missing; and then give a verdict on who is closer to the truth overall. Please write the answer in American English.
