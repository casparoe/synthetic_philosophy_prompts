I keep coming back to a parallel between two things that are rarely put next to each other, and I can't tell whether it is a genuine structural identity or a loose metaphor. In software engineering, dead code is code that still ships, still gets parsed, and sometimes still executes on schedule, but whose outputs nothing downstream consumes. It persists because deletion carries real risk: it may be entangled with live code in ways no one has documented, and no single engineer has both the authority and the certainty to remove it. In organizations I see what looks like the same object. There are positions — sometimes called bullshit jobs — whose outputs are ignored or would go unmissed, sometimes held by people who privately suspect as much. They persist because eliminating them is costly and uncertain, because they are wired into procedures and payrolls in ways nobody fully remembers, and because managers face the same asymmetric risk: nobody is blamed for keeping a legacy role, but somebody will be blamed if removing it breaks something. Automation makes the comparison sharper, since both a codebase and a firm can be viewed as a set of more or less formalized procedures, and in both cases automating or reorganizing processes is what reveals which steps were ever load-bearing.

I want your judgment on whether this is deep or superficial. Is a role of that kind best understood as dead code in an organization's operating system — an unused, unmaintained procedure retained by default, governed by the same logic of entropy, hidden dependencies, and asymmetric risk — or does the analogy break exactly where it would matter? After all, dead code executes nothing and knows nothing, while a person can hold tacit knowledge, can become productive again if conditions change, and has ends and interests of their own, which makes the persistence of such a role an ethical and political fact rather than merely a maintenance problem. Please make the mapping precise, state what would have to be true on both sides for results to transfer in either direction — for example from what we know about how code rots and why deletion is hard to predictions about which roles survive restructuring — and name one concrete expectation the parallel would license that you think is false or seriously off. Then separate what is reasonably settled from what is genuinely contested among people who study organizations or software maintenance, and be explicit about any place where I would be leaning on a contested or simplified view as if it were consensus.
