I'm putting together a little talk on why reasoning about mutable state is so much harder than reasoning about pure code, and I'm collecting candidate explanations. So far I have (and I think these six cover the standard answers, so I'm after something off-list):

1. Aliasing: two names can point to the same cell, so writing through one name quietly changes what the other name sees, and local reasoning goes out the window.
2. Loss of referential transparency: with mutation, you can't substitute equals for equals, because two expressions with the same current value can behave differently depending on what's behind them.
3. Non-local side effects: a function can mess with state that another, unrelated function depends on, so you have to keep the whole program in your head to understand any part of it.
4. Races and nondeterminism: once concurrent threads can mutate shared cells, the outcome depends on interleaving, so the same program text can produce many different results.
5. The frame problem: to describe what a mutating command does, you'd have to say not just what changes but also everything that doesn't, which is unbounded and never written down.
6. Identity through time: updating an object forces you to say what makes it the *same* object before and after the update — each assignment is a tiny Ship of Theseus.

I want one more explanation of the same kind — a reason mutation is hard to *think about* — that isnt on this list and is not just a rewording, special case, or combination of these six. If you're tempted to give the working-memory/cognitive-load answer, only give it if you can make it specific to mutation as opposed to pure code with long expressions.

Then tell me briefly whether you think your new explanation is genuinely independent of my six, and which of my six you think is weakest.
