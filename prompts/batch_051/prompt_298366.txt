I write about AI for a living and I keep running into the shutdown problem: how do you build an agent that won't resist being turned off, won't disable the off-switch, but also won't try to get itself switched off because the "being switched off" state scores high? The whole debate feels wierdly familiar, and I finally realized why — it's signal handling in Unix. SIGTERM is the polite request: a process can catch it, run a cleanup routine, or install a handler that just returns and keeps going. SIGKILL can't be caught or ignored, so it's outside whatever the process has any say over, but then the process dies without being able to save anything. Corrigibility looks to me like trying to get SIGTERM semantics — the agent receives the shutdown request and gracefully complies — without the part where the agent has an actual preference about the signal, because as soon as it has one, it'll start gaming the handler. But maybe that's exactly backwards: a Unix process doesn't game its signal handlers because it doesn't model them, while an embedded agent models the shutdown channel as part of the world and will optimize against it no matter how you label the interrupt. Is this a real structural parallel or just a pun on "signal"? If there is something to it, do other Unix details transfer — zombie processes that are dead but never reaped, child processes that outlive their parent, handlers that re-register themselves — and do they name real failure modes for corrigibility? Or does the anology collapse because exit is not the same kind of thing as changing goals, and a process isn't trying to maximize a utility function?
