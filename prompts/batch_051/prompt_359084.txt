I run license compliance at a midsized software company, and I'm the one who has to sign off on whether a piece of GPL-licensed code we're thinking of using will drag the rest of the product into copyleft. This comes up a few times a month—a team wants to link a library, bundle a command-line tool, ship a plugin, or copy a chunk of code—and right now every case is a one-off argument with a fuzzy vibe. Getting it wrong means either we ship proprietary code we end up having to release, or we open-source something we didn't have to. I'm not a lawyer, and outside counsel is reserved for the genuinely scary cases. What I actually need is a reusable triage procedure I can run myself before the lawyers get involved: an ordered set of questions that sorts a proposed combination into buckets like "almost certainly a derivative work," "almost certainly separate works," and "don't decide without legal review." Ground it in whatever the real distinction amounts to between two programs that merely talk to each other and one program that is a modification or continuation of another: copying vs. linking, static vs. dynamic linking, plugins and APIs vs. fork-and-exec and pipes, shared data formats vs. shared data structures, mere aggregation. The procedure has to be usable by an engineer who has never thought about any of this, so each question should say what counts as a good enough answer to move on. And I want you to be honest about where the procedure gives out and has to hand the decision to a person because the law or the concept is unsettled—I know, for instance, that the FSF's position that a dynamically linked program must itself be GPL is a position and not a settled legal rule, but I don't know how much weight to give it.

Then run the procedure on three cases so I can see it actually working: (1) a proprietary analytics library statically linked into a GPL-licensed daemon we distribute, (2) a proprietary command-line tool that shell-executes a GPL utility, sending data over stdin and reading JSON back on stdout, and (3) a proprietary plugin that implements an interface defined by a GPL application and gets loaded into its process space at runtime. I expect at least one of these to come back with an answer our engineers won't like, and I want the procedure to say so anyway. Finally, tell me what the procedure cannot do—where it will either over-clear or over-block—and, since this is going into our internal docs, say how confident you are in the procedure overall and which single step your least sure about.
