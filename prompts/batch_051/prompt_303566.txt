I've been going back and forth on here about what "state" actually means, and I keep landing on a test case that feels genuinely 50/50. My working criteria for something's having state are: (a) some part of it persists across calls and can be changed by those calls; (b) its later behavior depends on that history, so current inputs alone aren't enough to predict what it will do; (c) two copies that are current-input-identical but differ in history aren't fully interchangeable. Now consider a memoized pure function: outputs are a pure function of inputs, but internally there's a mutable table caching previous calls. First call f(1) computes and returns 3 and stores it; the millionth call f(1) just reads 3 back from the cache. The outputs never vary no matter what's in the cache, and wiping the cache would change zero answers, but something inside the thing is clearly changing over time—and the same call gets faster and hungrier for memory as history accumulates. Does the memoized function have state? Go through my criteria one by one; where the verdict is no or ambiguous, say whether that's a fact about the function or a bug in the criteria. I half-suspect the criteria are trying to draw one line when "state" is really relative to which level of description you care about, but I can't make that precise.
