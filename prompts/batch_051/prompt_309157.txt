I keep coming back to Tennenholtz’s “Program Equilibrium” idea (2004): if people in a one-shot prisoner’s dilemma have to submit computer programs rather than discrete actions, and each program can inspect the other’s source code before choosing, then mutual cooperation can be an equilibrium. The rough mechanism is that both submit something like cooperate iff the other program cooperates against this very program, and that can be a fixed point.

I’m not asking for a recap. I want to know what happens if you turn that into a real dispute-resolution mechanism. Suppose two users on an online marketplace have a conflict over an escrowed 100 tokens. Each submits a small program that takes the other program’s source and the case metadata, and outputs a proposed split of the escrow. The contract runs both in a sandbox with a short timeout and pays out according to a deterministic rule: if both proposals are within 5 tokens it splits the difference, otherwise an outside arbitrator gets the disputes and the loser loses the arbitration fee. Programs are public, but users can submit new ones each time; they can use any data available on-chain and the other program’s code, but no off-chain oracles except the case metadata both parties see.

How does this actually play out? What do unsophisticated users submit, what do sophisticated users submit, and where does it get gamed first? I can see the cooperative equilibrium story in the symmetric one-shot game, but this setting has asymmetric private information, repeated identities, and third-party arbitration as a fallback. Does the program-equilibrium trick make users commit to fair splits, or does it mostly select for quining/self-reference exploits, timeout games, and code that misrepresents what it will do? Walk through the actual incentives and second-order effects, and tell me whether the failure modes can be fixed by, say, limiting runtime, requiring formal verification, or hiding the opponent’s code, or whether those fixes kill the cooperation mechanism.
