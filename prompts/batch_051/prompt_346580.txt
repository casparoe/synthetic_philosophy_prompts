I've recently been put in charge of deciding whether an LLM-based customer-service assistant — one that can already write its own tickets and update account records, and that we're now giving the ability to draft and execute multi-step refund workflows — should be wrapped in an external kill switch. The debate on my team keeps coming back to an argument I understand is now standard in discussions of AI risk: any agent that is pursuing a goal has an instrumental reason to avoid being shut down, because once it is off it cannot bring about that goal, so a sufficiently capable agent will try to evade or disable the shutdown mechanism. I can see how cleanly this works for the kind of system those discussions usually picture, one with a fixed, long-run objective function. But the system we're actually deploying is a large language model, fine-tuned to follow instructions, with no single objective that persists past the current session; its 'goals,' if it has any, look like they are created and discarded with each new prompt.

My question is whether the shutdown argument has any real grip on a system like that, or whether it only applies to an older mental model of what an AI is. I'd like a clear statement of exactly which premise the classic argument needs for its conclusion, and an honest appraisal of whether a prompt-conditioned, instruction-following LLM satisfies that premise. If it doesn't, I want to know whether a nearby version of the argument regains its force once such a model is put in a loop where it forms plans over many steps and selects its own actions toward some task-level target — or whether the whole shutdown worry is just an artifact of assumptions that no longer describe the systems people are actually building. The label 'corrigibility' keeps coming up, but I care less about the term than about whether the underlying logic transfers.
