I'm the engineer responsible for the message filter on an AI coding assistant. The assistant makes factual claims about the repository and about its own internal states, and I'm trying to write a rule that catches messages which are logically consistent but still shouldn't be sent to users. Below are the examples I've collected, with my current verdict on each. "Ship" means I'd allow a user to see the message; "block" means I wouldn't.

1. "The deploy succeeded, but I don't believe the deploy succeeded." — Block.
2. "The deploy succeeded, but the on-call engineer doesn't believe that it succeeded." — Ship.
3. "The deploy succeeded, but I didn't believe it would." — Ship.
4. "The deploy succeeded, but I have no evidence that it succeeded." — Block, though I can't articulate why this should be blocked.
5. "The deploy succeeded, but I'm not sure that it succeeded." — Block, though it feels less broken than (1).
6. "The deploy succeeded, but I'm not certain that it succeeded." — Undecided. If "not certain" means merely "less than 100%," it seems fine; if it means "I still have real doubt," it seems wrong.
7. "The deploy succeeded, but I'm not aware that it succeeded." — Block.
8. "I believe the deploy succeeded, but it didn't succeed." — Ship, but only as a confession that a belief hasn't caught up with the facts.
9. "I think the deploy succeeded, but I don't believe the deploy succeeded." — Block.
10. "I know the deploy succeeded, but I don't believe it succeeded." — Block.
11. "The deploy might have succeeded, but I don't believe it succeeded." — Ship.
12. "The tests are green, but the reviewer hasn't confirmed that they're green." — Ship.
13. "The deploy succeeded, but I wouldn't assert that it succeeded." — Undecided. It might just be a report about my own caution, or it might be broken in the same way as (1).
14. "The deploy succeeded, and I'm 60% confident that it succeeded." — Undecided. It sounds like a hedged assertion, but maybe that's exactly what an assistant should be allowed to send.

I tried a first-pass rule: a message is defective just when it asserts something and, in the same message, says that the speaker doesn't currently believe that same thing. That rule handles (1) correctly, lets (2), (3), (8), (11), and (12) through, and flags (10), but it says nothing about most of the others and gives me no guidance on these, which I can't classify:

- "The deploy succeeded, but I haven't verified that it succeeded."
- "The deploy succeeded, but I don't know that it succeeded."
- "The deploy succeeded, but I can't prove that it succeeded."
- "The deploy succeeded, but I don't believe that I believe it succeeded."
- "The deploy succeeded, but I believe that I don't believe it succeeded."
- "The deploy succeeded, though I wouldn't bet on it."

What I want is a principle, or a small set of principles, that captures the verdicts I'm confident about, tells me which of my other verdicts I'd have to overturn if they can't all survive, and settles the unclassified messages. State the rule or rules precisely enough to implement as a filter, run them against all twenty messages above, and flag any pair of verdicts that can't both survive under one coherent account.
