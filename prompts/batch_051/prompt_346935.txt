A friend showed me this arguement and I can't find the exit. It seems to prove that mutable state is trivial to reason about, which is absurd given how much pain aliasing has caused, so something must be off—but each step looks fine to me.

(1) A variable in an imperative language is just a name for a memory cell.
(2) An assignment x = e changes the contents of the cell named by x and touches no other cell.
(3) So the store of a program is a finite map from variable names to values, and running a program is just updating one entry at a time.
(4) Finite maps are about as simple as it gets: look up a key, store a value, no hidden interactions.
(5) Therefore reasoning about mutable state is just bookkeeping.
(6) Yet with references and mutable fields, x.f = 1 can change what y.f reads, even though the statement only mentions x.
(7) That seems to leave two options: either (2) is false, or the map in (3) was missing a bunch of cells and isn't the full store after all.
(8) My friend says this shows the usual box-and-assignment picture is self-undermining: you can't keep both the locality of assignment and the claim that you know the whole state from the variables.

I don't think I should end up believing (5), but I also don't want to reject (2), since it's just what assignment means in a box model. Where does the argument actually go wrong, and what does it cost to reject the step that fails?
