I serve on the Responsible AI Oversight Committee at a laboratory that builds automated software-maintenance agents. We must decide whether to approve a proposed change to how the next generation of the lab's refactoring agent will be supervised.

Today the agent is supervised on outcomes. A proposed refactor is scored by whether the resulting code passes the test suite, meets style and performance standards, and merges without incident. The agent also produces a short written preservation argument explaining why the transformation preserves the program's behavior, but that argument is not scored; it is only archived.

The proposal is to add process-based supervision. A separate step-level verifier would score the individual steps of the preservation argument: the identification of an invariant, the claim that each edit respects the invariant, and the treatment of side effects. The agent would be rewarded for both the outcome and the quality of its argument, and a refactor that passes all tests while its argument fails the verifier would be treated as a negative example. The engineering team argues that production feedback is sparse and delayed, and that outcome supervision currently permits refactors that are correct only by accident: code that passes tests but violates unstated invariants on rare execution paths, sometimes causing failures weeks later. Step-level verifier judgments would provide denser training signal, and the written argument would become an auditable safety check rather than a formality.

Some committee members resist the change. They point out that the verifier is itself a learned model and can be gamed, so the agent may learn to write arguments that please the verifier without reasoning soundly, merely displacing reward hacking from tests to the verifier. Others note that requiring an explicit step-by-step argument may penalize competent refactors grounded in tacit pattern recognition, or may produce slower, more verbose agents without improving actual outcomes. Supporters respond that a refactor whose safety the team cannot articulate is one the lab should not ship, and that process criteria protect against the deeper failure of systems that satisfy surface tests while doing the underlying task badly.

Draft a short policy memo addressed to the Committee recommending whether to approve the proposal, reject it, or approve it under specified conditions. The memo should state a clear bottom line, give the reasoning behind it, and treat honestly the strongest consideration on the losing side.
