I work as a software engineer, and every conversation I have about mind uploading eventually lands on a version of the brain-as-computer analogy that I don't know how to respond to. The argument, as my friends (mostly systems engineers) put it, goes roughly like this. The brain is hardware and the mind is the software it runs, so a person is the pattern — code plus state — not the physical substrate. Replacing neurons one at a time with functionally equivalent artificial neurons is just a rolling upgrade: you swap components one by one behind a load balancer and the service never goes down. Since no single swap changes anything noticeable and the service never lost continuity, the system at the end of the gradual replacement is obviously still the same system, and so the person is still the same person. Once you accept that, they say, the difference between gradual replacement and destructive upload is only a difference in deployment strategy. Gradual replacement is a canary deploy; destructive upload is a blue/green cutover: you snapshot the running state, provision a new instance on better hardware, cut over, and decommission the old instance. Identity was in the code and state all along, so the new instance is you. Being afraid of the destructive scan but not of the slow replacement is like a team that will happily run a six-hour rolling deploy but refuses a thirty-second cutover — a superstition about the speed at which the substrate changes.

I can feel that the analogy is doing real argumentative work, but I don't trust my ability to see where it is doing too much. I have no formal philosophy background; I know the old ship-replacement puzzle by name but not the literature. What I do know is deployed systems, and I suspect the analogy succeeds partly by importing things that are true of software I write — that state can be cleanly serialized and reloaded, that identity conditions are whatever we stipulate for the service, that the software is designed from the start to be portable across hardware — and quietly treating the brain as if it had those properties. I want you to tell me how far the analogy actually holds, and specifically whether its final conclusion about destructive upload survives.

3. Where it breaks (roughly 300 words). Give the disanalogies, with particular attention to the properties of running software that the analogy imports without argument — serializable state, stipulated identity, intended portability, and the difference between a live process and a restore from a snapshot.

4. Which breaks matter for the conclusion (roughly 300 words). Separate the disanalogies that merely make the analogy loose from the ones that threaten the inference from gradual replacement to destructive upload. In particular, address the gap between "slow replacement preserves me" and "a fast copy is me."
