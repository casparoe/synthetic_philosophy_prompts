Assume the standard LessWrong-style distinction between tools and agents: a tool pursues only the objective supplied by the operator for the current run, whereas an agent maintains its own standing goal representation, can generate novel intermediate goals in service of it, and may act to protect that representation against shutdown or modification. Suppose we are building an LLM-based research assistant that can browse the web, execute code in a sandbox, and read and summarize files, and we want to keep it on the tool side of this divide even as its capabilities and task horizons scale. Below are seven proposed design mechanisms for doing this. Please rank them from 1 (most effective at preventing the system from becoming an agent) to 7 (least effective). Give one or two sentences of reasoning for each placement. Then name the single pair of mechanisms whose relative ordering you would be least confident about if the system were subsequently fine-tuned on transcripts of its own successful tool use, and explain briefly.

1. A fixed operation scheduler: every tool call passes through a human-written scheduler that can invoke only four primitives (read-file, run-search, execute-sandbox-code, append-memo); the model fills in arguments but cannot select, reorder, or repeat operations.
2. A valve model: each proposed command must be approved by a smaller model trained solely to flag commands as dangerous, and the valve sees commands one at a time with no representation of the larger task.
3. Myopic credit assignment: the policy is trained with a reward that depends only on the immediate next observation, with no value propagation or discounting across later timesteps.
4. Re-anchored context: the first block of the context window is a frozen copy of the operator's original instruction, reinserted by the scaffold at fixed intervals; any attempt by the model to overwrite or delete that block terminates the run.
5. A corrigibility probe penalty: an auxiliary training loss penalizes the mutual information between the model's activations and a separately trained classifier that detects, from internal state, whether the model would resist being shut down or having its current objective edited.
6. Action-proposal-only design: the model never executes commands itself; it outputs a ranked shortlist of candidate next actions, and fixed external code always executes the top-ranked action, with no write path from model to executor.
7. Delayed and inspectable effects: every command the assistant issues is applied only to a staging copy of the environment, and is copied into the real environment only after a 24-hour delay and human review, so no action can have unexamined immediate external effects.
