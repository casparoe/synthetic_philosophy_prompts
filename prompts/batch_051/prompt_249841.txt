At work I'm on a small committee that has to decide something that sounds dumb but has real money attached. Our company maintains a product called Meridian, inventory and billing software for auto repair shops, launched in 2009. Over the years basically every piece of it got replaced — the backend went from Perl to Java to Go, the database moved from Postgres to something proprietary, the UI has been rebuilt twice. Nobody ever said "we're building a new product now"; it was just normal maintenance. One of our oldest customers has a 2011 contract that locks in support and updates for "Meridian" at a fixed price. They're now arguing the current system isn't really Meridian anymore, so the locked price shouldn't apply (or, on there other reading, they're owed a free migration to whatever the "real" successor is). The weird part is we still have the original source in an archive, and another customer still runs a fork of the old version, so "the original Meridian" sort of still exists as code — we just don't sell it or patch it.

I've been asked to draft a short memo for the committee with a recommendation. We can't punt: the contract says the committee has to determine whether the current system is Meridian for purposes of the agreement. I keep flip-flopping. On one hand the current system shares literally no code with the 2011 version. On the other, if you trace the commit history there was never a break — every changed line went through review on the same repo, and the team always called it Meridian. Write the memo: a clear bottom line (is the current system Meridian for contract purposes or not), the reasoning, and an honest treatment of the strongest argument on the losing side. If you can, give us a rule or test we could actually apply next time this comes up, because it probably will. I'm a software engineer, not a philosopher, so I don't need the deep theory — just something the committee can actually act on.
