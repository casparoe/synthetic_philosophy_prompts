I'm a software engineer, and I've noticed that I make a certain epistemic bet every working day. The code I write and review rests on mathematical machinery: the arithmetic of machine integers, the logical systems inside type checkers and formal verification tools, the number theory behind cryptographic primitives. I treat the consistency of this machinery the way I treat the assumption that a CPU will not silently flip a bit — as a background condition that never gets scheduled for verification. Part of the reason is that I've absorbed the claim that no formal system strong enough to express basic arithmetic can prove its own consistency, so there is no clean proof to be had at the bottom. What I actually rely on is a track record: none of these systems has produced a contradiction under enormous use, and a contradiction in basic arithmetic would be so disruptive that, I assume, it would already have been discovered. My shortcut is to assign that risk a probability of zero and never spend engineering time on it. Is this policy defensible, or is it a bias dressed up as a rule — treating the absence of a discovered contradiction as if it were evidence of consistency, and treating an empirical absence as if it were a proof? Where would the habit fail, and is there a restated version that keeps the engineering benefits while not claiming more than the evidence supports?
