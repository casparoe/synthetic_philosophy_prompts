I chair code review, and sign off on every change, for a team maintaining a large Python codebase that computes regulatory and financial reports. We review several changes a day, and the stakes are high: our worst production incidents almost all trace back to shared mutable state, usually a function that mutates an object it was handed and thereby couples two parts of the system that were supposed to be independent. We cannot ban mutation, and we cannot rewrite in a functional language. Please write a reusable decision procedure our reviewers can follow when judging whether a particular use of mutable state is acceptable. Ground it in the distinction that makes mutation hard to think about: the difference between an object being the same object through change and two objects merely having the same value, and the way in-place mutation keeps one identity alive through time so that later changes reach backwards into earlier snapshots. The procedure must be usable in roughly ten minutes by a competent reviewer with no philosophical background; specify the questions to ask in order, what counts as a sufficient answer to each, where the procedure stops with a no, where it hands the decision to a person because the issue is one of design judgement rather than hard criteria, and what to do when a reviewer cannot determine whether the object is still reachable from elsewhere. Then apply it to three cases: a sort helper that sorts its list argument in place and returns None; a cache that stores a dictionary handed to it by a caller and later mutates that dictionary while refreshing; and a hot inner loop that mutates a large array it created itself and which never escapes the function. Include at least one case in which the procedure gives an answer the team will not like, and be explicit about what the procedure cannot settle. Please write the answer in British English.
