I spend a lot of time thinking about why code that mutates state is so much harder to reason about than code that returns new values, and I keep running into a prior problem: I cannot find a working definition of "mutation" that survives contact with the cases I actually meet. I suspect the word does at least two jobs at once. Sometimes it means something operational — an existing object is altered in place, so that every name referring to that object sees the new contents. Sometimes it means something observational — a later computation can detect that something changed, or an expression will now evaluate differently. These two readings usually travel together, but I can prise them apart.

Give me a working definition of mutation that correctly classifies the following cases. My own rough verdicts before I try to theorise: I am confident the first is mutation; I am confident the third is not mutation on any object-centric view; I am confident the fourth is mutation; I am genuinely unsure about the rest.

1. `xs.append(7)`, where `xs` is a mutable list in Python. Two variables refer to the same list before the call; both see the appended element afterwards. The list object itself persists.

2. `xs = xs + [7]`, again in Python. This creates a new list and rebinds the name `xs`; any other reference still points to the old, unchanged list. A later use of `xs` will see a different list afterwards, so the line is not observationally inert, but no pre-existing object changes.

3. `a, b = b, a`, a simultaneous reassignment in Python. Both names are rebound; no object is touched.

4. `obj.x = 5`, an attribute assignment on a user-defined object. The object persists, an attribute changes, and every alias of `obj` sees the change.

5. `count += 1` running inside a function that declares `count` global. The integer `count` originally referred to is discarded and a new integer is bound; what persists is the environment slot, not the integer.

6. A function that writes a line to standard output. The program's own data structures are untouched, but the terminal scrolls and a file offset advances, both of which are genuine changes.

7. A cached function: `def f(x): if x not in cache: cache[x] = expensive(x); return cache[x]`, where `cache` is a dict held in a closure. On first call the cache is updated; later calls observe faster results, but the function's answers never change.

8. Inserting into a persistent collection: `new = old.add(x)` in a language with immutable collections. `old` remains usable and unchanged from the caller's perspective, while the implementation may internally reuse and revise shared nodes that no alias can observe.

9. A shallow copy of a tuple containing a list: `b = a[:]` gives a new tuple `b` whose first element is the same list object as `a[0]`. Appending through `b[0]` shows up when you inspect `a[0]`, even though both tuples are nominally immutable.
