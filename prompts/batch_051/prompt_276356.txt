Lately I can't stop noticing a parallel between the old counterpart theory vs. transworld identity debate and the way different version-control systems decide what counts as "the same file" across commits. In the metaphysics: transworld identity says there is literally one individual that exists in many possible worlds with different accidental properties, while counterpart theory says each individual is world-bound and "could have been F" is really about counterparts in other worlds that are similar in the contextually relevant ways. Now look at Git versus something like Subversion. Subversion tracks file identity over revisions: it's the same object, revision 42 versus revision 43. Git's object model doesn't really store file identity across commits at all; it stores snapshots of content-addressed blobs and reconstructs "this file changed" afterward by comparing similar blobs, even guessing renames by similarity when the path changes. The path hangs around by default, but that feels like a convenience for humans rather than a primitive sameness in the underlying model.

So my question is whether the parallel is deep or whether its just the words "similarity" and "identity" doing all the work. Pressed further, what maps to what? Is a commit a possible world, a blob an individual, a path history a counterpart relation or a transworld identity label? What would have to be true on both sides before a result transfers — for example, does the old puzzle that one and the same thing can't be both square and round across worlds have a genuine analog in why Git makes blobs immutable per commit? Does the fact that Git needs a similarity threshold for rename detection mark a place where the metaphysical version gets vague without any threshold? I'd love one concrete thing the analogy seems to predict that is false on one side, so I can see exactly where the structures come apart. And if the whole comparison is superficial and I'm just playing word association, tell me that rather than humoring it.
