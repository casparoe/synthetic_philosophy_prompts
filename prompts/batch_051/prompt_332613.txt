Below is a draft of a short essay on the copyleft concept of a derivative work. Please read it and comment as specified.

Draft essay: Where does one program end and another begin?

Copyright law is comfortable with works that arrive already individuated: a novel, a canvas, a sculpture. Software does not arrive that way. A running system may load libraries, execute code emitted by another tool, communicate with a back end over a socket, or embed an interpreter. Which of these combinations makes the system a modified version of an original program, rather than two works standing in some looser relation?

Copyleft licenses draw a practical line between derivative works and mere aggregation. Placing two programs on the same disk is usually treated as aggregation, while editing the program's own source is derivation. But between those clear cases lies a long continuum: a plugin loaded into the same process, a program linked against a library at build time rather than at run time, a service that sends queries to a back end over HTTP, a code generator that emits snippets of copyleft code into an otherwise independent codebase, a container image that packages several programs together, a separately distributed patch that applies only to the original. Each candidate criterion—shared address space, symbol resolution, whether code from one file is copied into another, whether the two sides exchange data through a narrow interface, whether one is useless without the other—captures some intuitions and fails on others.

I want to suggest, without pretending to settle the legal question, that the underlying difficulty is not technical but ontological and social. Software boundaries are conventions made for coordination: they mark modules, teams, ownership, and licensing obligations. There is no fact of the matter, in the binary or the source tree, about where one program ends and another begins. The derivative/aggregation distinction is best understood as an attempt to apply a legal concept built for indivisible objects to a medium whose parts are routinely split, recombined, and wrapped. On this view, calling something a derivative work is less like discovering a structural property and more like asserting a claim about control: who must share, who may keep closed, and which downstream users inherit which obligations.

An analogy: spoken language has no consistent acoustic gap between words; listeners segment a continuous signal using a competence they already possess. Code likewise has no naturally occurring program boundaries, only boundaries imposed by a community with interests. The difficulty is that copyleft asks the law to treat some of those imposed boundaries as if they were natural for the purpose of deciding when obligations propagate.

Please comment on the draft with the following questions in mind. First, is the central claim—that the derivative/aggregation boundary is underdetermined by the technical facts—stated too strongly, and how should it be qualified? Second, which of the candidate criteria set aside above has the strongest case for being more principled than the draft allows, and what would the account need to say to resist it? Third, does the reframing in terms of asserted control do explanatory work, or does it merely relabel the problem? Fourth, is the word-segmentation analogy apt, or does it presuppose the conclusion? Conclude by suggesting at least one concrete revision that would make the essay harder for a defender of a bright-line technical criterion to dismiss.
