I've been refactoring a bunch of Python at work and I keep running into the same muddle: mutation sometimes feels completly fine and other times feels like the source of every bug, and I can't tell what my actual rule is. I have no philosophy background, so sorry if this is a known topic I'm just stumbling into.

Here are some cases and my gut reactions. (1) A helper takes a list, appends to it in place, and returns the list. In a one-off script I'm fine with that. But if the same list is also referenced by a caller three stack frames up, the helper feels sneaky to me, even though the operation is identical. So I blame the aliasing, not the mutation. (2) I make a shallow copy of an object that has a field pointing to a mutable array. I think of the copy and the original as different objects, but the shared array makes them "not fully seperate" — like two hands holding the same bucket. (3) Strings, ints, and tuples: I basically never worry about who else holds a reference, and I think it's because they're immutable, so identity hardly matters. (4) I've used an immutable/persistent list library where an "update" returns a new list and the old one stays untouched. That's much easier to reason about in a big codebase, but I notice I never think of the new list as "the same list, updated" — I think of it as a different thing entirely. (5) A bank account object after `account.deposit(20)`: I unhesitatingly say it's the same account, the same object, even though its state changed and the pre-deposit version no longer exists anywhere in the program. That feels fine, not like a contradiction. (6) Two objects that compare equal (`a == b`) but aren't the same object (`a is not b`), like two separately-fetched rows with identical fields: I say they're different objects but the same row, and I'm not sure what "same" is doing in that sentence. (7) Mutating a collection while iterating over it: whether or not the runtime catches it, it feels deeply wrong before any error occurs, like the thing I'm iterating over stops being the thing I started with mid-loop. (8) Two threads incrementing a counter without a lock. I know it's a race, but part of me insists that an increment is one operation, so nothing should be lost — and the fact that it can be lost feels like reality rejecting my entire picture of what the operation is.

Cases 4 and 5 seem to point in opposite directions, and I can't figure out how to hold both. Is there a single account of what makes mutation easy or hard to think about — something about identity over time, ownership, or value vs. place — that captures all or most of these verdicts? If not, which do I need to give up? And what does the resulting principle say about the case I keep flip-flopping on: an event-sourced object where every change is appended to a log and the current state is recomputed by folding the events — is the object the same thing across events, or is each recomputed state a new object, and why do I keep changing my mind about that one?
