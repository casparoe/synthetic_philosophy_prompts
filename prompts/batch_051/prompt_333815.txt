Two people on my team got into an argument in code review, and I've been asked to referee but genuinely don't know. The code has a shared feature-flag config object that different subsystems read during startup. One subsystem mutated a flag on it, and another subsystem's behavior changed too because both held references to the same object. Ana said the fix is to stop mutating shared config: treat the config as immutable, so any "update" returns a new object and each subsystem keeps it's own version. Ben said that's abolishing identity to avoid a bookkeeping problem. The config is supposed to be one thing — when a flag changes, everyone should see the change — and with copies you now have several things with the same name and a new convention about which one is the *real* config. Ana replied that mutation is what makes the bookkeeping impossible: if any function you hand the object to can reach in and change it, you can't reason about your own variable's value locally. Immutability makes the "which version is current" decision explicit instead of hidden in aliasing. Ben said explicit or not, you've recreated identity by hand — a current-version pointer plus frozen snapshots. Real entities genuinely change over time, and modeling a changing flag as a sequence of copies forces you to add IDs and a clock just to say "that same property, later." Ana answered that the bug is exactly the cost of "same property, later" when nobody knows who can mutate it; with immutable values a half-built state can't even be observed. Ben said that's a discipline issue: construct the new state fully, then swap one pointer atomically — mutation doesn't force you to expose partly built objects. I honestly couldn't call it. Please explain who's right about which specific point, what both of them are missing, and who is more right overall.
