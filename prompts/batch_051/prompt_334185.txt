I keep running into this one claim about why mutation is hard to think about, and I can't tell if its testable or just a slogan. The claim is that mutable state is hard not because of human working-memory limits, but because it breaks something semantic: when two names can point to the same array and a function can mutate that array behind your back, the same line of code can do different things depending on invisible history. So the difficulty is supposed to be about identity-over-time in the program, not about whats in the programmer's head.

The claim makes a prediction, I think. The semantic story says aliasing in particular should be nasty—two names, one object, mutation through one name showing up through the other—whereas the cognitive-load story says any hidden state should be roughly as bad, even if its just read-only. My friend says to just give people the same algorithm in a mutable and an immutable style and measure bug rates, but that seems confounded by whatever style they've been taught.

So I want you to design the test that would actually separate those two mechanisms. Human subjects, a static analyzer, a proof assistant, a tiny language you make up for the experiment—whatever you think is cleanest. Be concrete about the setup, the conditions, and the measurement. Say what result would count as evidence for the semantic story, what result would count as evidence for the cognitive-load story, and then be honest about what the best result still wouldn't settle. For example, could any experiment distinguish the claim that mutation is intrinsically hard from the claim that we've just all been trained to reason in a mutation-unfriendly way? I want the residue spelled out, not hand-waved.
