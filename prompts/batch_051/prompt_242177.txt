Okay so I have an analogy I've been dragging around for a while and I want a gut-check on whether it's actually doing real work, or if its just a cute way of restating the problem.

I keep wanting to model generic sentences like "ducks lay eggs" the way I'd model a class in code. Duck is a type, lay_eggs is a method on the type, and the truth of "ducks lay eggs" is about the type's interface, not about what fraction of instances succeed when you call the method. Male ducks are instances that throw UnsupportedOperationException (or belong to a subclass that doesn't implement the method). Ducklings are instances where the method exists but has an unmet precondition (sex, age). The sentence stays true because it's a claim about the type, not an average over instances.

Same with "mosquitoes carry malaria." On my model, the Mosquito type has a carry_malaria method, and the fact that most mosquito instances would return false doesn't falsify the sentence, because the sentence isn't a summation over instances.

So here's my actual theory, stated flatly: a generic statement is true iff the property is part of the kind's interface, where "interface" means something like the schema we use for the kind, not a statistical report on its members.

I want to know (a) whether this theory is actually saying something or just moving the question into the word "interface", and (b) where it breaks. Because I can already see one problem: I could write class Duck { def can_drive() } and obviously "ducks can drive" is false, so "interface" can't just mean whatever I decide to put in code. There has to be some constraint, but I don't know what it is.

And here's the case that's currently annoying me most: "lions have manes." I think that generic is at best weird and probably false, but a type-level method has_mane that checks sex is extremely natural, and my model would predict the sentence is true. If I try to fix it by saying has_mane lives on the male subtype, then I'm not doing type-level stuff anymore, I'm just grouping by observed instances, which defeats the whole point. Where does this go wrong — is the model hopeless, or does it get something right and just needs a constraint on which methods can live on the type?

Am I just reinventing some standard view in dumber words? If so, what's the closest standard view, and what's the thing my version still gets wrong?
