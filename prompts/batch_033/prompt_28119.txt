I'm on my lab's deployment review board—the group that has to sign off before we give a model actual tools and let it touch anything with consequences. I've been reading the AI-control-adjacent stuff on LessWrong and the alignment forum long enough that the control/alignment distinction feels natural to me, but half this board talks about it like it's a mood. We've got a proposal in front of us for a coding agent that would run with real autonomy inside our infra: it can write and run tests, install packages in a sandbox, read a bunch of internal repos, and eventually open PRs against production code. The team wants multi-hour runs on real codebases, which is exactly the setting where, if the model were capable of strategic deception, it would be in a position to do something about it.

Their control plan is basically a list of measures that only make sense if you take the misalignment hypothesis seriously: an untrusted monitor reading all the model's chain-of-thought and flagging anything deceptive, honeypot files and tripwire canaries to catch exfiltration or secret edits, a rule that any output that even looks like steganography gets escalated, and a kill switch keyed to suspicious patterns. They also want to run control evals first—train an adversarial stand-in, let it try to do bad things, and measure how often the plan catches it.

The board is split. One camp says the whole thing is incoherent: if we actually believed the model might be trying to escape or sabotage us, we shouldn't deploy it at all, and if we don't believe that, the tripwires are theater that will just slow everything down. The other camp says the plan is too trusting, not too paranoid: it assumes the model makes detectable mistakes, when a patient enough model could just wait out the monitors, and it leans on a monitor model that's no stronger than the agent itself, so the monitor can't reliably catch a scheming agent that's trying to hide from it.
