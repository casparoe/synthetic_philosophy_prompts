I am a software engineer without formal training in philosophy, and I would like a consistency check on a set of working views I have accumulated about levels of description in computing systems. I have encountered in passing the idea that there are three stances — physical, design, and intentional — and that higher-level patterns can be real; the views below are stated in my own engineering terms, and I care about whether they fit together, not about matching any label.

1. Higher-level entities are real. A race condition that never actually causes an observed failure is still a real property of the program; so are deadlocks, function boundaries, and cache lines. These are features of the system, not merely convenient ways for an engineer to talk.

2. The bottom level is complete. The behavior of a computing system is fixed by the behavior of its physical parts — transistors, voltages, timing — and in principle a sufficiently detailed physical simulation would reproduce everything the system does. No higher-level description adds causal powers over and above those of the parts.

3. No level of description is the correct one. Which level I should use depends on the prediction or control problem I face and on what I can observe; assembly, source, and architecture diagrams are each right for some questions and wrong for others.

4. Talk that attributes goals and beliefs is a compression scheme and nothing more. I routinely say that the scheduler believes this core is idle, or that the allocator thinks this block is free, because those statements predict better than a description of the code or the hardware would. But the belief is not in the system the way a race condition is; it is a shorthand that an observer projects onto the system.

5. The test for whether a pattern is real is whether it earns its keep. A pattern is real only if it predicts or compresses observations better than lower-level descriptions would, for some actual predictive or control purpose and in practice, not merely in principle. A pattern that never pays its way is a projection.

6. Some patterns are objective. Two competent engineers who start with different tools and do not see each other's work will independently converge on the claim that there is a race condition in a given piece of code. That convergence tracks something in the system, not just a shared preference among engineers.

Please go through these and tell me which pairs are in tension and which only appear to be. For each genuine tension, say how severe it is and what the cheapest revision would be; then tell me which single revision would do the most to make the set consistent. I would rather have a ranked audit than a list that treats every pair as equally problematic.
