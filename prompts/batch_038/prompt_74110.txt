ok so this has been bugging me for about a year and I finally articulated it to a coworker who just shrugged and went back to his PR.

I work in a big monorepo, and the thing is git doesn't actually store files. Every commit is a snapshot: each file's content gets hashed and stored as a blob, and the commit points at a tree that maps path names to those blob hashes. There's no little record anywhere that says "this blob is the next version of that blob." Nothing persists. `git mv old.py new.py` doesn't even record a rename — it just stages a delete and an add, and the rename only comes into existence later, when you run a diff and git compares contents and guesses that the two are similar enough to probably be the same thing. There's a similarity threshold you can tweak, I think it defaults to something like half the lines matching.

But then we have commands that answer "what's the history of this file?" and they don't agree with each other. `git log src/auth/session.py` walks the path — if someone renamed the file, the history stops dead at the rename, and if someone instead deleted every line and pasted a completely different module in under the same path, git happily reports all of it as one continuous file. `git log --follow` does the opposite: it reconstructs identity from content similarity and carries you back across renames, but it only works if you ask about exactly one file. And `git blame -C` goes further and attributes a line to some other file entirely, because it decided the code was moved or copied rather than written.

So there's this one file in our repo, `billing/invoices.py`. Eight years old, renamed four times, and there is not a single line left in it from the original version. Everyone on the team talks about it as one thing with one history, and half the time the tooling agrees with us and half the time it doesn't, depending which flag somebody typed.

What I want to know is what picture of "same file over time" this design actually presupposes. It feels like there are at least two answers baked in — identity by name/path, and identity by content — and they're treated as interchangeable when they plainly aren't. Is one of them the real commitment and the other just a convenience for humans? Or is the deeper point that there's no fact of the matter at all, and the question only gets an answer once you say what you're after (who wrote this, where did this bug come from, whose review do I need) — in which case git is right to have several answers but wrong to present them as answers about the same object?

Also tell me which rival picture it rules out. If you thought a file was some underlying thing that persists through total content replacement and through renaming, the way you'd think of a physical object, git has literally nowhere to put it. Is that a limitation of the data model, or an argument that the underlying-thing picture is bogus?

And practically — what would break if we picked one criterion and stuck to it? I'm thinking about everything that rides on top of file identity here: CODEOWNERS, `git bisect`, the blame-based "go ask this person," changelogs, license and attribution audits that care where a block of code came from. Which of those break under path-identity and which break under content-identity?

Oh, and one wrinkle I can't fit into the above: content-addressing is supposed to mean same content = same thing, but if I cherry-pick a commit onto another branch I get a totally different hash even when the resulting tree is byte-for-byte identical, because the parent is part of what gets hashed. So a commit's identity depends on its ancestry too, not just on what's in it. Does that mean git is commited to two different identity criteria at once, one for files and one for commits?
