I run model evals at a mid-size lab and every release we have the same fight: someone shows a benchmark where the model does great on average, someone else shows one hand-picked prompt where it does something awful, and we have no agreed way to settle which of those is the relevant fact. I want to write this into our release standard.

Can you give me a decision procedure an evals engineer can actually run on a proposed deployment? The questions in order, what counts as a passing answer at each step, how to choose and defend the input distribution you're averaging over, how many samples you'd need to say anything at all about a rare-but-catastrophic failure rate and what to do when you can't afford that many, where an adaptive adversary changes the answer versus where it doesn't, and which steps terminate in "this goes to a human" because the question is how bad the worst case is rather than how likely it is.

Then run it on two cases: a customer-support agent with tool access thats fine on 99.9% of tickets but can be steered into issuing a refund it shouldn't, and a coding model whose failure mode is a plausible-looking but subtly wrong security fix nobody catches until much later. One of those should come out no or not-yet even if the headline numbers look good — tell me which and why. And be upfront about which steps are judgement calls dressed up as procedure, plus what the procedure fundamentally can't tell us. Assume whoever runs it has about a week, no formal-methods background, and that anything short of a clean pass needs my sign-off plus legal's.
