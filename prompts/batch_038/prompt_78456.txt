Ok, so context: I'm an engineer on a small monitoring/red-team group at a lab. We ship a thing I'll just call the monitor — a probe sitting on top of the model's internal activations, trained to fire when the model is in a state we'd label as planning-to-deceive, based on elicitation runs where we made it do that on purpose. It got trained once, against one specific checkpoint, running one specific way, and it works decently there.

The problem is everything downstream of that. The model gets fine-tuned. It gets distilled into something smaller. Someone switches the serving stack to lower precision and different kernels. The system prompt gets rewritten. We swap the tokenizer. Every single time, a PM walks over and asks me the same question: does the monitor still apply, or do we have to rebuild it? And right now Im answering from vibes, which is exactly what you're not supposed to do when the thing you're monitoring for is rare and expensive to miss.

You're an expert on mechanistic interpretability, but I want you to also think like someone who validates diagnostic tests — sensitivity, specificity, what makes a measurement still measure the same construct after the instrument changes. Please think carefully, and before you write the procedure, spend a few paragraphs brainstorming the space of ways two systems can fail to share a mechanism. I specifically want you to separate out at least these four verdicts and be explicit about which one each test in your procedure is actually tracking: (a) same mechanism, same coordinates; (b) same function, relocated — the computation is still there but it's implemented somewhere else in the residual stream or by different units; (c) replaced — something functionally similar is doing the job but it isn't the mechanism we calibrated against; (d) gone or unreachable — the behavior can't be produced this way anymore. Flag the places where those come apart in practice, especially a change that keeps the function but scrambles the coordinates, and a change that keeps the coordinates but makes the state unreachable from the new prompt distribution.

The deliverable I want is a reusable decision procedure, not an essay: numbered questions to run in order, what counts as a pass at each one, roughly what each step costs in compute or human time, and where the procedure stops and hands the call to a person because the remaining question is a judgment call dressed up as a threshold. Say plainly which steps those are. Assume the person running it is a junior engineer or a program manager who has not read the interpretability literature, so any step that secretly needs that expertise has to be marked as a handoff rather than written as if they can do it.
