We're about to run a batch of experiments where trained agents play one-shot games against each other and each agent gets handed the other's policy source code as part of its input — basically Tennenholtz's program equilibrium setup, where the players submit programs instead of strategies and the programs read each other's code before outputting an action. Before I let anyone in the group argue from those results that "mutually transparent agents will cooperate," I want the spec: what does a solution concept for this setting have to actually deliver to count as adequate? Not a tour of program games, not the history — the requirements list.

Here's what I already have in play, and I'll describe each so you don't have to guess which variant I mean:
- the clique-bot move: cooperate iff the opponent's code is string-identical to yours, defect otherwise. Mutual cooperation is an equilibrium here, but one extra space anywhere in either file and you both defect.
- the Löbian fair-bot: cooperate iff you can find a proof that the opponent will cooperate against you, defect otherwise.
- ε-grounded simulation: with small probability ε cooperate, otherwise actually run the opponent's program on your own code and output whatever it returns.
- the folk theorem for this setting: every payoff vector that's feasible and individually rational in the base game is achievable in program equilibrium.

For each requirement give me (i) what it demands, (ii) the concrete case or result that motivates it, (iii) whether you think it's non-negotiable or just the taste of one camp. There are two camps here — pure game theorists who only care whether the equilibrium exists, and people like me who want to make claims about systems that actually get deployed — and I want the list marked for which camp each item belongs to. My purpose sets the bar: I want a concept good enough to license predictions about agents run against opponents nobody chose, whose code has been through a compiler, an optimizer, and possibly a fine-tune since anyone read it. So anything that only matters for hand-written toy programs should be flagged as such rather than smuggled into the core.

Things I specifically want you to rule in or rule out, with reasons:

1. Robustness to syntactic noise versus incentive-compatibility. My worry is that these can't both hold: a program tolerant enough to still cooperate with a slightly-different opponent is also tolerant enough to get exploited by an opponent that defects only inside the tolerance window. If you think that's right, say so and tell me which one should give. If you think it's wrong, sketch the construction.
2. Non-termination and mutual simulation. Two programs that each try to simulate the other don't halt. We're thinking of putting a hard wall-clock timeout on every run and paying both sides the minimax payoff when it fires. Is that a fix or a new problem — does the timeout become part of the strategy space, and does the solution concept have to say what counts as the game once resource bounds are inside it?
3. The code you can read isn't the code that runs. Stale copies, build artifacts, weights that don't match the source, an opponent who can recompile between the moment you read them and the moment you act. Does adequacy require a program-level analogue of subgame perfection — no profitable deviation at any point where revision is still possible?
4. Equilibrium in programs versus equilibrium in behaviour. Infinitely many program pairs produce the same action profile. Should a concept that can't pick among behaviourally equivalent implementations count as predictive at all, and how much of the folk theorem's near-vacuity comes from that?
5. Whose utility the program is optimizing. Ours are trained, not written, so there's no guarantee the submitted program's objective is the objective of whoever put it in the arena. Is closing that gap a requirement on the solution concept or on the experiment?
