**DRAFT: "Right answer, wrong route"**

**1. The switch I want to make.** Almost all monitoring asks a question about outputs: is this answer weird, is this plan scary, does this transcript look like the model is lying. But the output is the last step of a long causal process, and two very different processes can end in the same token string. So suppose instead we have some handle on the internals — say we've done enough patching and ablation on a task family that we can roughly say which components carry which information and which input features the answer depends on — and we build the detector to ask a different question: *did this answer come out of the mechanism we checked, or out of something else?*

**2. Why that seems like an improvement.** Two cases motivate it for me. First, right answer wrong route. A model asked whether some function handles an empty input gives the correct "no." On the validation set, the correct answers came from a pathway that actually traced the branch conditions in the code. On this one, the answer is right but it came from somewhere else entirely — the function name matched something it had seen, and the "no" is basically a retrieved docstring sentiment. Output monitoring sees a correct answer and moves on. Second, wrong answer right route. The same branch-tracing pathway, run on code where the relevant branch is 400 lines away and gets truncated out of context, produces a confidently wrong answer. The mechanism is the one I validated; it's just been pointed outside its scope. I'd rather be told "your validated mechanism is running on an input it was never validated against" than "this output looks off," because the first tells me what to fix.

**3. The problem: same as what?** Everything above assumes I can say when two runs use "the same mechanism," and I don't think I can. My best candidate is a counterfactual one: two runs use the same mechanism iff they have the same causal profile — the same sites matter, patching them from one run into the other changes the output in the same way, and the output depends on the same features of the input. Same dependencies, same sensitivity, same mechanism. That feels right and also feels like it's smuggling in three problems.

**(a) The grain problem.** A causal profile is only defined relative to a battery of interventions, and any battery is finite. Coarse battery: too many genuinely different pathways look identical. Fine battery: everything differs from everything, because two runs on different token strings have different residual stream contents and some site's patching effect will differ in the third decimal place no matter how similar the tasks are. So "same mechanism" turns out to be indexed to which differences I chose to care about. I have a wobbly analogy I'm not sure is allowed: asking whether two runs use the same mechanism is like asking whether two performances of a song are the same performance. There's no fact until you say which respects count. If that's right, mechanism identity isn't discovered by the detector, it's decided by the designer — which makes the detector's verdicts partly a statement of my interests, and I don't know if that's fine or fatal.

**(b) Multiple realizability.** Matching causal profiles might be too *coarse* at the same time as being too fine. Two differently wired subcircuits can imitate each other across a fixed battery — a lookup route and a composition of two smaller routes that happen to reproduce the same dependence pattern on the inputs I tested. Same profile, different algorithm. And the algorithm is arguably the thing I care about, since "how it got the answer" is what tells me whether the answer generalizes.

**(c) The baseline problem.** Same mechanism as *what*? Three options: a single stored reference run, a human-written circuit hypothesis, or the distribution of profiles over my validation set. The first two are brittle and I can't produce them for new task types. The third is the only statistically sane one, but then "the mechanism" has become a distribution and my question has quietly changed from *is this identical to that* to *is this typical of those*. Which looks an awful lot like behavioral anomaly detection, just with much more expensive features. If that's what I've done, the whole project is a detour.

**(d) The stable-liar worry.** And the typicality version fails on the case I most care about. If a model has a consistent alternate way of answering — one it uses reliably whenever some condition holds — it will look perfectly typical *within* that condition. Consistency checks catch instability, not stable-but-unvalidated pathways. Only comparison against an external "this is the pathway we approved" catches that, and (c) just told me I don't have one.

**4. What I want to try instead: subsumption, not identity.** Stop asking whether this run used the same mechanism. Ask whether it used *any mechanism I can already explain and have already signed off on*. Keep a library of mechanism-families, each with (i) a causal profile plus tolerances, (ii) an account of which input features it depends on, and (iii) a written reason why that dependence is acceptable on this task type. A run is anomalous iff its profile is within tolerance of nothing in the library. Anomaly = no benign explanation on file, rather than anomaly = difference from a reference. That seems to fix (d), because a stable alternate pathway is anomalous precisely by being absent from the library, and it makes false positives mean "we found something we don't understand yet," which is a thing worth knowing and not an emergency.

**5. Costs I can see.** Per-run interventions are absurdly expensive, so you'd train a cheap proxy to predict causal profiles from activations — and now the proxy is itself a mechanism whose sameness you'd need to check, and I think that's a regress rather than a solution. The library has to be maintained as models and task mixes change. And "tolerance" is doing all the work in section 4 while I have no principled way to set it, which might mean I've only moved the grain problem from the battery to the threshold.
