Ok so this might not be a philosophy question but somewhere along the way I started thinking it is, and I don't have anyone to ask.

I run a mid-size electronics outfit. Me and one competitor both depend on the same contract manufacturer, and that fab only has so much line capacity each quarter. Every quarter we each submit a booking request. If we both ask for a modest slice, the fab is happy, unit prices stay normal, we both get what we need. If we both ask for the lion's share, the fab auctions the capacity instead, the price jumps for everybody, and we each end up paying way more than we would have. Trouble is, from where I sit, asking big is always the safer play, and I've got every reason to think their CEO sees it exactly the same way. So we've spent three years asking big and paying for it.

Last month their ops lead floated something I've never heard of. Not a negotiation — no handshake deal, no side letter, our counsel would have a fit. Instead, we would each publish the actual decision procedure our team uses to compute the quarterly request. Not a description of it. The literal spreadsheet logic and code, handed over under audit, so each side can read the other's rule before writing its own. His pitch: if I can read their rule and see that it matches any escalation from me, and they can read mine and see the same thing, then neither of us escalates and we both come out ahead. He keeps saying it isn't collusion because nobody agreed to anything, we just stopped hiding.

I said yes in principle and now I cant sleep. Four things are bugging me:

1. If my rule is written to react to what their rule says, and theirs is written to react to what mine says, is there any fact of the matter about what either of us actually does? It feels like two mirrors pointed at each other. Our engineer says just feed their program into ours and run it, and when I asked what happens when their program is trying to run ours at the same time he got irritated and said it obviously terminates. I don't think it does.

2. Their side has a newer version of the proposal: instead of actually executing each other's code, each of us trains a model to read the other's code and predict what it'll do. That sounds like it fixes number 1, but now we'd be cooperating with a prediction of each other instead of with each other, and I can't tell whether thats a fix or a bigger hole.

3. Is there something to gain by being the one who goes first, or by publishing a rule that doesn't read theirs at all — just a fixed number no matter what they do? It feels like a rule that ignores the other side is either extremely safe or extremely easy to walk all over and I can't tell which.

4. The big one: none of this bites unless the code we hand over is the code we actually run. What stops either of us from showing a nice cooperative rule and running something else? Is there a setup where the honesty part takes care of itself, or do we need an auditor with real teeth — and if we need that, why bother with the code at all?

I have this nagging feeling that this whole arrangement has a name and that people have already worked out a lot of it, including which of my four worries are real problems with no workaround and which are just me being a businessman out of his depth. Can you tell me what's actually going on here, and then tell me whether there's a version of this deal a rational person should sign? Don't worry about the antitrust angle, assume counsel cleared it.
