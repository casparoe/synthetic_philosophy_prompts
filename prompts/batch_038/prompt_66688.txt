I write backend systems for a living and I have never taken a philosophy course, so I want to be explicit about what I can and cannot evaluate in your response. Six weeks ago my team stood up an internal module, "Assertions, Flags, and Fact-Checking," for new engineers who work on our claims pipeline. I run it, and the final assessment is a 90-minute in-class essay worth 20 marks. The module's third and fourth weeks cover deflationary theories of truth, which I teach because our product attaches a boolean column to a record and calls that column verification. I have drafted the artifact the question will be built on, but I do not trust my own instincts about where the philosophical pressure actually is, and I need the question, a model answer, and a marking scheme.

First, the artifact. I invented it, simplified from our production system, so no student can have seen it and no answer can be copied from anywhere:

Our table is called ClaimStore. Each row has `claim_id`, `text` (a well-formed declarative sentence in a restricted fragment of English), `source`, and a boolean `verified`, plus who set it and when. The design doc asserts one invariant, which the doc's author named the disquotation invariant: for every row r, `verified(r)` is TRUE if and only if the sentence stored in `text(r)` holds. Nothing else in the doc explains what the flag means; the doc says the invariant is the whole story.

Three downstream systems consume the flag.

1. A roll-up rule, stated once in a config file: every row in the verified set is true. The table grows continuously, so this rule cannot be expanded into a finite list of rows, and it must cover rows that do not exist yet.
2. An endorsement service that never parses `text` at all. It is permitted to surface, forward, and act on flagged rows, and its logs contain lines that attribute content it has never read, of the form: whatever the sensor asserted yesterday is true.
3. An accountability rule. Acting on an unflagged row is a process violation. Acting on a flagged row that later turns out to be false opens an incident in which the person who set the flag is held to account personally, and the review is not blameless. The design doc describes this as the flag carrying a norm.

There is also an open ticket. Row 4471 has a `text` value that says, of that very row, that its `verified` field is FALSE. Under the disquotation invariant the flag on that row is TRUE exactly when it is FALSE. The on-call engineer closed the ticket with a validation rule rejecting any `text` value containing the strings verified, true, or claim_id. The table still grows and the roll-up rule still runs.
