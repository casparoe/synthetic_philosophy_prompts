so I'm building an anomaly-detection harness for fine-tuned agent models, and my advisor read the methods section and said my criterion for mechanism identity proves too much — that it collapses into "there are no mechanisms, hence no anomalies." I've been staring at it for a week and cant find the bad step. Here's the argument as I now reconstruct it.

Setup so the terms aren't floating: by a mechanism I mean whatever subcomputation inside the model carries some behavior. I identify mechanisms by intervention, not by reading weights — patch activations in and out, see what the behavior follows. Two checkpoints count as running the same mechanism for a behavior when the interventions come out the same. That's the whole method, and the harness flags an anomaly when a fine-tune's behavior is carried by something other than the mechanism that carried it in the reference model.

(1) Two mechanisms are the same mechanism iff they have the same causal profile: same outputs for same inputs, same response to same interventions.
(2) Nothing further could constitute mechanism identity. If no intervention, however elaborate, could tell M1 from M2, then there's no fact of the matter beyond that — the causal profile is all there is.
(3) Any circuit in a model has only a finite causal profile relative to the interventions anyone can actually perform, since performing an intervention costs compute and there's finitely much of it.
(4) For any finite causal profile you can write down a lookup table — hardcoded, hand-built, bearing no structural resemblance to the original weights — that reproduces it exactly.
(5) So by (1) and (2), every mechanism we could ever study is identical to some lookup table.
(6) Identity is transitive, so everything sharing a profile is one mechanism: the trained circuit, the lookup table, and a completly different implementation in a different model family are all the same mechanism.
(7) So a reference checkpoint and its fine-tune can never differ in mechanism, only in causal profile. But profile differences are exactly what my harness was supposed to explain by appeal to mechanisms, not what it was supposed to be reduced to. Either there's nothing mechanistic to detect, or detecting it isn't a mechanistic enterprise.
(8) Therefore (1) is false: mechanism identity is not fixed by causal profile.

I really don't want (8). If causal profile doesn't fix mechanism identity then I've lost any substrate-neutral way to compare across model families, and the project has no method left — I'd be reduced to saying two mechanisms are the same when their weights are similar, which is hopeless given superposition and given that I want to compare different architectures. But I also can't see how to hold onto (1) through (6), and each of those looks fine to me in isolation, tho I'm aware that's exactly what a bad argument feels like from the inside.

So: which step do you reject, and why did it look innocent on the way in? If more than one is rejectable, rank them by what giving them up costs me. And if you think (1) actually survives, tell me what the harness is picking up when it fires — because if the honest answer is just "different causal profile," then the word mechanism isn't doing any work in my methods section and I should delete it.
