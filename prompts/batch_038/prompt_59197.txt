I audit smart contracts for a living: six years of Solidity, EVM semantics, storage layouts, proxy patterns, gas behaviour, and the formal-verification tooling built around them. I know enough game theory to follow a Nash equilibrium and the rough shape of the folk theorem for repeated games, but I am not a theorist. I recently came across the program-equilibrium literature — the setting Tennenholtz gave that name to in 2004, after earlier work by McAfee, Howard, and Rubinstein — in which players do not choose actions but submit computer programs that play a base game on their behalf, each program receiving the other program's source code as input and returning an action, and a program equilibrium is then a Nash equilibrium over pairs of programs. Three constructions struck me, and I want to hold them against the world I actually work in:

(a) Syntactic comparison: a program that cooperates if and only if the opponent's submitted program is character-for-character identical to its own code, and defects otherwise. Two copies of it cooperate, and neither can gain by deviating, since any different program gets defected against.

(b) Proof-based cooperation: a program that cooperates if and only if it can find a proof, in some fixed formal system, that the opponent's program run against it would cooperate. Löb's theorem is used to show that two such programs cooperate with one another, and that, assuming the proof system is consistent, a program that would defect simply gets defected against.

(c) ε-grounded simulation: a program that cooperates with small probability ε and otherwise calls the opponent's program on itself, so that mutual recursion terminates almost surely while a would-be defector is punished in expectation.

The literature also has a folk theorem: a payoff vector is achievable in some program equilibrium exactly when it is feasible and individually rational — essentially the whole repeated-game payoff set, obtained in a single simultaneous move.

Please restate all of this in my vocabulary, as faithfully as you can: deployed bytecode versus verified source, storage slots and mutable state, calls and delegatecall, revert and gas limits, immutable versus upgradeable contracts, timelocks and multisigs, the mempool and transaction ordering, the cost of computation, and the difference between what a contract does and what it can be made to do by the state it happens to be called in. Take the three constructions one at a time and then the folk theorem, and for each say what has a clean on-chain counterpart, what you had to bend to make it fit, and what cannot be expressed at all.

Then give me the residue report, which is the part I actually care about:

1. Flag every place the translation is doing work rather than describing something — every time you find yourself importing an assumption from my world (gas is finite, state persists between calls, the code at an address can be swapped behind a proxy, calls have side effects, ordering is auctioned) — and say whether the original result still holds once that assumption is in place.

2. Say whether the premise that two programs can inspect and reason about each other freely, costlessly, and without altering anything is load-bearing for the cooperative results. If it is, I want your view on whether the program-equilibrium folk theorem is best read as a theorem about games or as a theorem about an idealized interpreter nobody has.

3. Tell me which way the residue runs. I can already see that some things survive better on-chain than in the theory — immutability makes precommitment genuinely credible, where the theory seems to need an outside enforcer to guarantee that the code submitted is the code that runs. Say what else survives better, and what has no on-chain home at all, Löbian reasoning included: whether an agent here can even pose a counterfactual question about its opponent's action without paying for it and revealing that it asked.

4. Say whether anything important in my world — MEV, statefulness across transactions, governance forks that change the payoff function itself — is invisible in their framework in a way that suggests it answers a question I would not recognize as mine.

Be honest about failure. If a construction has no counterpart in what I do, say so plainly rather than reaching for an analogy.
