I'm a backend engineer with about twenty years in distributed systems and no philosophy training beyond some Wikipedia rabbit holes that I now regret starting. I got interested in the causal exclusion argument after arguing with a colleague about whether a language model's "beliefs" cause its outputs or whether it's really just the weights doing everything, and I've since realized I can't get two of my own beliefs to stop fighting. The first is that at the hardware level, every event has a sufficient physical cause: transistors and electrons, no gaps for anything else to fill. The second is that every postmortem I've ever written contains a sentence like "the missing null check caused the outage," and I've never once felt I was lying. When I read the standard positions on this — non-reductive physicalism, Davidson's anomalous monism, interventionist accounts of causation, epiphenomenalism, the identity theory — I understand each one while I'm reading it, then immediately lose track of which combination of commitments I actually hold, and I suspect half my colleagues are in the same boat. So please write me a decision tree for our reading group. It should start from the one commitment I'm sure about, causal closure at the hardware level, and end at leaves labeled with positions, though an unnamed-but-defensible leaf is fine if you say what it amounts to.

The tree's branch points must be questions a person can answer from concrete cases without knowing which position the branch leads to. Use cases I actually recognize from work. Case one: the missing null check in the service layer, and the postmortem sentence blaming it — literally true, true only as shorthand for some physical state, or a useful fiction? Case two: the same program ported between radically different machines, so two systems are in the same software state while sharing essentially no physical state — does anything causal survive the port, or is "the same bug" just a label on a coincidence? Case three: the distributed failure where no single machine is misbehaving, but every node is waiting on a message no one will ever send, and the postmortem says "the deadlock caused the outage" — is the deadlock itself a cause, a mere description of a pile of causes, or neither? Case four: the observation that if you had intervened at the software level and flipped the null check in, holding everything else fixed, there would have been no outage — does that settle that the null check was a cause? Case five: one section of the postmortem blames the null check and another blames the machine state, and someone objects that you can't have both — is that right, or can one event have both as genuine causes?

Beyond that, a few requirements. One node must turn on whether explanation and causation can come apart, so that "the deadlock explains the outage" could be true even if "the deadlock caused the outage" is false. One node must turn on the difference between thinking of causes as producers and thinking of them as difference-makers, roughly case one versus case four. Multiple realizability from case two should appear, and the tree should be honest about whether it does causal work or only descriptive work. The leaves must include reduction or identity, realization-based non-reductive physicalism, an interventionist option, something in the neighborhood of Davidson's view that strict causation is always physical while software talk still earns its keep, epiphenomenalism, and the option that software states are useful fictions. Build the tree from the logical space of answers to your questions rather than from a list of famous names: figure out the questions and their combinations first, then locate the actual positions in that space, and note any combination nobody seems to occupy, with a guess as to whether that's because it's incoherent, unattractive, or just unexplored. Flag any pair of leaves your tree cannot really separate, and say what case, if any, would pull them apart. Keep it to nine questions or fewer.

One formatting note, and it's firm: our internal wiki mangles anything fancy and I'll be reading this on my phone in an airport, so continuous prose only. No headings, no bullet points, no numbered lists, no bold, no tables. Write each question and its branch options as ordinary sentences, the whole tree as if you were dictating it to a colleague in an email.
