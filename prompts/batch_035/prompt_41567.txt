I'm a backend engineer and something that's been bugging me about how we model data. In basically every app I've worked on there are two ways of storing the same customer. There's the mutable row: a users table where you just overwrite fields in place, so the user is whatever the row currently says and the past is just gone. And there's the event log: an append-only list of everything that ever happened, where the "user" is more like the whole history, and the current state is just the latest projection you compute from it. Some people (the event sourcing crowd) go all the way and insist the log is the source of truth and the table is just a cache. So what view of what a thing IS does each approach presuppose -- is a user a thing that stays numerically the same while its properties change, or is it a sequence of states strung together? Does the plain mutable table actually commit you to anything, or is it compatible with both pictures? And note we run both at the same time, with the same primary key meaning "same customer" across all edits, including ones that change every field -- is that coherent or are we quietly equivocating about what the ID refers to? I gather philosophers have a whole fight about how objects persist through time, so map this onto that if it helps. And tell me: if a team decided the event log is the real source of truth, does that force any other changes in how they'd treat identity, merges, or "the same user" questions, or is it genuinely just an implementation detail with no metaphysics attached?
