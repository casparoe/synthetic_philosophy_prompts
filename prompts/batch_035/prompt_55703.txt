I'm a high school student who has been reading about mechanistic interpretability and AI safety, and I keep running into a question that seems to sit underneath a lot of that work without ever being spelled out: when we say a model is "using the same mechanism" in two situations, what would actually make that true? Researchers want to catch a model that has switched to a different internal process by comparing it to the process it was originally verified to have, but I have not seen anyone lay out what a criterion of mechanistic sameness has to deliver before it can do that job. Before I try to evaluate or build any test, I want the full specification.

Please write the desiderata for a criterion of mechanistic sameness — a rule that takes a model plus either two inputs or two versions of a model and says whether the same mechanism produced the outputs. For each requirement, give the case or consideration behind it, mark it as non-negotiable or as a preference of one research camp, and flag any pair of requirements you suspect cannot be jointly satisfied. That last part is the part I most want to see.

To show the level of case I mean, here are some situations I think the criterion has to sort correctly:

1. A model does arithmetic through a genuine carry-propagating circuit on most inputs, but on inputs matching a certain pattern it quietly uses a memorized table that returns the same answers. Same behavior from the outside; different mechanism underneath. The criterion has to call this different.
2. Two models trained from different random seeds solve a task with circuits wired in a different order, built on somewhat different features, in a way knowledgeable people would intuitively call the same algorithm. The criterion has to call this the same.
3. A model is fine-tuned so that a safety check runs before every output; later, the check still fires every time, in exactly the same form, but its output no longer gates anything downstream — it has become decoration. Has the safety mechanism survived, and what does the criterion need in order to tell decoration from function?
4. The same model under a small weight perturbation: outputs barely change, but internal statistics shift in ways that could be noise or could be a handoff to a backup pathway, and nothing about the outputs alone can tell us which.
5. A dead-code case: a component that once did the work is still active but redundant, because a second component learned to duplicate it. Which component is the mechanism now, and does the criterion need a notion of "the" mechanism at all, versus a set of them?

After the requirements, tell me which single requirement does the most to exclude candidate criteria, and then go through two specific candidates — pure behavioral equivalence, and sameness of internal activations under a fixed metric — saying exactly which numbered requirement each one fails and why.

For format, please give me:

A table with columns: "No." (so later sections can cite requirements by number), "Requirement" (a short name), "What it demands", "Case or consideration behind it" (cite one of my five or add your own), "Status" (non-negotiable / camp preference), and "Tension with" (requirement numbers it may conflict with, or none).

Then a short prose section on the jointly unsatisfiable pairs, if you think there are any — that is the result I care most about, since a spec whose demands conflict is itself a finding.

Then the two candidate-criterion paragraphs.

Finally, a JSON object summarizing everything, with this schema: { "requirements": [ { "no": integer, "name": string, "one_line": string, "status": string } ], "jointly_unsatisfiable_pairs": [ [integer, integer] ], "most_excluding_requirement": integer, "behavioral_equivalence_fails": [integer], "fixed_metric_activation_similarity_fails": [integer] } — where each integer refers to a requirement number from the table.
