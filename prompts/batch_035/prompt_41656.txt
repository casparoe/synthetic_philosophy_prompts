i sit on the safety review board at a mid-size AI lab. every couple of weeks we get a deployment proposal for giving a model more agentic access — browsing, running code, sending emails on a user's behalf, that kind of thing — and the stakes are real because these things go out to millions of users. the problem I keep hitting is that proposals bundle a list of safety measures together and never say which KIND of measure each one is, and the kind matters a lot. some measures are evidence that the model isn't misaligned (alignment evals, red-team reports, honesty benchmarks). others are protection in case it IS misaligned (rate limits, requiring a human confirmation click for certain actions, a separate classifier watching outputs, honeypot tasks). the unofficial doctrine around here, borrowed from the ai control crowd, is that for high-capability models the second kind has to carry the load, because alignment evidence is always provisional — the model could pass every eval and still behave badly in situations the evals didn't happen to cover, or behave badly only when it really matters. but nobody has written down how to actually apply this when a proposal lands on my desk and I have maybe an hour before the review meeting, after which our safety lead signs the final call.

write me a procedure the board can run on a proposal. it should:

1. sort each proposed measure into "evidence the model is fine" vs "protection if it isn't", with tests that work when a measure is ambiguous. a monitoring model, for example, is protection with respect to the deployed model but evidence with respect to itself, and the procedure needs to handle that nesting instead of pretending everything sorts cleanly.
2. say what a proposal must include for each measure to count — the failure story it's guarding against, the assumption about the model it silently makes — and what counts as insufficient.
3. mark the points where the procedure stops and a human has to make a values call: how much residual risk is acceptable given the upside, whether trusting the red-team report is a bet on that team's competence and honesty that no checklist can make for us, and so on.
4. be honest about where it will misfire: measures that stack so the categories stop mattering (defense in depth), proposals written to blur the categories on purpose, monitoring thats so costly in latency that the product team quietly turns it off after launch.

then run it on three measures from a proposal we actually got last month: (a) a report from the alignment team that the model refused sabotage opportunities in 500 staged scenarios, (b) a rule that any outbound email over a certain length gets a confirmation click from the user, (c) a second model that watches the main model's tool-use transcripts and flags anything "suspicious". tell me what the procedure says about each, and be blunt about (a) — the alignment team put months of work into it and they'll be annoyed, but I suspect the procedure will come back saying it can't substitute for control, and I want to know if thats right or if I'm being too hard on them. also say straight up what the procedure cannot do, so we don't start treating it as more than it is.
