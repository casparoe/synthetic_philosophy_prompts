been reading the AI safety sphere forever (lurked lesswrong back when the sequences were still being posted as posts) and the thing i keep noticing about control research -- the whole "assume the model might be misaligned and build safety around that" agenda -- is that people argue past each other because nobody has agreed what the thing is actually supposed to DO. one person judges a control scheme by whether it would stop a full treacherous turn, another judges it by whether it's cheap enough that a lab would actually deploy it, and each thinks the other's standard is cope. so before i go read another proposal, i want the spec first. write the desiderata: what an adequate control scheme has to deliver, which cases it must get right, which things it's not allowed to depend on -- with the consideration behind each -- and flag any pair of requirements you suspect can't be jointly satisfied, because i think that's where the real content is. then briefly, how the main live approaches do against the list (scaffold-level monitoring with a seperately trusted model, interpretability-based honesty checks, dangerous-capability evals used as deployment gates, and just making the model aligned so you don't need control at all). keep the weight on the criteria though, not the scorecard.

here are things i'd want on the list but am happy to be argued out of, so treat these as drafts not the spec:

- it can't condition on knowing HOW the model is misaligned. the whole point of control vs alignment is you're buying insurance against failure modes you can't currently specify, so a scheme that only works against scheming-as-described-in-your-favorite-essay is security theater.

- the scheme can't need the subject model's cooperation for safety-critical functions. asking the model to honestly report whether it's scheming in its chain of thought is only doing oversight work if the model is already honest, which is the thing in question. but is asking the model to justify its actions to a monitor "cooperation"? i go back and forth on where the line is, since in practice control schemes do query the model all the time.

- you have to be able to measure how good the scheme is without possessing a real misaligned model. labs don't have a confirmed schemer sitting in a box, so all they can do is prompt a model to role-play misaligned or fine-tune one to be misaligned for evals, and both of those feel like testing a firewall against a drawing of a hacker. can this requirement even be stated in a way that isn't unsatisfiable on its face?

- it has to stay safe while the model knows the scheme. the model reads the system prompt, knows the monitoring setup exists, and gets iterated against it over time, so the scheme needs to survive adversarial optimization pressure from something smarter than your red team. but every actual control eval runs against today's models or against humans, both dumber than what we're insuring against. this one feels like the closest thing to a real impossibility result lurking in the setup.

- the monitor can't share blind spots with the thing it's monitoring. if your untrusted model and your monitoring model are both fine-tunes of the same base, they may fail on the same things, so the monitor inherits exactly the failures you needed it to catch. but the pressure runs the other way: monitoring is hard, you want a strong monitor, and the strong models all come from the same few bases. flagging this as a pair that maybe can't be jointly satisfied.

- it has to fail loudly. a control scheme that quietly stops working is worse than none, because it eats the safety budget -- everyone feels covered and stops doing the other stuff -- while providing nothing.

- it has to be cheap enough to actually run. a scheme with 100x compute overhead doesn't get deployed, the lab just ships without it. but is that a real desideratum or cope for labs that want to ship no matter what? i genuinely don't know where the line is between "adequate for deployment" and "good enough to justify deployment" and i'd want the list to take a stance.

- it has to keep working when the task domain shifts. monitoring is presumably distributional -- catching outputs that look like a model going off the rails -- but deployment is exactly the model doing novel stuff nobody has monitored before. so whatever the monitor keys on has to be about behavior type, not task type.

also please say which single requirement does the most work excluding actual proposals. my guess is it's the no-cooperation-on-safety-critical-functions one, since it quietly kills every scheme whose safety story routes through the model being nice, but i want to know if you disagree. and if some subset of these turns out jointly unsatisfiable given anything we actually know -- the monitoring compute gap, whatever -- i want that said plainly rather than handwaved, because "the desiderata are unsatisfiable, that's the result" is the answer i'm half expecting and honestly the one i'd find most useful.
