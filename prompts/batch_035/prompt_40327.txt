we've got this function in our legacy payments code, call it resolveAccountId, written like 9 years ago by a guy who left before I joined. No spec, no design doc, no comments worth anything. It takes a user submitted account string and returns a canonical account id. Its been fine forever. Last week a ticket comes in: an account string that starts with a "-" and the function does something genuinely weird with it, behavior thats been there the whole time but nobody ever hit it.

Now half the team wants to call it a bug and fix it, the other half says its intended behavior ("its worked this way for 9 years, people probably depend on it, don't touch it"). Standard stuff. But I got into an argument with a teammate, Maya, about something underneath that, and its bugging me.

Maya says obviously there's a fact of the matter about whether its a bug — the original author wrote it with some intent, and if we read the code carefully enough we'd figure out what he meant it to do, and that settles it. I pointed out we've all read the code. Its string parsing with a couple regexes. There's nothing in there that says anything about inputs starting with "-". She then said the unit tests settle it. But the tests only cover the inputs someone thought to write down back then — none of them touch this case, so I don't see how they determine anything about it. Its like, all the evidence we have is a finite pile of past inputs and what the function did on those, and the new input just isn't in the pile. Reading the pile harder doesn't seem to add anything.

Then another guy on the team, Dave, said I'm massively overthinking this and the answer is that there IS no fact of the matter at all — a program only means what we decide it means going forward, the past can't constrain us, just pick whatever behavior we want and update the docs. But that also feels wrong to me? Like if someone proposed a "fix" that made it return garbage on inputs the old version handled perfectly, I'd want to say they misunderstood the function, not just that they made a different choice. I can't really justify that though.

So, questions. Is Maya right that careful reading would reveal the intent? Am I right that nothing in the code or the tests pins down what it should do on the new input? Is Dave right that there's just nothing there and its all decision? These all seem to pull in different directions and I can't find a view Im happy with. And separately — does any of this actually matter for the practical bug/no-bug call, or is that just an engineering tradeoff (who depends on the weird behavior, whats the migration cost, etc) and this whole other debate is disconnected from it? Something about the situation feels genuinely weird to me — everyone "knew how the function works" for 9 years, and the moment an input shows up that the history never touched, it turns out that all that knowing doesn't obviously add up to an answer. Feels like it generalizes beyond this one function too, to specs generally, but I cant put my finger on how.
