In test-driven development, a programmer writes automated tests before writing the code itself, and many teams treat a passing test suite as settling what the program was supposed to do — the tests, they say, are the specification. Yet any finite battery of tests is compatible with infinitely many functions that agree on the tested inputs and diverge everywhere else, a point developers run into whenever a suite passes but users still report bugs. What view of rules and their applications does this practice presuppose? Does treating tests as a spec presuppose that a rule's content is fixed by an enumeration of its applications, and if so, how does that sit with the rule-following considerations suggesting that no list of applications can determine what one meant to compute? Note also the practice's own piecemeal escapes — adding a test whenever a bug surfaces, or replacing enumerated cases with property-based tests that generalize — and say whether these presuppose a different, richer conception of specification than the base practice does. Reconstruct the implicit theory, distinguish what the practice strictly presupposes from what it merely fits well with, and tell me whether the whole thing is philosophically underdetermined, i.e., compatible with rival views about what a rule's content consists in.
